# hexoflat

Original cooperative tactical fantasy game: turn-based combat on a hex-grid map, card-based character abilities, progression, scenarios, persistent campaign.

Inspired by general tactical dungeon-crawler concepts (including Frosthaven), but must not copy its names, characters, story, texts, artwork, terminology, balance, or other protected content. All mechanics, worldbuilding, classes, enemies, abilities, scenarios, and visual assets must be original.

## Target stack

- Monorepo: pnpm workspaces + Turborepo
- Frontend (`apps/web`): Vue 3 + TypeScript + Vite
- UI state: Pinia
- Server state: TanStack Query
- Board renderer: PixiJS
- Game engine: `packages/engine` — pure TypeScript, zero dependency on Vue, browser APIs, NestJS, or the database
- Backend (`apps/api`): NestJS + Fastify adapter
- API: REST + WebSocket
- Database: PostgreSQL
- ORM: **Drizzle** (decided 2026-07-29 — TS/SQL-first, fits the Zod-heavy style already in the repo; not Prisma)
- Validation: Zod
- Auth: **custom lightweight JWT auth in NestJS** (decided 2026-07-29 — not Keycloak/Auth0, revisit only if the project goes multi-org/enterprise)
- Asset storage: S3-compatible
- Testing: Vitest (unit) + **Playwright** (e2e, decided 2026-07-29 — not Cypress; better fit for multi-tab/WebSocket drop-in/drop-out co-op scenarios)
- Deployment: Docker (`apps/api`), GitHub Pages (`apps/web` static build)
- Observability: OpenTelemetry + Sentry

## Non-negotiable architecture rules

1. All game-state changes happen through validated commands (Zod) and produce domain events. No mutating game state outside this pipeline.
2. `packages/engine` must stay importable with zero Vue/browser/Nest/DB dependencies. If a change to engine code requires one of those, it belongs in `apps/web` or `apps/api` instead.
3. Content (heroes, ability cards, enemies, items, statuses, maps, scenarios) is data-driven, validated with Zod, versioned, and kept separate from runtime game state.
4. Architecture must support single-player and drop-in/drop-out co-op: joining an active scenario, transferring control of an existing hero, reconnecting, state sync, snapshots, save/load, replay.
5. Shared game state and components across desktop/tablet/mobile, with platform-specific layouts/interactions layered on top — not forked implementations.
6. E2E-тести шарові й селектор-вільні. `apps/playwright/e2e/**` викликає **тільки** Feature-класи:
   ніяких локаторів, ніякого `page`, ніякого `waitForTimeout` (це enforced ESLint-ом, не
   домовленістю). Локатори живуть виключно в `src/components/*.component.ts`. Стан гри та
   геометрію гексів тести питають у застосунку через `window.__HEXOFLAT_TEST__`
   (`apps/web/src/e2e/`, вмикається `VITE_E2E_HOOKS=true` тільки в e2e-збірці) — жодного
   дублювання логіки `packages/engine` у тестовому коді. Деталі й «чому» —
   `apps/playwright/README.md` і коментарі в `src/framework/base-component.ts`.

**Path of Will economy (branch `implement-will-chalange-to-refil-will-power-store-hero`):** Will is a hero's stock of tokens (start 20, capacity 50, `KNOWLEDGE_RULES` in `packages/engine/src/knowledge/math.ts`). A world step costs 1 via `stepCost`; camping (`willZone: 'free'` on the location definition) and combat are free, everything else is `'paid'` — one rule, `willZoneCharges`. Hex actions carry an optional content-defined `willCost` (0..5, printed on the object; the engine reads it from content, never from the command payload) and `START_HEX_ACTION` spends it atomically with the action (web wraps `applyCommand` in `transactKnowledge`; insufficient Will → `WILL_REJECTED`, state unchanged). Entering the cave costs 2, leaving is free. Will comes only from the Book of Will (code name: Knowledge Hall / `knowledge/`): an endless one-question-at-a-time practice, +1 Will per correct answer, +2 for a fast one (`KNOWLEDGE_RULES.hallFastAnswerMs`), no cap on questions until capacity is full (`grantWill`, source `hall`; `item` source is declared, not implemented). `current` changes only through `grantWill`/`spendWill`, which emit `WILL_GRANTED`/`WILL_SPENT`. **Max-health bonus rule (`HeroModel.setMaxHealthBonus`):** gear that raises the heart capacity does not heal. A full hero stays full when the maximum grows (3/3 → 4/4 with a +1 shield), a hurt hero keeps his health (2/3 → 2/4). Removing the bonus clamps health to the new maximum and remembers the missing hearts (`bonusHealthDebt`), so taking a shield off and on cannot be used to heal.

**Battle rules as they stand (Oleh, 2026-10-29 … 2026-10-31):**

- **Turn order.** Initiative is rolled once at battle start (lowest token acts first, round-1 advantage keeps the lower of two) and the same order repeats until the fight ends; there are no re-rolls. The "your turn" tag/chip follows the turn owner (the attacker during a block window), and enemy animations lock hero input (`battleStore.animating`, `enemyTurnPlaying`). The battle starts straight from ATTACK (no deploy card); `squad-flow` prepares the field and calls `battleStore.start()`.
- **Hero turn UI.** The hero card has no ACTION/MOVE bar or "defense mode" tag; the mouse wheel over the board still enters ACTION and cycles hands (internal `ui.stage`). The **Turn cost** panel shows the price of the NEXT action only (`composables/battle-next-cost.ts`: the walk path in MOVE, the tool's use price in ACTION), red when above the Will left; there is no "Moved N steps" text, no planned-cost line and no swap button (engine `swap-item` still exists). The button reads END TURN. Hex colouring in battle is gone (only the real shield sprite is drawn).
- **Enemy row (BATTLE tab, 2026-11-02).** The enemy row's hex token is the plain board sprite (`battle-hex-token.vue` with `plain`: no coloured frame, cover fit, gold glow when it is the turn owner; the hero card keeps the framed token). The six shield pips are gone; instead two hand slots show what the enemy holds (`composables/battle-row-hands.ts`: the item's own sprite, a shield/sword sprite as a placeholder for enemy-only items like the bone blade, the bare hand sprite for an empty hand; tooltip names the item). `BattleCreatureRow.shields` was replaced by `hands`.
- **Strike flow (block window, `battle/reaction.ts`).** A melee strike is picked from where the attacker stands as long as a free neighbour of the target is reachable with the Will left (`reachableRing`). `strike` opens `state.reaction` (stage `block`, 5 s): the defender is active out of turn and raises free shields anywhere on the ring (no confirm-block; `take-hit` or the 5 s `reaction-timeout` closes it), the attacker waits and only sees `shieldsRaised`. Then, in stage `aim` (5 s), an **enemy** attacker aims inside the same command; a **hero** attacker never waits (2026-11-02, Oleh: an NPC defender must not make the hero wait): `finishBlock` resolves at once from the cheapest `aimOptions` hex (his own hex when it is in the ring) and walks there paying the steps, so the stage `aim` now exists only for enemy attackers. The real shields are revealed (2.5 s on the board) and a shield on that hex blocks; no shield or a single option resolves at once. After a hero's attack from the tool hex, if no unused real weapon is left in either hand (a bare hand does not count, `weaponHandsLeft` in `composables/battle-tool-hex.ts`), the tool hex closes by itself (`use-battle-view.ts`); with two weapons it stays for the second hand. Dodge, act-phase guards and the defense-mode movement lock were removed. Enemy AI defends by guessing a ring hex (seeded, not the attacker's), and aims inside the same command (`enemyReacts`, `aimAction`).
- **Sweep.** After a melee strike the weapon hand sweeps all around: every other living enemy of the attacker's side adjacent to the attacker takes the weapon power (`STRIKE_SWEPT`, no block window), never allies or the swinger; ranged weapons do not sweep. Enemy AI therefore stays out of crowds (`isCrowdedAround`: at most 2 around one hero) unless the hero is boxed in (2 or fewer free exits); the hero's `push` opens a box.
- **Content/prices.** `usePrice` is a global content field (`loot.usePrice`, `usePriceOf(key)`); the battle catalogue takes the potion price from the health bottle (no `rules.use`); `content/use-price.test.ts` enforces it. Only the sword, shield and potion exist in battle for the hero (`BATTLE_ITEM_BY_HEXOBJECT`); other items give an empty hand, and USE on a non-battle item in a battle shows "cannot be used in a battle". Changing the weapon/shield slots in a battle sends `set-hands` (4 Will per hand, only in the hero's act turn).
- **Field.** The crypt battlefield has only floor, the border wall and 1–2 saws (ledges, rubble, oil, pillars and boulders are no longer generated; the engine still supports them). A saw hex is never a strike position: `strikeSideHexes` (free neighbours of the target minus saws, `battle-board.ts`) feeds the strike ring, the reach check, enemy AI and the decoy-shield overlay. `BattleState.wounds` (the hex each hit came from, reset every round) is engine data only and is no longer drawn: the procedural blood drops were removed. Every creature that loses health from a swing with a weapon (the target when the hit is not blocked, plus every swept bystander; never a bare hand, never a fully blocked blow) plays the blood splash atlas `public/hex-assets/hex-effects/blood-splash/` (6 frames of 264 px in one `vfx.png`, loaded as a Pixi spritesheet by `render/blood-splash.ts`, drawn by `battle-fx-layer` over the target for the last 45% of the strike; timing in `BATTLE_MOTION.splashStart/splashSizeTiles`). Every strike also floats the damage dealt (never `0`: a blocked blow shows no number). Damage that no blow caused (saw hex, fall, any other `CREATURE_DAMAGED`) plays the same splash and number: the plan turns an uncovered `CREATURE_DAMAGED` into a `shake` step with `damage` (`BATTLE_TIMING.woundMs`), so every actor of either side behaves alike from the upper-right corner of each hit hex for 2 s (`render/layers/battle-damage-layer.ts`, own ticker so it outlives the animation queue; spawned once per strike step by `BattleAnimationQueue.advance` → `frame.numbers`; `BATTLE_TIMING.damageNumberMs`, `BATTLE_MOTION.damage*`); when the target's blow is fully blocked (damage 0) the plan adds a `shake` step with style `soft` (`softShakeMs/softShakeTiles`). The sprite that swings (strike step `toolKey`) and the one in the enemy row hands both come from `battleToolKeyOf(itemKey)` (`render/battle/battle-tool-key.ts`): the item's own sprite, else sword for any enemy-only weapon and shield for an enemy shield, and the bare hand only for no item or `unarmed`. Strike animation: a bare weapon sprite goes round the owner twice in 1 s (`battle-timing.ts`).
- **Refusal order.** `validateStrike` checks the Will before reach, so a hero beside the enemy with less than the strike price (7) gets `INSUFFICIENT_WILL`, never the misleading `NOT_ADJACENT` ("Stand next to it first"); `NOT_ADJACENT` now means no ring hex is reachable with the Will left. **Balance bands are knowingly red and the two tests are `it.skip` in `balance.test.ts` (re-enable them when the shields are reworked)** (1 vs 2 warriors 93.8%, 2 vs the full squad 65.2%) since hero strikes stopped waiting in `aim`; Oleh accepted this (2026-11-02) and will rework the hero's shields later (the hero currently gets an extra shield on the wrong shield type), so do not retune HP/prices or the bands before that; e2e `aim` specs were not re-run.
- **Death.** A kill plays, in order: the strike (with the blood splash), the hit shake, then a `fall` step (`BATTLE_TIMING.deathFadeMs`, token fades in place; plan step from `CREATURE_FELL`). The dead token stays visible until its `fall` ends (`BattleAnimationFrame.dying` → `battleTokenLayer.setDying`), then the grave stays on that hex for the rest of the battle: a dead enemy leaves the skeleton grave sprite `public/hex-assets/hex-constructs/enemy-constructs/skeleton-grave-token.png` (`BATTLE_GRAVE_SPRITES` in `battle-look.ts`, preloaded via `battleAssetPaths`, fitted to `BATTLE_GRAVE_SPRITE_FIT` of the hex), a dead hero keeps the procedural RIP slab (`render/layers/battle-grave.ts`, `BATTLE_GRAVE_LOOK`). Visual only: the engine still treats the hex as free. Add a grave sprite for another side/kind by extending `BATTLE_GRAVE_SPRITES`.
- **Hero data.** The hero store is the single source of truth: the battle starts from the hero's current and maximum health and writes damage/healing back after every command (`followBattleHealth` in `squad-flow.ts`). Battle events are logged to the Events tab (`services/battle/battle-event-log.ts`).
- **Balance (tests currently `it.skip`, see above).** `battle/balance.test.ts` (500 seeds, target bands before the hero strike change): 1 hero vs 2 warriors 60–85% (lowered from 70 when the sweep arrived), 2 heroes vs the full crypt squad 40–60%; warriors have 5 hp, the skeleton king 13 hp.
- **Deadline and hand-off.** The engine refuses shields and aim after the 5 s (`WINDOW_CLOSED`); the cave exit is built into the outer wall of the entry room (border, never the middle). The one-page current state with the code map, tests and open items is [`docs/battle-system/BATTLE-HANDOFF.md`](./docs/battle-system/BATTLE-HANDOFF.md) — read it first in a fresh battle chat.
- **Rendering guards.** The battle board preloads every sprite before its first frame (`preloadTextures(battleAssetPaths(biome))` in `use-battle-board.ts`; add new battle sprites to `battleAssetPaths`). The right hero-board panel and the map pane have hard width bounds (`minmax(0, …)` tracks, `contain: inline-size`, explicit `minmax(0, 1fr)` column in `.hero-board-body`) so long text is clipped instead of stretching the layout; the Battle tab is plain text and tab fonts scale with the panel width (see `hexoflat-web-state`, Layout width guards).
- **Fog.** One reveal rule for every board (the hero hex and six neighbours, `fog-service.ts`; `BY_REGION` is gone); dungeons cover hidden hexes with `fog-hex.png`, the world with `cloud-hex.png` (`fogLookForBoardKind`).

## Workflow rules

- Always ask before `git commit` — not just before `git push`.
- **After every finished feature, update the project skills** (`.claude/skills/*/SKILL.md`) and this file with what the feature taught: new commands/hooks/files, new gotchas, changed rules, new plan docs. A feature is not done until the skills describe the code as it now is (stale skills mislead the next chat).
- E2E is grouped by feature (`apps/playwright/e2e/<group>/`, tags `@auth @board @camp @combat @hero @shell`, `@smoke` on single tests). `apps/playwright/impact-map.ts` + `scripts/select-e2e*.ts` pick the groups a diff affects: pre-push runs only those (`E2E_ALL=1` / `E2E_SKIP=1` override), the gating PR does the same in the `e2e-plan` job, pushes to `main` and nightly run everything. Plan: `docs/e2e/e2e-impact-selection-plan.md`; new feature folders must be added to a group's `roots`, `pnpm run e2e:map:check` guards the tags.
- CI (`.github/workflows/ci.yml`) runs lint + typecheck + test + build (parallel), then e2e (gated behind all of those passing), then deploys `apps/web` + the Allure report to GitHub Pages — one sequential pipeline, on every PR (any target branch) and on push to `main`/`game-dev-vite`. It used to be two separate workflows that each ran their own e2e job; merged 2026-08-12 because that duplicated the most expensive job and caused runner queueing on every PR.

**Hero stash (branch `hero-stash-implementation`):** spec and progress in [`docs/stash/stash-board-spec-doc-ref.md`](./docs/stash/stash-board-spec-doc-ref.md) (read the Oleh decisions block: only the spec's schema and rules apply, its visuals do not). Rules are pure engine functions in `packages/engine/src/inventory/` (`planItemMove`, `planItemAutoPlace`, `planStoreResources`, `planSortStash`, `carriedWeightKg`, stash 64 cells x 8 columns, stash weighs nothing); web keeps `hero-stash-store`, `stash-storage` (localStorage `hexoflat.hero.stash.v1`) and the adapter/orchestrator in `services/inventory/` (`stash-transfer.ts`). S1 (engine), S2 (state), S3 (layout, later redesigned: 7-column grids with the Inventory cell size via `use-inventory-cell-size.ts`, five chests of 6x7 cells as tabs, unlocked in order for 100 then 1000 coins paid with the Unlock action while holding coins in a hand (coins are a hand tool like the scroll; only the price is taken from the stack), no divider and no equipment row; `a-game-scenes/map-scene/components/stash/`, shown by `hero-board-panel.vue` while `heroStash.isOpen`, closed by `use-stash-session.ts`) and S4 (interaction: its own pointer drag in `composables/use-stash-drag.ts`, deliberately separate from `use-inventory-drag.ts`; double-click / right-click / Enter send an item across) are done; S5 (filters that only dim, Store resources and Sort buttons in the STASH header, "N more below" in the bag) is done; S6 (e2e: `apps/playwright/e2e/hero/stash.spec.ts` through `StashBoardFeature` / `UnlockStashChestFeature`, written but not yet run) is done.
