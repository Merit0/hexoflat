# Частина А. Дошка квестів — загальна модель (рішення Олега 12.11.2026)

Дошка квестів — не «екран Шукача скарбів», а **система**: через неї герой вчиться й здобуває будь-який контент гри, а творець додає квест рядком даних. «Шукач скарбів» (Частина Б) — один із видів квесту на цій дошці.

## А1. Принцип

Квест складається з трьох частин, і кожна — дані:

| Частина      | Питання                      | Модель                                     |
| ------------ | ---------------------------- | ------------------------------------------ |
| **Взяти**    | хто і за скільки може взяти  | `requires: Requirement[]`, `accept: Cost`  |
| **Зробити**  | що рахується і скільки треба | `objective: Objective`                     |
| **Отримати** | що дає                       | `rewards: Reward[]` — будь-який об'єкт гри |

Ціль не знає про дерева, сокири чи скелетів. Вона **слухає доменні події** гри (`TREE_CHOPPED`, `ENEMY_DEFEATED`, `TASK_RESOLVED`…) і рахує. Тому новий квест «зрубай 10 дерев» чи «переможи 3 лучників» — це рядок контенту без жодного коду, а новий _вид_ цілі — один запис у реєстрі.

## А2. Модель

```ts
interface QuestDefinition {
  id: QuestId;
  nameKey: I18nKey; descKey: I18nKey;
  repeat: 'once' | 'repeatable';     // once — одноразовий (унікальний): після нагороди зникає назавжди
                                     // repeatable — після нагороди знову висить на дошці
  requires: Requirement[];           // коли картка відкрита; новий варіант { kind: 'questDone', questId }
  accept: Cost;                      // ціна взяття (free | will | item)
  objective: Objective;
  rewards: Reward[];                 // { kind:'item', itemKey, amount } | { kind:'will' } | { kind:'loot', tableId }
  turnIn: 'board' | 'auto';          // нагороду видає дошка (CLAIM) чи сам фінал квесту
  maxSellValue?: number;             // межа для тесту економіки повторюваних квестів
  tableRule: I18nKey;
}

type Objective =
  | { kind: 'count'; event: DomainEventType; where?: Record<string, string | number>; target: number; unitKey: I18nKey }
  | { kind: 'expedition'; expedition: 'treasureSeeker'; params: TreasureSeekerParams };
// на потім, по одному запису в реєстрі: 'deliver' (принести предмети), 'reach' (дійти до місця), 'all' (кілька цілей разом)

interface QuestLog {                 // частина агрегату progress героя
  active: { questId: QuestId; progress: number; state: 'active' | 'ready' }[];
  done: Record<QuestId, number>;     // скільки разів завершено
}

// реєстр видів цілі — єдине місце з кодом на вид
OBJECTIVES[kind] = { onEvent(entry, event): number /* новий progress */, isComplete(entry), describe(def) /* текст картки */ }
```

Приклад Олега цілком у даних:

```ts
{ id: 'woodcutter', repeat: 'repeatable', requires: [], accept: { kind: 'free' },
  objective: { kind: 'count', event: 'TREE_CHOPPED', target: 10, unitKey: 'quest.unit.trees' },
  rewards: [{ kind: 'item', itemKey: 'axe', amount: 5 }], turnIn: 'board', tableRule: 'quest.woodcutter.table' }
```

## А3. Правила

- **R-Q-1. Дошка.** Показує всі квести. Вимоги не виконано — картка замкнена з однією причиною. Одноразовий завершений — більше не показується.
- **R-Q-2. ACCEPT.** `QUEST_ACCEPT { questId }` проходить `checkAction`: `activity = camp`, вимоги, вільний слот, Воля ≥ ціна взяття + доплата за слот. Відмови: `REQUIREMENTS_NOT_MET`, `QUEST_SLOTS_FULL`, `QUEST_ALREADY_ACTIVE`, `INSUFFICIENT_WILL {cost, have}`.
- **R-Q-3. Слоти.** Контент: `questSlots { base: 1, max: 3, extraCost: [5, 10] }`. Перший квест — за свою ціну; другий одночасний — +5 Волі, третій — +10. Так усі квести одразу не взяти, але два-три «по дорозі» — можна, якщо гравець порахував, що це вигідно. **Точка розширення:** ефект навички `{ kind: 'questSlots', free: n }` робить `n` додаткових слотів безплатними (дерево навичок цим планом не змінюється).
- **R-Q-4. Прогрес.** Рахує сервер у тій самій команді, що породила подію; лише для активних квестів; `where` фільтрує поля події. Події до взяття квесту не рахуються.
- **R-Q-5. Ціль досягнуто.** `state = 'ready'`, подія `QUEST_READY`. Далі прогрес не росте.
- **R-Q-6. CLAIM.** `QUEST_CLAIM { questId }` біля дошки: нагороди видає спільна `grant(hero, reward)`. Немає місця в сумці → `BAG_FULL`, квест лишається `ready`. Для `turnIn: 'auto'` нагорода видається у фіналі квесту (у «Шукача» нагорода — сама скриня).
- **R-Q-7. ABANDON.** Безплатно, з будь-якого місця. Ціна взяття не повертається, прогрес губиться, слот вільний.
- **R-Q-8. Повторюваність.** `once`: після нагороди `done[id] = 1`, картки більше немає. `repeatable`: картка одразу знову на дошці, прогрес з нуля.
- **R-Q-9. Ліворуч завжди мапа; увесь вміст квестів — у правій панелі** (рішення Олега 12.11). На мапі з квесту є лише те, що є частиною світу: об'єкт дошки, числа на гексах, скриня, здобич. Узятий квест видно завжди:
  1. у правій панелі, блок **MY QUESTS** (у кемпі — над дошкою; поза кемпом — вкладка QUESTS): назва, лічильник `3 / 10`, смужка, нагорода, CLAIM / ENTER, зняти квест; лічильник оновлюється одразу з подією;
  2. на дошці (та сама права панель) — картка з позначкою «взято»;
  3. `ready` — золота позначка на вкладці QUESTS і на об'єкті дошки в кемпі.
     Картки дошки, перебіг «Шукача» (кроки, слід, статус), повідомлення про засідку й картка результату — теж лише в правій панелі; на мапу нічого не накладається.
     За столом: картку знімають з дошки й кладуть біля планшета героя; прогрес — жетони на картці.
- **R-Q-10. Квест-експедиція** (`objective.kind = 'expedition'`): ACCEPT платить вхід і займає слот; дія **ENTER** біля дошки (безплатна) відкриває мапу квесту. Будь-який фінал звільняє слот. Успіх збільшує `done`; невдача — ні, і квест треба брати знову.
- **R-Q-11. Сервер.** `QuestLog` зберігається в `progress`. Усі команди ідемпотентні за `commandId`. Перезавантаження нічого не губить.
- **R-Q-12. Економіка.** Для кожного `repeatable` з нагородою-предметом: сума цін продажу нагороди ≤ `maxSellValue` квесту (контент, задає Олег). Тест не дає випадково зробити «фабрику монет».
- **R-Q-13. Навчання.** Ціль `count` по `TASK_RESOLVED { correct: true }` робить навчальні квести («розв'яжи 15 задач») тим самим механізмом; пізніше `where: { topic }` дасть квести за темами.

# Частина Б. «Шукач скарбів» — квест-експедиція

Усе нижче описує один вид квесту. Де Частина Б говорить «START» — це **ACCEPT (платить вхід) + ENTER** з R-Q-10; «віха `seeker-N-clean`» — це `done['seeker-N'] ≥ 1`; картка — це `QuestDefinition` з `objective.kind = 'expedition'`. Якщо Частини розходяться, діє Частина А.

## 2. Квест за 12 правил

1. У кемпі стоїть **Дошка квестів**. На ній три картки «Шукача скарбів». Картка показує **вхід, кількість кроків, ціну кроку, ціну кроку назад**. Суму гравець рахує сам.
2. **START** списує вхід і відкриває **нову мапу в тумані**. Герой стоїть біля воріт.
3. Коли герой стає на гекс, відкриваються його сусіди. На кожному відкритому гексі — **число**.
4. Від воріт до скрині веде прихований **слід**: числа за правилом картки (1, 2, 3… / 5, 10, 15… / 3, 6, 12…).
5. Серед сусідів рівно **один** гекс має наступне число. Решта — **пастки**: типові помилки (на 1 більше, пропущений крок, інша дія).
6. **Перші H кроків** правильний гекс світиться золотом — так гра показує правило. Далі герой обирає сам.
7. **Крок уперед** коштує `stepCost`. **Крок назад** (на попередній гекс свого шляху) — **утричі дорожче**.
8. Пройдений шлях лишається відкритим, з числами й лінією — його можна перевірити будь-коли.
9. **Помилку гра не показує.** Після неправильного гекса числа йдуть **за тим самим правилом від неправильного числа** — фальшивий слід.
10. На останньому кроці поруч з'являється **скриня**. Після фальшивого сліду вона виглядає так само.
11. **OPEN** (рука з кільця інструментів): справжня скриня — здобич розлітається на сусідні гекси; фальшива — **засідка**, нерівний бій. Перед OPEN ще можна відступити й виправити слід.
12. **Воля скінчилась** до скрині — квест провалено, герой у кемпі. **GIVE UP** — безплатний вихід у будь-який момент. Вхід не повертається.

## 4. Правила детально (контракти)

### 4.1 Картки «Шукача» на дошці

- **R-QB-1.** Дошка — об'єкт мапи кемпу зі здатністю `questBoard`. Відкривається **так само, як торговець чи Книга Волі** (Q0 з'ясовує спосіб). Наведення показує картку об'єкта з одним реченням без чисел.
- **R-QB-2.** Картка «Шукача» — `QuestDefinition` (Частина А) з `accept` = вхід, `turnIn: 'auto'`, `objective: { kind: 'expedition', expedition: 'treasureSeeker', params }`, де `TreasureSeekerParams { steps: L, stepCost, backMultiplier, rulePool, hintSteps, chestLootTableId, ambushTable }`.
- **R-QB-3.** Картка показує: назву, одне речення опису, `Entry N Will · L steps · step N · back N`, нагороду словом («chest»). **Суми немає ніде в UI** — ні на картці, ні в підказці, ні в банері.
- **R-QB-4.** Картка II має `requires: [{ kind: 'questDone', questId: 'seeker-1' }]`, III — `seeker-2`. «Завершено» для «Шукача» = відкрито справжню скриню; перемога в засідці не рахується.
- **R-QB-5.** ACCEPT — за R-Q-2 (вхід + доплата за слот). **Достатність Волі на кроки не перевіряється і не підказується.**
- **R-QB-6.** `QUEST_ENTER { questId }` біля дошки, безплатно: створено експедицію `kind: 'quest'`, `activity = expedition`, герой біля воріт мапи квесту. Інші активні квести лишаються активними й рахуються далі.

### 4.2 Правила послідовностей

- **R-SEQ-1.** Правило = `{ kind, params }` → `term(i)`. Види для релізу:

| `kind`        | Параметри                               | Приклад                  | Продовження від неправильного числа `w` |
| ------------- | --------------------------------------- | ------------------------ | --------------------------------------- |
| `arith`       | `start, step` (step ≠ 0, може бути < 0) | 5, 10, 15… / 50, 47, 44… | `w + step`                              |
| `geom`        | `start, ratio` (2)                      | 3, 6, 12, 24…            | `w × ratio`                             |
| `alternating` | `start, steps[2]`                       | 1, 3, 6, 8, 11… (+2, +3) | той самий наступний крок                |
| `growingStep` | `start, step0, inc`                     | 1, 2, 4, 7, 11…          | той самий наступний крок                |

- **R-SEQ-2.** Параметри випадкові в межах пулу картки (§5.1), з потоку `quest:<id>:rule`.
- **R-SEQ-3.** Усі члени — цілі, > 0, не більше 3 цифр. Інакше — інші параметри.
- **R-SEQ-4.** `continueFrom(rule, k, w)` дає члени фальшивого сліду після відхилення на кроці `k` з числом `w` (остання колонка таблиці). Людина, яка помилилась раз і далі рахує правильно, бачить слід, що «сходиться».
- **R-SEQ-5.** Новий вид правила = один запис у реєстрі `RULES` (term + continueFrom + шаблони пасток). Код квесту не змінюється.

### 4.3 Однозначність і пастки

- **R-AMB-1.** Після `hintSteps` підсвічених членів наступний член має бути **однозначним**: жодне правило з **каталогу альтернатив** (усі види §4.2 і Додатка Б з малим перебором параметрів) не збігається з цим префіксом, даючи інший наступний член. Якщо збігається — `hintSteps` +1 (не більше `L − 2`) або інші параметри.
- **R-AMB-2.** Пастки беруться з шаблонів помилок: наступний ± 1; наступний ± 10; пропущений член; інша дія (`+step+1`, додав замість помножив, подвоїв замість додав); повтор поточного числа. На одному кільці всі числа різні, > 0, ≠ правильному.
- **R-AMB-3.** Пастка не може дорівнювати наступному члену жодного правила з каталогу, яке збігається з **видимим шляхом героя**.
- **R-AMB-4.** Щонайменше дві пастки на кільці — «близькі» (± 1 або пропущений член), якщо на кільці є місце.
- **R-AMB-5.** Враховуються вже відкриті сусіди: число гекса `h` не може бути наступним членом після числа будь-якого відкритого сусіда `h`, і навпаки; на істинному сліді `h` не може дорівнювати члену, якого герой чекатиме, стоячи на гексі сліду поруч із `h`. Інакше на наступному кроці «правильних» гексів стане два.
- **R-AMB-6.** Члени фальшивого сліду теж мають бути > 0; пастка, продовження якої виходить за межі, не ставиться.

### 4.4 Мапа і слід

- **R-MAP-1.** Мапа генерується наявним генератором з новим пресетом `treasure-field`: усе в тумані, природний край, ворота біля краю, без ворогів, без об'єктів на прохідних гексах; розмір ≤ 18×17.
- **R-MAP-2. Слід:** `L` гексів від сусіда стартового гекса. Кожен гекс сліду межує лише з попереднім і наступним гексом сліду та не межує зі стартовим гексом (крім першого).
- **R-MAP-3. Гекс скрині `C`:** сусід лише останнього гекса сліду; **усі шість його сусідів — гекси поля** (QC2a, 2026-11-14: замінило «≥ 3 прохідні сусіди»), тому поза останнім гексом сліду рівно 5 вільних місць для здобичі. Гекс скрині не лежить на зовнішньому кільці й не на кільці 5 поруч із прогалиною краю.
- **R-MAP-4.** Біля кожного гекса сліду ≥ 2 прохідні гекси поза слідом (місце для пасток і фальшивих продовжень).
- **R-MAP-5.** Сід — прихований, на сервері. Перезавантаження дає ту саму мапу й ті самі числа. Наступний START — нова мапа.

### 4.5 Відкриття і числа

- **R-REV-1.** Коли герой стає на гекс, відкриваються всі його закриті сусіди. Для кожного запам'ятовується `revealedBy` — гекс, з якого його відкрито.
- **R-REV-2.** Число гекса — **чиста функція** (сід, шлях героя до гекса-відкривача, гекс). Повторне відкриття з того самого шляху дає те саме число.
- **R-REV-3.** Розподіл на кільці:
  - герой на **істинному сліді** (відхилень 0): наступний гекс сліду отримує `term[k+1]`, решта — пастки;
  - герой на **фальшивому сліді**: один зі щойно відкритих гексів, що **не належить істинному сліду**, отримує наступний фальшивий член; решта — пастки;
  - `C` і гекси істинного сліду, відкриті не з істинного сліду, отримують пастки, як звичайні гекси.
- **R-REV-4.** Якщо на фальшивому сліді немає вільного гекса для продовження — фальшива скриня з'являється вже на цьому кроці (R-END-2).
- **R-REV-5.** Сервер надсилає клієнту лише числа **відкритих** гексів.

### 4.6 Кроки, підказка, Воля

- **R-STEP-1.** `QUEST_STEP { hex }` — на відкритий прохідний сусідній гекс, крім попереднього гекса шляху (туди — `QUEST_STEP_BACK`). Ціна `stepCost` із загальної Волі героя.
- **R-STEP-2.** Крок додає `{hex, number}` у `path`. Клієнт малює шлях лінією й рядком чисел.
- **R-HINT-1.** Поки `path.length < hintSteps` і відхилень не було жодного разу — проєкція містить `hintHex`. Після першого відхилення чи кроку назад підказки немає до кінця квесту.
- **R-WILL-1.** Гра ніде не каже, чи вистачить Волі до кінця. Відмова лише на конкретний крок: `INSUFFICIENT_WILL {cost, have}`.
- **R-WILL-2.** «Друге дихання» (етап 4 дорожньої карти) **у квесті не діє**: бюджет Волі — частина задачі. _(Рішення за замовчуванням, питання 1 у §12.)_

### 4.7 Відхилення і фальшивий слід

- **R-FALSE-1.** Відхилення = крок на гекс, число якого ≠ наступний член поточного сліду. `deviations` +1; поточним стає `continueFrom` від цього числа; довжина фальшивого сліду закінчується на тому ж кроці `L`.
- **R-FALSE-2.** Нове відхилення на фальшивому сліді — новий фальшивий слід від нового числа, `deviations` +1.
- **R-FALSE-3.** Жодна подія, проєкція, колір чи звук не відрізняє гекс відхилення від правильного.

### 4.8 Крок назад

- **R-BACK-1.** `QUEST_STEP_BACK` — на попередній гекс шляху. Ціна `stepCost × backMultiplier`. Можна повторювати до стартового гекса.
- **R-BACK-2.** Гекс, з якого відступили, прибирається зі шляху й лишається відкритим із числом та позначкою «тут уже був» (сліди). Стати на нього знову можна (це звичайний крок).
- **R-BACK-3.** Гекси, які відкрив **лише** покинутий гекс (`revealedBy`), знову закриває туман. Скриня, що з'явилась біля покинутого гекса, зникає.
- **R-BACK-4.** Якщо прибрано гекс відхилення — `deviations` −1, поточним стає слід до цього відхилення.

### 4.9 Фінал

- **R-END-1. Справжня скриня.** Герой стає на `L`-й гекс істинного сліду з `deviations = 0` → на `C` з'являється скриня (`CHEST_APPEARED`).
- **R-END-2. Фальшива скриня.** Герой стає на `L`-й гекс фальшивого сліду → скриня з'являється на вільному сусідньому гексі. Клієнт отримує ту саму подію `CHEST_APPEARED` без жодної різниці.
- **R-END-3. OPEN.** Рука з кільця інструментів → OPEN на сусідню скриню, безплатно. Сервер вирішує:
  - справжня → правило `loot-plan.md` §1.1: герой переходить на гекс скрині, здобич з `chestLootTableId` розлітається на вільні сусідні гекси, скриня порожня; `phase = 'collect'`; віха `seeker-N-clean`;
  - фальшива → `AMBUSH_SPRUNG { deviations }` → бій на окремій мапі бою з перевагою засідки; склад загону з `ambushTable` за кількістю відхилень (§5.3).
- **R-END-4. Фаза збирання.** Числа гаснуть, кроки безплатні, герой підбирає здобич. Дія **RETURN TO CAMP** (безплатна) завершує квест: `QUEST_COMPLETED { outcome: 'treasure' }`. Незібране пропадає; перше в житті героя таке покидання — одноразове попередження (як у `loot-plan.md` §1.3).
- **R-END-5. Перемога в засідці** → фаза збирання на полі бою (могили, `loot-plan.md` §1.3) → вихід з поля бою → `QUEST_COMPLETED { outcome: 'ambushWon' }` → кемп. Віхи `clean` немає.
- **R-END-6. Поразка в засідці** → наявне правило поразки (кемп; втрати — за чинною `SetbackPolicy`) → `QUEST_FAILED { reason: 'DEFEAT' }`.
- **R-END-7. Застряг.** Після кроку: Воля < `stepCost`, скрині поруч немає → `QUEST_FAILED { reason: 'STRANDED' }` → кемп. Гравець бачить картку результату з одним реченням причини.
- **R-END-8. GIVE UP** — безплатна дія під час ходьби → `QUEST_FAILED { reason: 'LEFT' }` → кемп.
- **R-END-9.** Після завершення мапа квесту видаляється. Вхід не повертається в жодному випадку.
- **R-END-10. Розбір після кінця.** Картка результату показує пройдені числа; якщо було відхилення, перше з них позначене й підписане одним реченням («The trail left the rule at 6. The rule said 5.»). Сервер віддає це лише в події завершення.

### 4.10 Сервер і збереження

- **R-SRV-1.** Усі команди квесту виконує сервер через engine; повтор з тим самим `commandId` повертає той самий результат.
- **R-SRV-2.** Проєкція клієнта містить: картку, `path`, відкриті гекси з числами, `hintHex` (якщо діє), позицію, фазу, скриню як об'єкт без поля `kind`. **Не містить:** сід, `trail`, правило, фальшивий слід, `deviations`, числа закритих гексів.
- **R-SRV-3.** Перезавантаження сторінки на будь-якому кроці повертає гравця в той самий стан квесту (через `activity`).
- **R-SRV-4.** Потоки RNG: `quest:<id>:rule`, `quest:<id>:trail`, `quest:<id>:numbers`. Той самий сід + команди → ті самі події.
- **R-SRV-5.** Наприкінці квесту сервер пише одну подію для майбутньої майстерності: `QUEST_SUMMARY { offerId, selfSteps, deviationsTotal, outcome }`. Читачів поки немає.

### 4.11 Фізична версія (`tableRule`)

Тайли лежать сорочкою догори. Наглядач має картку сліду (гекси й правило). Герой став на тайл — Наглядач відкриває сусідні й кладе картки чисел: наступний член і пастки з картки рівня. Перші H кроків на правильний тайл кладеться золотий жетон. Крок назад — три поділки на трекері Волі; тайли, відкриті лише покинутим тайлом, перевертаються назад, на покинутий кладеться жетон слідів. Наприкінці Наглядач ставить скриню; на OPEN перевертає її: скарб або жетони загону.

### 5.1 Картки релізу

| Картка                                 | `id`       | Пул правил                                                                                                | `L` | Крок | Назад | H   | Вхід | Вимога           | Чисто | З одним виправленням |
| -------------------------------------- | ---------- | --------------------------------------------------------------------------------------------------------- | --- | ---- | ----- | --- | ---- | ---------------- | ----- | -------------------- |
| **I. First Trail** / Перший слід       | `seeker-1` | `arith` start 1, step 1                                                                                   | 10  | 1    | 3     | 4   | 20   | —                | 30    | 34                   |

## 6. UI (чинний дизайн гри — правило)

Токени, шрифти, вкладки — з наявного коду (`hero-board-panel.vue`, дошка магазину). Підписи англійською й українською через i18n. Правило Олега: **наведення показує інформацію, дії лише запускають події.**

### 6.1 Дошка квестів (права панель)

У кемпі права панель показує згори MY QUESTS, під ним — картки дошки списком з прокруткою. Схема картки «Шукача»:

```
┌──────────────────────── QUEST BOARD ─────────────────────────┐
│ Will 46 / 50                                                 │
│ ┌──────────────────────────────────────────────────────────┐ │
│ │ I · FIRST TRAIL                                          │ │
│ │ Follow the numbers through the fog to the chest.         │ │
│ │ ⬡ Entry 20   ⬡ 10 steps   ⬡ Step 1   ⬡ Step back 3       │ │
│ │ Reward: chest                              [  START  ]   │ │
│ └──────────────────────────────────────────────────────────┘ │
│ ┌ II · LEAPING TRAIL ──── 🔒 Find the chest of the First Trail ┐│
│ ┌ III · CUNNING TRAIL ─── 🔒 Find the chest of the Leaping Trail┐│
│ How it works: the first steps glow gold. After that you      │
│ choose alone. The fog never tells you if you were wrong.     │
└──────────────────────────────────────────────────────────────┘
```

START неактивна лише коли Волі менше за вхід (причина під кнопкою). Суми немає.

### 6.2 Мапа квесту

- Відкритий гекс: число в центрі, великим (читається на телефоні, до 3 цифр).
- Підказка: золоте світіння одного гекса в перші H кроків.
- Досяжні гекси: синя рамка й ціна (`1`); попередній гекс шляху: `↩ 3`.
- Шлях: тонка золота лінія через пройдені гекси. Гекс відхилення нічим не відрізняється.
- «Тут уже був»: бліді сліди на гексі, з якого відступили.
- Скриня: об'єкт на гексі; справжня й фальшива однакові. Наведення: «A chest. Open it with your hand.»
- Банера квесту на мапі немає: назва, `Step 6 / 10` і ціни — у правій панелі.
- Фаза збирання: числа гаснуть, здобич на гексах, кнопка RETURN TO CAMP.
- Засідка: скриня розчиняється, жетони загону виринають з туману (≤ 600 мс); повідомлення про засідку — у правій панелі → наявна картка розстановки бою.

### 6.3 Панель під час квесту

Картка квесту (ті самі чотири числа) · рядок `Your trail: 1 · 2 · 3 · 4 · 5` · кнопка GIVE UP (з підтвердженням) · після завершення — картка результату (Treasure / Ambush won / Stranded / Left) з одним реченням.

### 6.4 Телефон і планшет

Крок і крок назад — дотик по гексу. OPEN — наявним способом кільця інструментів для дотику; якщо на момент Q4 його ще немає (етап 5), тимчасово: дотик по сусідній скрині з порожньою рукою відкриває кільце. Q0 фіксує, що є.

### 6.5 data-testid

`quest-board`, `quest-run-card`, `quest-trail-row`, `quest-give-up`, `quest-return-to-camp`, `quest-result`. Гекси й скриня — через наявний тест-хук дошки (`window.__HEXOFLAT_TEST__`), без селекторів канваса.

## 7. Архітектура

### 7.1 Engine — `packages/engine/src/quests/`

```
quests/
  seeker-content.ts     Zod: TreasureSeekerParams, пули правил, ambushTable (картки — у quests.content.ts Частини А)
  quest-state.ts        Zod: QuestRun (у стані експедиції, адитивно)
  sequences/
    rules.ts            реєстр RULES: term, continueFrom, шаблони пасток
    alternatives.ts     каталог альтернатив + isUnambiguous
    decoys.ts           вибір пасток (R-AMB)
  trail.ts              слід і гекс скрині на дошці (R-MAP)
  numbers.ts            числа при відкритті, revealedBy, повернення туману
  seeker-actions.ts     QUEST_ENTER, QUEST_STEP, QUEST_STEP_BACK, QUEST_OPEN_CHEST, QUEST_RETURN, QUEST_GIVE_UP
  projection.ts         projectQuestForClient (R-SRV-2)
```

`QuestRun`: `offerId, rule, trail[], chestHex, path[], current: 'true' | { fromStep, values[] }, deviations, everDeviated, revealed{hex → {number, revealedBy}}, visited[], chest?: { hex, kind: 'real' | 'lure' }, phase: 'walking' | 'collect' | 'ambush' | 'ended', outcome?`.

Відмови (у спільному переліку `RefusalCode`): `INSUFFICIENT_WILL`, `REQUIREMENTS_NOT_MET`, `QUEST_IN_PROGRESS`, `NOT_ADJACENT`, `HEX_NOT_REVEALED`, `HEX_BLOCKED`, `NOTHING_TO_STEP_BACK`, `NO_CHEST`, `WRONG_PHASE`, `NO_ROOM_FOR_LOOT`.

Події: `QUEST_STARTED`, `QUEST_HEXES_REVEALED`, `QUEST_HEXES_FOGGED`, `QUEST_STEPPED`, `QUEST_STEPPED_BACK`, `CHEST_APPEARED`, `CHEST_VANISHED`, здобич — події з `loot-plan`, `AMBUSH_SPRUNG`, `QUEST_COMPLETED`, `QUEST_FAILED`, `QUEST_SUMMARY`.

Кожна команда оголошує дозволену `activity`: ACCEPT і ENTER — `camp`; решта — `expedition(kind: quest)`.

### 7.2 API

Команди квесту — тим самим шляхом, що `WORLD_STEP` / `START_HEX_ACTION` (Q0 називає точні місця). Стан квесту — частина серверного документа експедиції. Віхи `seeker-N-clean` — в агрегаті `progress`.

### 7.3 Web

`stores/quest-store.ts` (команди, проєкція, черга подій — без правил) · `composables/use-quest-view.ts` · компоненти `quest-board-panel.vue`, `quest-offer-card.vue`, `quest-run-card.vue`, `quest-result-card.vue` · рендер `render/layers/quest-numbers-layer.ts` (числа, підказка, лінія шляху, сліди, ціни кроків).

## Додаток Б. Драбина після релізу (лише нові рядки в реєстрі правил і нові картки)

| Картка | Вид                       | Приклад                     | Для кого |
| ------ | ------------------------- | --------------------------- | -------- |
| IV     | `interleave` двох `arith` | 1, 10, 2, 20, 3, 30…        | клас 4   |
| V      | `squares` / `triangular`  | 1, 4, 9, 16… / 1, 3, 6, 10… | клас 5   |
| VI     | `centeredHex`             | 1, 7, 19, 37, 61…           | клас 5   |
| VII    | `fibonacci`               | 1, 1, 2, 3, 5, 8…           | клас 5–6 |
| VIII   | `affine`                  | 1, 3, 7, 15… (×2+1)         | клас 6   |
| IX     | `primes`                  | 2, 3, 5, 7, 11…             | клас 6+  |
| X      | `polynomial`              | 2, 5, 10, 17… (n²+1)        | дорослі  |

Правила за індексом (`squares`, `primes`…) продовжуються від неправильного числа зсувом решти на різницю.
