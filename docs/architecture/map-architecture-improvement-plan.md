# Map architecture: fixes, optimizations and improvements

Source: read-only audit of the map architecture (2026-11-16, branch `codex/map-object-transitions`). The verdict was **implemented, with targeted defects**: exactly one gameplay board is mounted (`gameplay-board-host.vue`), domain states (world documents, quest run, battle) live on the server and in module-level projections, nothing is saved on unmount, and projections hide the seed and the trail. Keep the design; do not introduce a single persistent Pixi application (recreating a board has shown no measurable cost).

## Next phases (one chat each, in this order)

### M1. A background world tick never announces presence (correctness, small) [DONE — 2026-11-16]

- **Trigger.** Every quest exit (PAUSE, RETURN, GIVE_UP) sets server presence to `camping` (`quest-run.service.ts` `campPlace`), but `world-map-store` still holds the Silesia map. The host mounts the world board and starts the loop at once; `leaveQuestField` waits for `GET /player/world`. A tick 250 ms later with `hasDueWork` (likely: respawns piled up while the loop was stopped) calls `ensurePresence(Silesia)` → `WORLD_ENTER silesia`.
- **Consequence.** On slow networks the server hero goes back to Silesia, and `refetchServedWorld('camping')` can cache the Silesia document under the `camping` key.
- **Fix.** `serverTickAction` skips the tick when `inventorySession.presence` is set and differs from `{currentLocationKey, currentMapId}`; ticks never call `ensurePresence` for a place the hero has not chosen.
- **Tests.** Unit test in `stores/world-map-server.test.ts` with the fake player server: presence = camp, store on Silesia, due spawner → no `WORLD_ENTER` is sent.
- **Result (2026-11-16, branch `map-architecture-improvements`).** `serverTickAction` (`stores/server-world-actions.ts`) returns before `ensurePresence` while `inventorySession.presence` names another location or map; with no presence (fresh session) or the same place it ticks as before. Hex actions, steps and travel still announce presence themselves, so a started action always ticks. Tests: `world-map-server.test.ts` "keeps a background tick quiet …" (red before the fix: `['WORLD_ENTER', 'WORLD_TICK']`) and "ticks again once the shown world …". Web 3365/3365, typecheck, lint; e2e `gather-resource`, `return-portal`, `quest-world-entry` 7/7 without retries.

### M2. `WORLD_ENTER` is validated by the server; the client starts from server presence (authority) [DONE — 2026-11-16]

- **Trigger.** `world.service.ts` moves presence to any `locationKey` without a sealing check, entry price or trip count. The client picks the location from the URL prop and its own `nav` blob (`hex-world-map.vue` watch, `bootstrapWorld`, `heroStore.setLocation`). Opening `/world/cave` loads the cave from the cache and the first action enters it.
- **Consequence.** `WORLD_TRAVEL` rules (2 Will, `trips` that reset the trader refresh price, `sealedUntil`) can be skipped.
- **Fix.** Server: `WORLD_ENTER` is allowed only while presence is `null` or names the same location; otherwise `rejected` with a new code. Client: `bootstrapWorld` and the route prop use `inventorySession.presence.locationKey`; a URL for another location is replaced by the presence route.
- **Cost.** API tests that use `WORLD_ENTER` as a fixture (`world.integration.spec.ts`, `battle-collect.integration.spec.ts`, `quest-run.integration.spec.ts`) move to `WORLD_TRAVEL` or a dev fixture. Check every flow that leaves presence `null` (new hero, quest ENTER) before closing it.
- **Tests.** API: entering another location while present elsewhere is refused and nothing is charged. E2E: a deep link to another location shows the presence location.
- **Result (2026-11-16, Oleh: silent redirect + server refusal).** Engine `world/enter-rule.ts` (`enterRefusal`, `HERO_ELSEWHERE`): `WORLD_ENTER` is refused while presence names another location, nothing is charged; `WorldService` places the hero through `placeHeroIn`. Dev fixture `POST /player/dev/relocate-fixture` (`relocateFixtureSchema`, fixtures flag only) moves the hero for e2e; the hook `prepareKnowledgeWorld(current, locationKey = 'silesia')` is now async and uses it. Web: `services/world/presence-location.ts` (`heldLocationKey`, `onHeroElsewhere`, `reportHeroElsewhere`), `composables/use-presence-route.ts` replaces the `hex-world-map.vue` route watch (a URL for another location is `router.replace`d to the held one, `replaceLocationRoute`), `bootstrapWorld` starts from presence, `ensurePresence` reports a `HERO_ELSEWHERE` refusal so the route returns to the held place. The fake player server mirrors the rule (battle fixtures moved to `test-support/fake-battle-fixtures.ts` for the line limit). Return-portal e2e checks the camp through the cached world (`findTilesWithKeyIn` / `verifyTileCountWithKeyIn`) because `goto('/world/camping')` now redirects. New e2e `e2e/board/world-deep-link.spec.ts`. **New hero (Oleh, 2026-11-16):** a hero with `presence: null` may enter only the camp (`HOME_LOCATION`); a refusal without presence sends the client to the camp. API tests put the hero elsewhere with `placeHeroIn(world, …)` (`world/world-test-support.ts`, relocate fixture under a temporary flag); web tests with `fakeStandIn(location)` (`test-support/fake-session.ts`, fake server `fakeRelocate`).

### MAPFIX-2. World commands name the map they expect (AUDIT-MAP-1 MAP-03/07) [DONE — 2026-11-16]

- **Trigger.** World commands carried only `heroId`; the server ran them on whatever map `progress.presence` named, and the web applied a step answer to the map it captured at send time, so an answer for a map the hero had left could change or render state.
- **Result.** Engine: `expectedMapId` (required, 1..128 chars) on `WORLD_STEP`, `WORLD_ACTION`, `WORLD_TICK`, `WORLD_TRAVEL`, `WORLD_PORTAL_OPEN`, `WORLD_PORTAL_ENTER`, `WORLD_PORTAL_CLOSE` (`MAP_BOUND_WORLD_COMMANDS`); `world/map-guard.ts` (`mapRefusal`, code `MAP_MISMATCH`). `WORLD_ENTER` (it establishes presence, which may be `null`) and `WORLD_BATTLE` (battle commands out of scope) are unchanged (Oleh, 2026-11-16). Server: `WorldService.run` refuses a mismatch after the journal/idempotency, revision, quest and `WORLD_ENTER` checks and before loading the world: journal row `rejected`/`MAP_MISMATCH` with no events, nothing else written; a replayed `commandId` still returns its original answer. Web: every world command sends the shown `currentMapId`, `WorldCommandResult.mapId` echoes it, and one comparator (`services/world/held-map.ts`: `holdsPlace` for the M1 tick guard, `holdsMap` for answers) drops a stale answer in `applyWorldResultAction`, the step (`stepOnServerWorld` answers `MAP_MISMATCH`, the walk stops silently), the tick, the portal and the board crossing. The fake player server mirrors the rule. No retry: a refused step ends the walk, a refused tick backs off and the M1 guard then keeps it quiet.
- **Tests.** Engine `world/map-guard.test.ts` (REQ-1); API `world.integration.spec.ts` «a command for a map the hero has left» (REQ-2, REQ-3; red without the guard); web `stores/world-map-stale-response.test.ts` (REQ-4, REQ-5; red without the web drop). API test helpers fill `expectedMapId` from the presence (`onHeldMap` in `world/world-test-support.ts`).
- **Reload on refusal (Oleh, 2026-11-16).** `sendWorldCommand` calls `reportMapMismatch()` (`services/world/presence-location.ts`, a listener like `reportHeroElsewhere`) when the server answers `MAP_MISMATCH`; `use-presence-route.ts` handles it once at a time: `refetchServedWorld(heldLocationKey())` (`GET /player/world` = the presence map), and only when that map is the held one it shows it (`goToLocation` for the same location, `replaceLocationRoute` for another; the route watch then loads the fresh cache). A client-side drop does not reload. Test: «reloads the map the server holds after a MAP_MISMATCH refusal» in `world-map-stale-response.test.ts` (real store and composable, red without the signal) and `use-presence-route.test.ts`. The fake `GET /player/world` (`fakeWorldSnapshot`) now returns the current world like the real server.

### MAPFIX-3. Nothing from a board survives its unmount (AUDIT-MAP-1 MAP-05/06) [DONE — 2026-11-16]

- **Trigger.** `holdPortalFxFor` left its `setTimeout` (and `portalFxBusy`) alive after the world board unmounted; the loot flight safety timer and the module-level request stayed after any board unmounted (the next board could play it); `runTween` had no `try`, so one throwing frame stopped every later `Ticker.shared` listener.
- **Result.** `render/portal-fx.ts`: holds are tokens, hold timers are tracked, and the board's `registerPortalFx` unregister clears both and frees `portalFxBusy`; a release from the old board's animation that finishes late never frees the new board. Every board dispose calls `finishLootFlights()` (`use-hex-board.ts`, `use-quest-board.ts`, battle through `graveFlights.cancel()`, which also stops `onBusy` reports after unmount). `render/tween.ts`: a throwing frame removes its handler, settles `done` and logs once; `hero-layer.tweenTo` now runs on `runTween` (same 180 ms, easeOutCubic), so it is protected too.
- **Tests.** `portal-fx.test.ts` (REQ-1 ×2 + overlap characterization), `use-hex-board.lifecycle.test.ts` (real `useHexBoard` mount/unmount: REQ-1, REQ-2, REQ-4), `tween.test.ts` (REQ-3), `services/loot/loot-flight-state.test.ts` (characterization), `battle/grave-flights.test.ts` (REQ-2 on the battle board). REQ-4 was already green before the fix (layers removed their listeners). E2E `battle-collect.spec.ts` + `quest-seeker-loot.spec.ts` 10/10.
- **Left.** `layers/portal-layer.ts` `tick` (perpetual portal spin on `Ticker.shared`) has no `try`; moving board animations to `app.ticker` (M4 second bullet) is not done.

### MAPFIX-4. One entry point for changing the active map (AUDIT-MAP-1 MAP-07/11) [DONE — 2026-11-16]

- **Trigger.** The active map was replaced in five places with five different orders: `loadLocationMap` + `installServedWorld` (+ the rest of `goToLocation`), `refetchWorldAction` (`host.map = …`), the dev `applyFreshBoard` + `finishRebuild`, `clearAllWorlds`, and the failed-load branch. Async swaps (`retryWorldLoad`, the replayed-answer refetch) applied their result even when a newer swap had happened, and opening the world scene loaded the map twice (route watch + `bootstrapWorld`), the second time restoring the battle with an already taken server view.
- **Result.** `stores/active-map-swap.ts`: `swapActiveMap(host, swap, deps)` is the only writer of `map`, `descriptor`, `currentMapId`, `currentLocationKey`, `worldLoadFailed`. A swap is `served` (cached server document), `missing` (no document), `refetched` (same map from `GET /player/world`), `fresh` (dev preview board) or `cleared` (logout); `SWAP_STAGES` is the one fixed order (stop loop → assign → hero place → cache with engagement → fog (fresh) → spawners → reseed → battle restore → entry hex → dirty → nav → reveal → entry tile → cache), each stage lists the kinds it runs for. The store calls it through `swapMap(swap)`; `goToLocation` = seal check + `loadLocationMap`; `refetchWorldAction` and the dev actions call `host.swapMap`. `installServedWorld`, `applyFreshBoard`, `setHeroLocation`, `leaveCurrentLocation`, `placeHeroOnArrival`, `arrival-action.ts`, `leave-location-action.ts` are gone. Latest request wins: every swap bumps a generation (`claimMapSwap`); `retryWorldLoad` and `refetchWorldAction` claim before their `await` and drop the result when another swap happened meanwhile. Swaps that fetch outside the store (quest exit, map-mismatch reload, portal, travel) are requests at the moment they call `goToLocation`. One load on open: `bootstrapWorld` and the `use-presence-route` watch skip a location the store already shows (`isShowing`), which also removes the second load after a route push that follows `goToLocation` (portal, crossing, gate, respawn).
- **Tests.** `stores/world-map-swap-paths.test.ts` (REQ-1, inline snapshots taken before the refactor: bootstrap, retry, board crossing, portal, quest exit, camp respawn, refetched map, dev board, logout; `crypto.randomUUID` is made deterministic because the fake server's map ids decide the entry hex), `stores/world-map-swap-order.test.ts` (REQ-2 retry overtaken by a travel, two overlapping refetches; REQ-3 one map swap on open for a matching and a replaced deep link; all red before). E2E `world-deep-link`, `board-exit`, `return-portal`, `dungeon-fog`, `quest-world-entry` 11/11.
- **Left (M5).** A quest exit still loads the camp twice: the route watch loads the cached camp as soon as the quest route is replaced, then `leaveQuestField` loads the refetched one.

### MAPFIX-5. Compile-time guard for board kinds (AUDIT-MAP-1 MAP-08) [DONE — 2026-11-16]

- **Trigger.** Branches on `boardKind` were `=== 'DUNGEON'` / `!== 'DUNGEON'` checks, and the kind union was written out in three places, so a new kind would silently fall into the STATIC side.
- **Result.** One union `BoardKind` in `packages/engine/src/registry/board-kind.ts` (`MapDefinition.boardKind` uses it, `portal-rules.ts` re-exports it). Every branch on the kind is a `switch` with `assertNever`: `portal-rules.ts` `campHexFor`, `world-leave.ts` `freshAfterLeave`, `respawn-world.ts` `freshAfterDeath`, `travel.ts` `countsAsTrip`, web `dev-board-panel-actions.ts` `regeneratesInDevPanel`, `render/fog-look.ts` `fogLookForBoardKind`. Behaviour unchanged, no test edited. Adding a kind to the union gave one typecheck error in each of the six (checked, reverted).
- **Left as is.** Branches on the `'camping'` location key (portal rules, `IN_CAMPING`, camp facilities/Book install, respawn place, home location, portal return) are about one location, not a kind, and cannot be exhaustive. `descriptor.kind` checks in `dev-board-panel.vue` and `dev-board-panel-actions.ts` narrow the `BoardDescriptor` union (`STATIC | DUNGEON | RECIPE`), a different union.

### M4. One failing animation cannot stop `Ticker.shared` (robustness) [PARTLY DONE in MAPFIX-3]

- `runTween` and `hero-layer.tweenTo` run `onFrame` in `try`; on an error they remove their handler, resolve `done` and report the error, so a broken frame never blocks other listeners. **Done in MAPFIX-3** (`tweenTo` uses `runTween`).
- Consider moving board animations from `Ticker.shared` to the board's own `app.ticker` (destroyed with the app), as the battle animator already does. Do it only together with M3, because hero and portal tweens are shared by the world and the quest field.

### M5. Leaving a quest loads the world once (optimization) [PARTLY DONE in MAPFIX-4]

- Today the exit runs `goToLocation` up to three times: the route prop watch (`QUEST_MAP` → `WORLD` with the stale `currentLocationKey`), `leaveQuestField`, and the prop watch again after `routeToLocation`. Each run deserializes the whole map, replaces `world.map`, stops the tool and redraws every tile.
- Fix: the quest exit installs the refetched world and replaces the route in one step, and the prop watch ignores a key equal to `currentLocationKey`. Combine with M1: the world board mounts only after the world matches presence.

### M6. Indexed tile lookup (optimization)

- Three O(n) scans over ~400 tiles: `world-map-board.vue` `getTileByCoord`, `use-active-map-context.ts` `objectAt` (every hover), `world-map-store.getTileAt`. Workflow §3 already lists O(n) lookup as a known conflict.
- Fix: an engine-side index on `HexMapModel` (`tileAt(coordinates)`, rebuilt only where the tile array is replaced), then use it in the three places. Characterize `getTileAt` first.

### M7. One quest field model per projection (optimization)

- `buildQuestField` runs in `use-quest-run-view.ts` and again in every `useActiveMapContext()` (host, board input, hex tooltip, and one per `equip-token.vue` instance, lazily).
- Fix: one module-level `computed` next to `questRun` in `services/quests/`, consumed by both.

### M8. Stale battle replies are ignored (correctness, small)

- `battle-store.run()` applies `reply.steps` after `await` without checking that the battle is still the same one; a reply that arrives after `close()` or `restore()` can bring a projection back.
- Fix: a generation counter bumped by `prepare`, `restore` and `close`; drop replies of an older generation. Unit test in `battle-store.test.ts`.

### M9. Quest board re-created per run (edge case)

- `use-quest-board.ts` chooses the floor sprite once at start; a different run replacing the projection without a remount (reconnect only) keeps the old floor. Key `quest-field-area` in the host by run identity (`offerId` + `start`), or rebuild the layer when `background` changes.

### M10. Shared camera fit for quest and battle (cleanup)

- `use-quest-board.ts` snaps the camera to device pixels and follows the hero; `use-battle-board.ts` does neither. Move both to one `fitBoardCamera(frame, reference, pane, focus?)` in `board-camera.ts`. Changing battle snapping is a visual change: ask Oleh first.

## Out of scope

- A single persistent Pixi application or keeping hidden boards mounted (KeepAlive / `v-show`): the one-board rule stays.
- The world board lifecycle (`use-hex-board.ts`): it starts once from `onMounted` with the pane polling fallback of `useBoardCamera`, has no double-start path, and the render skill forbids replacing that measurement.
