# Map architecture: fixes, optimizations and improvements

Source: read-only audit of the map architecture (2026-11-16, branch `codex/map-object-transitions`). The verdict was **implemented, with targeted defects**: exactly one gameplay board is mounted (`gameplay-board-host.vue`), domain states (world documents, quest run, battle) live on the server and in module-level projections, nothing is saved on unmount, and projections hide the seed and the trail. Keep the design; do not introduce a single persistent Pixi application (recreating a board has shown no measurable cost).

### M1. A background world tick never announces presence (correctness, small) [DONE — 2026-11-16]

- **Trigger.** Every quest exit (PAUSE, RETURN, GIVE_UP) sets server presence to `camping` (`quest-run.service.ts` `campPlace`), but `world-map-store` still holds the Silesia map. The host mounts the world board and starts the loop at once; `leaveQuestField` waits for `GET /player/world`. A tick 250 ms later with `hasDueWork` (likely: respawns piled up while the loop was stopped) calls `ensurePresence(Silesia)` → `WORLD_ENTER silesia`.
- **Consequence.** On slow networks the server hero goes back to Silesia, and `refetchServedWorld('camping')` can cache the Silesia document under the `camping` key.
- **Fix.** `serverTickAction` skips the tick when `inventorySession.presence` is set and differs from `{currentLocationKey, currentMapId}`; ticks never call `ensurePresence` for a place the hero has not chosen.
- **Tests.** Unit test in `stores/world-map-server.test.ts` with the fake player server: presence = camp, store on Silesia, due spawner → no `WORLD_ENTER` is sent.
- **Result (2026-11-16, branch `map-architecture-improvements`).** `serverTickAction` (`stores/server-world-actions.ts`) returns before `ensurePresence` while `inventorySession.presence` names another location or map; with no presence (fresh session) or the same place it ticks as before. Hex actions, steps and travel still announce presence themselves, so a started action always ticks. Tests: `world-map-server.test.ts` "keeps a background tick quiet …" (red before the fix: `['WORLD_ENTER', 'WORLD_TICK']`) and "ticks again once the shown world …". Web 3365/3365, typecheck, lint; e2e `gather-resource`, `return-portal`, `quest-world-entry` 7/7 without retries.

### MAPFIX-7. Latest request wins; executed but stale answers are kept (branch review #2, #7) [DONE — 2026-11-17]

- **Rule: drop the render, never the server's effect.** An answer for a map the client no longer shows is never drawn on the shown board, but what the server did (Will, inventory, portal link, presence, travelled documents) is kept and the board is brought back to the server's world once.
- **#2 Tickets.** `claimMapSwap()` returns a ticket `{ latest(), settle() }`; only a request that will swap takes one (`reloadLocationMap`, `retryWorldLoad`), and `swapActiveMap` bumps the generation itself. `reloadLocationMap` claims a ticket per caller and shares one network request per key (`locationReloads`); it returns `true` only when its own ticket applied. `refetchWorldAction` takes no ticket: it observes (`observeMapSwaps()`) and applies only if no swap was claimed or applied since it started, no ticketed request is still waiting, and it is the latest refetch. The MAPFIX-6 recovery replaces the route only when its reload applied, so a superseded recovery never moves the route to a stale place.
- **#7 Stale executed answers.** `keepStaleAnswer(result)` (`services/world/served-world.ts`) is called wherever an accepted answer is dropped because the map changed: step (`stepOnServerWorld`), hex action and gate travel (`knowledge-controller.ts`), board crossing, portal open/enter (`use-portal.ts` `droppedPortalAnswer`). It caches the travelled/touched documents and calls `reportStaleAnswer(mapId)` (`presence-location.ts`); `use-presence-route.ts` (`onStaleAnswer`) ignores an answer for the still-shown map, otherwise stops the hand and runs the MAPFIX-6 recovery of the held location (joins a running one). Will and inventory come from the answer's aggregates (`sendWorldCommand` already applies them), so no new endpoint. The portal animation was already released in `finally`.
- **Tests.** `stores/world-map-latest-request.test.ts` (scene with `usePresenceRoute` and a fake router): REQ-1 (evicted load + refetch with no swap → evicted map, route = board), REQ-2 (two `reloadLocationMap` callers with a swap between → one request, only the latest applies), REQ-3 (recovery superseded by a travel → board and route on the travel target, no route bounce), REQ-4 portal OPEN (board untouched, one resync, Will and scroll = server, hand stopped) and ENTER (release once, no exit, one resync to the camp, route = board), plus a stale step.
