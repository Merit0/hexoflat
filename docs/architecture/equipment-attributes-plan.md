## 1. Слоти й групи

- Слоти — наявна модель коду (EA0): `EQUIP_SLOTS` weapon, shield, armor, gloves, helm, boots, ring, amulet; UI показує 6 (без ring, amulet). Тип предмета має поле `slot` у контенті; сумісність слота береться з типу, не з ключа (див. §12 D-EA2).
- Група визначає роль предмета й пул атрибутів.

| Група    | Типи → слот                                                    | Атрибути                                                                                    |
| -------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Зброя    | меч, сокира, кайло → weapon                                    | §3                                                                                          |
| Оборона  | щит → shield                                                   | §4                                                                                          |
| Одяг     | шолом → helm, броня → armor, рукавиці → gloves, чоботи → boots | §5                                                                                          |
| Прикраси | каблучка → ring, амулет → amulet                               | §5b (типи `enabled: false`, доки слоти ring/amulet не показані в UI — окреме рішення Олега) |
| Ноша     | пояс, сумка, ліхтар                                            | чернетка                                                                                    |
| Оберіг   | талісман                                                       | лише унікальні; атрибути задає Creator                                                      |

## 2. Генератор атрибутів (`EquipmentAttributeGenerator`)

- Працює **лише для базових токенів** у `createBase`. `createUnique` копіює атрибути з визначення й генератор не викликає. Поле `rolled` у `UniqueTokenDefinition` прибрати.
- Входи: `level = container.level ?? board.tier` (1–4), група й тип (уже вибрані фабрикою), `type.tool`, сідований RNG, профілі й реєстр атрибутів з контенту.
- Вихід: `ItemAttribute[]`. Генератор не знає назви, спрайта, героя чи бою.

Кроки:

1. Профіль = `profiles['tier-<level>']`. Немає профілю — помилка валідації контенту.
2. Пул: атрибут є в профілі, `implemented: true`, група збігається, тип у `onlyTypes` (якщо задано), виконано `requires` (`tool`).
3. Кількість: зважений кидок `0..maxCount`, обрізаний до пулу.
4. Вибір: зважений, без повторів. Порожній пул = зупинка, не помилка.
5. Значення: ціле в `[min, max]` з кроком `step` (одиниці: пів-серця, очки криту, сторони, кроки, пів-кг).
6. Вихід проходить Zod.

Кількість атрибутів 0/1/2 за рівнем (спільно для всіх груп): tier-1 55/40/5, tier-2 40/45/15, tier-3 25/50/25, tier-4 10/50/40; `maxCount` 2.

Принципи: окремий потік RNG на крок (`token:<id>:attr:count`, `:attr:pick:<i>`, `:attr:value:<key>`); токен зберігає результат, не сід; межі героя застосовує правило використання, не генератор; нове = дані.

OOP: `EquipmentAttributeGenerator implements IAttributeGenerator`; залежності через конструктор: `IAttributeProfileProvider`, `IAttributePoolFilter`, `ICountRoller`, `IWeightedPicker`, `IValueRoller`.

(значення серць у контенті — пів-серця: ½ = 1, 1 = 2)

**Рядок атрибута в описі:** `{назва} {іконка} {число}` — назва з i18n (en / uk), іконка з наявного набору `item-icons.ts`, число. Приклад: `Smart Step [boots] 5` / `Розумний крок [boots] 5`. Пояснення правила — окремий ключ i18n для підказки. Нових іконок і стилів немає.

## 3. Зброя — затверджено

Шкода — базова властивість типу (меч 1 серце, сокира/кайло ½), не генерується. Атрибути можуть змінювати шкоду.

| Атрибут                                                               | Ефект                                                                              | Вага | tier-1 | tier-2 | tier-3 | tier-4 | Статус               |
| --------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ---- | ------ | ------ | ------ | ------ | -------------------- |
| `crit` Крит                                                           | очки криту; resolver RNG: 1 очко = 1%; додається до шансу криту героя              | 45   | 4–6    | 5–8    | 7–10   | 9–12   | відкрито             |
| `critDmg` Критична шкода                                              | при криті цієї зброї: базова шкода × 2 + бонус; не залежить від `crit` на предметі | 20   | ½      | ½      | ½      | ½–1    | відкрито             |
| `trophy` Трофей                                                       | +N жетонів у могилі ворога, вбитого цією зброєю (смертельний удар)                 | 25   | 1      | 1      | 1      | 1–2    | відкрито             |
| `yield` Видобуток                                                     | +N ресурсу при рубці/видобутку; `requires: { tool: true }`                         | 30   | 1      | 1      | 1–2    | 1–2    | відкрито             |
| initiative, sweep, feint, knockback, critPower, damagePlus, damageMul | —                                                                                  | —    |        |        |        |        | `implemented: false` |

Шанс криту удару = шанс криту героя (рукавиці §5, навички) + `crit` зброї, якою б'ють; межа 25% на удар.

Межі героя: критична шкода ≤ +1 серце; трофей ≤ +2; видобуток ≤ +2. Вороги криту не мають. Рука не є токеном і атрибутів не має.

## 4. Оборона (щит) — затверджено

Базові властивості типу `shield` (не генеруються):

- **Захист 1 серце** (`defense: 2` пів-серця) — діє лише на удар у заблоковану сторону.
- **Блок 1 сторона.** Без надітого щита блоку немає (лише ухил). Скасовує D6 «2 сторони».
- **Шкоди немає.** Щит не б'є. Майбутня навичка «удар щитом» б'є атакою героя (від інших джерел). Скасовує D6 «удар щита 1».

| Атрибут                         | Ефект                                                                                | Вага | tier-1 | tier-2 | tier-3 | tier-4 | Статус                             |
| ------------------------------- | ------------------------------------------------------------------------------------ | ---- | ------ | ------ | ------ | ------ | ---------------------------------- |
| `block` Блок                    | +N сторін блоку за хід                                                               | 40   | 1      | 1      | 1      | 1–2    | відкрито                           |
| `heart` Серце                   | +N до максимуму сердець героя                                                        | 40   | ½      | ½      | ½–1    | ½–1    | відкрито (`heart` вже реалізовано) |
| `thorns` Шипи                   | нападник, чий удар влучив у щит, втрачає N серця (навіть якщо частина шкоди пройшла) | 20   | ½      | ½      | ½      | ½–1    | відкрито                           |
| defensePlus, counter, steadfast | —                                                                                    | —    |        |        |        |        | `implemented: false`               |

- `defensePlus` (+Захист) заблоковано разом із `damagePlus` зброї: відкриваються лише парою.
- Відкинуто: дешевший блок у Волі (ціна блоку не залежить від предмета), захист від криту (вороги не критують).

Межі героя: сторін блоку ≤ 6; серце від щита ≤ +1 за щит; шипи ≤ 1 серце за удар. Два щити — два слоти, сторони сумуються.

## 5. Одяг — затверджено

Базове **Серце** типу (не генерується), щоб предмет без атрибутів мав сенс у слоті: шолом ½, броня 1, рукавиці ½, чоботи ½.

| Атрибут                                | Типи (`onlyTypes`) | Ефект                                                                                               | Вага | tier-1 | tier-2 | tier-3 | tier-4 | Статус                                    |
| -------------------------------------- | ------------------ | --------------------------------------------------------------------------------------------------- | ---- | ------ | ------ | ------ | ------ | ----------------------------------------- |
| `heart` Серце                          | усі                | +N до максимуму сердець                                                                             | 35   | ½      | ½      | ½–1    | ½–1    | відкрито                                  |
| `absorb` Поглинання                    | броня, шолом       | незаблокований удар −N, але шкода ≥ ½                                                               | 20   | ½      | ½      | ½      | ½      | відкрито                                  |
| `sight` Погляд                         | шолом              | +N до радіуса відкриття туману                                                                      | 30   | 1      | 1      | 1      | 1–2    | відкрито, якщо радіус туману є в коді     |
| `heroCrit` Крит героя                  | рукавиці           | очки до шансу криту героя                                                                           | 30   | 1–2    | 1–3    | 2–4    | 3–5    | відкрито                                  |
| `smartStep` Smart Step / Розумний крок | чоботи             | кожен N-й крок не коштує Волі (менше N — краще). Рядок: `Розумний крок [boots] N`                   | 30   | 5      | 4–5    | 3–4    | 3      | відкрито, якщо ціна кроку у Волі є в коді |
| `deftHands` Deft Hands / Вправні руки  | рукавиці           | дія «Використати» (USE) предмета коштує на N Волі менше, мінімум 1. Рядок: `Вправні руки [will] −N` | 30   | 1      | 1      | 1      | 1–2    | відкрито, якщо USE має ціну у Волі в коді |
| mass, rest                             | —                  | Маса (чекає поштовху), Відпочинок (якщо кемп не лікує)                                              | —    |        |        |        |        | `implemented: false`                      |

**Smart Step — правило лічильника:**

- Герой має лічильник платних кроків `stepCounter` у своєму стані (не в предметі).
- Кожен крок, що мав коштувати Волю, збільшує лічильник на 1. Коли лічильник досягає N, цей крок безкоштовний і лічильник = 0.
- N = найменше значення серед надітих чобіт (не сумується); без чобіт зі `smartStep` лічильник не рахує.
- Діє лише на кроки світової мапи, що коштують Волю (EA0: `knowledge/reducer.ts:118` ← `world-commands.ts:150-158`). Бій і поле квесту — ні (інші ціни кроку). Безкоштовні зони лічильник не рухають.
- Заміна чобіт лічильник не скидає. Зберігається разом зі станом героя.
- Фізично: на картці чобіт доріжка з N клітинок; жетон рухається на 1 за платний крок; на останній клітинці крок безкоштовний, жетон на старт.
- Детермінований, без RNG. Показ — наявними засобами (без нових елементів UI).

Порядок удару з Одягом (§6): крит → шкода → якщо заблоковано: − Захист щита, інакше: − Поглинання (не менше ½) → ефекти.

Smart Step: шкала N = 1…5 (1 — кожен крок безкоштовний). Базовий генератор дає 3–5; N = 1–2 — лише унікальні предмети (Creator), бо 1 = рух без Волі, 2 = −50%.

Межі героя: серце з усіх предметів (база + атрибути) ≤ +5; Поглинання ≤ ½ на удар (не сумується); Погляд ≤ +2; Smart Step N ≥ 1 (базові ≥ 3); Вправні руки разом ≤ −2, ціна USE ≥ 1.

## 6. Удар — конвеєр і замінна логіка криту

Порядок кроків (кожен — інтерфейс):

1. **Крит** — `ICritResolver` кидає завжди, включно із заблокованими ударами.
2. **Шкода** — база типу; при криті × 2 + `critDmg` цієї зброї.
3. **Блок / Поглинання** — удар у заблоковану сторону: шкода = max(0, шкода − Захист щита), спрацьовують Шипи; інакше: шкода = max(½, шкода − Поглинання) (якщо Поглинання > 0).
4. **Ефекти** — подія удару.

```ts
interface ICritResolver {
  id: 'rng-chance' | 'dice' | 'counter' | 'math';
  resolve(ctx: CritContext): CritOutcome; // { critical, detail }
  describe(rating: number): DescriptionLine;
}
```

- Вибір логіки — контент `combatRules.critResolver: 'rng-chance'`.
- Предмет і герой зберігають рейтинг (очки), resolver переводить його у свою механіку → зміна логіки без міграції.
- Потік RNG `combat:<battleId>:strike:<n>:crit`. Подія удару фіксує `critical`, `resolverId`, `blocked`, `damageBeforeBlock`, `damageDealt`; повтор бере результат з події.
- Показ: web показує дані події наявними засобами. Нових компонентів і стилів немає.

| Удар                    | Шкода | Після щита (Захист 1) | Без блоку, Поглинання ½ |
| ----------------------- | ----- | --------------------- | ----------------------- |
| Сокира                  | ½     | 0                     | ½                       |
| Меч                     | 1     | 0                     | ½                       |
| Меч, крит               | 2     | 1                     | 1½                      |
| Меч, крит + `critDmg` ½ | 2½    | 1½                    | 2                       |

## 7. Назви базових токенів

- Шаблон: `{прикметник} {іменник}`, 2 слова. Інструменти — лише іменник (D13).
- Група прикметника = фактична кількість атрибутів: 0 → бідні (Бідний, Зламаний, Зношений, Старий, Тріснутий, Грубий, Іржавий), 1 → матеріал (Дерев'яний, Залізний, Бронзовий, Мідний, Шкіряний, Кістяний, Кам'яний), 2 → добрі (Міцний, Гартований, Полірований, Майстерний, Гострий, Добротний).
- Прикметник може мати `material` (дозволено лише для типів з цим матеріалом) і `groups` (Гострий — лише зброя). «Легкий» / «Важкий» не використовувати, поки прикметник не змінює вагу.
- uk: тип має `gender` (`m|f|n|pl`), прикметник — 4 форми. `TokenName = { kind: 'generated'; adjective: WordKey; noun: ItemTypeKey } | { kind: 'noun'; noun } | { kind: 'authored'; nameKey }`.

## 8. Ціна базового токена

Випадкова в діапазоні світу (D4), але в третині за кількістю атрибутів: 0 → нижня, 1 → середня, 2 → верхня.

## 9. Розширюваність — додати або змінити атрибут без переписування

Атрибут = **дані** (контент, Zod, версія) + **стат героя**, який читає правило гри. Правила ніколи не читають атрибути предметів напряму.

```ts
interface AttributeDefinition {
  // контент
  key: AttributeKey; // ніколи не перевикористовується
  group: GroupKey;
  onlyTypes?: ItemTypeKey[];
  requires?: { tool?: true };
  stat: HeroStatKey; // 'maxHearts' | 'maxWill' | 'critPoints' | 'blockSides' | 'absorb' | 'stepFreeEvery' | 'useWillDiscount' | 'shopBuyDiscountPct' | 'answerWillReward' | 'fogRadius' | 'graveLootBonus' | 'harvestBonus' | 'critDamage' | 'thorns' ...
  aggregate: 'sum' | 'min' | 'max'; // як складати з кількох предметів (Smart Step = min, Поглинання = max)
  scope: 'hero' | 'item'; // item = діє лише для дій цього предмета (crit, critDmg, trophy, yield)
  cap?: number; // межа героя
  display: {
    labelKey: I18nKey;
    hintKey: I18nKey;
    icon: TIconName;
    format: 'plus' | 'minus' | 'pct' | 'sec' | 'hearts' | 'plain';
  };
  implemented: boolean;
  deprecated?: boolean;
}
```

- `resolveHeroStats(hero, equipped, registry): HeroStats` — чиста функція: база типів + атрибути → агрегація → межі. Єдине місце, де атрибути стають числами. Правила (бій, крок, USE, магазин, Зал, туман, могила, видобуток) читають лише `HeroStats` або статистику предмета (`scope: 'item'`).
- Поведінкові правила, яким мало одного числа (лічильник Smart Step, крит, Шипи), — окремі класи за інтерфейсом, зареєстровані за `stat`; їх читає конвеєр (§6) або правило дії.

Як змінювати на оновленні:

| Зміна                                                     | Що робити                                                                                       | Код             |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | --------------- |
| Нове значення, вага, діапазон, межа                       | змінити контент                                                                                 | ні              |
| Новий атрибут для наявного стату (напр. «Серце» на поясі) | рядок `AttributeDefinition` + рядок профілю + i18n + іконка з наявних                           | ні              |
| Атрибут на новому типі/групі                              | `onlyTypes` / `group` у контенті                                                                | ні              |
| Новий стат (нова механіка)                                | 1 ключ `HeroStatKey` + 1 правило гри, що його читає + контент                                   | так, одне місце |
| Вимкнути атрибут                                          | `deprecated: true` → генератор не видає; наявні предмети показують його, ефект діє, доки є стат | ні              |
| Перебалансувати вже видані предмети                       | upcaster за `CONTENT_VERSION` (дозвіл Олега)                                                    | так             |

**Назви атрибутів статичні.** Генератор не створює назв атрибутів: він обирає лише ключ і значення. Назва, підказка, іконка й формат — у реєстрі (`display`) і локалях en/uk; ними керує Creator. Зміна тексту назви одразу діє для всіх предметів, бо рядок будується під час показу (D-EA8). Генеруються лише назви предметів (§7).

Правила: ключ атрибута й стату не перевикористовується; токен зберігає значення, тож зміна контенту не змінює видані предмети; `implemented: true` лише коли стат має читача (перевіряє тест).

**Однаковий шаблон кожної фази A:** характеризаційний тест поведінки, яку змінює атрибут → читач стату → `implemented: true` → тест атрибута → EA-16 зелений → e2e лише якщо зміна видима в наявному сценарії. Один шаблон промпту, змінюється лише атрибут і рядок цієї таблиці.

Типи вмикаються (`enabled: true`): одяг — після EA4 (база серця); прикраси — після A02 і рішення про слоти ring/amulet в UI (D-EA2).

Вмикання нових типів додатково вимагає спрайта або згоди Олега на placeholder.
Кожна фаза від EA4 починається з характеризаційних тестів поведінки, яку змінює.

Поза планом: Ноша (ще не спроєктована), Оберіг (лише унікальні), заблоковані атрибути, нові спрайти (Creator додає пізніше; до того — placeholder).
E2E: лише сценарії, яких торкається фаза (EA3 — підказка предмета/спорядження, EA5 і A10–A15 — бій, A03/A04 — рух/USE); без повної регресії.

Відкриті питання до EA0 (відповідає звірка):

1. Чи може зараз будь-який предмет лягти в будь-який із 6 слотів? Якщо ні — EA1 додає це як окремий крок.
2. Як зберігається назва вже виданих токенів — підтвердити, що legacy-гілка читання достатня без підняття `CONTENT_VERSION`.

`stepCost` та `travelStepBudget` — спільний engine-розрахунок для сервера, планувальника та прев’ю; бюджет — доступний префікс маршруту, тому при 0 Will наступний безкоштовний крок дозволено. `progress` v11 має additive upcaster 10→11 (`paidSteps: 0`) без скидання збережень і без зміни CONTENT_VERSION. Старі кроки не використовуються як фаза нового лічильника. KNOWLEDGE завантажує server-held inventory разом із progress; клієнт не передає N або лічильник у команді.

Профілі чобіт не змінені: tier 1 N=5, tier 2 N=4…5, tier 3 N=3…4, tier 4 N=3; N=1/2 підтримується на вже виданих/унікальних токенах. Boots залишаються disabled. E2E використовує owned legacy shield з атрибутом через наявну dev-фікстуру, без послаблення фабрики.
