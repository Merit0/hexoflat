# Аудит генератора предметів: надійність, незалежність і секретність

Дата: 2026-11-18. Перевірений HEAD: `277167d748119a5a783ad2b3b5151107618d9d1d`.

## 1. Мета та висновок

Генератор має працювати в будь-якому джерелі нагород: на мапі, у магазині, бос-контейнері, квесті та майбутніх механіках. Він повинен відтворювати результат на сервері, зберігати ідентичність предмета та не давати гравцю відновлювати прихований лут із доступних клієнту даних.

**Висновок початкового аудиту (до виправлень): ядро добре відокремлене від дошки, але весь механізм генерації та видачі ще не готовий до безумовного повторного використання.** Підтверджені колізії ID і дефекти валідації. Унікальні нагороди не підключені до виробничої видачі. Розширення типів досі потребує старого реєстру предметів.

Перевірені сценарії секретності пройшли. У цьому аудиті не продемонстровано відновлення актуального прихованого луту зі штатної клієнтської проєкції. Це не доводить відсутності всіх витоків або майбутніх експлойтів. Надійність має забезпечуватися контрактами, захисними тестами й перевіркою кожного нового джерела, а не обіцянкою «ніколи не зламається».

## Стан після виправлень у цій гілці

Реалізовано й перевірено регресіями F1–F6 для нової генерації. Нижче збережені початкові відтворення дефектів; вони описують стан до виправлень, а не поточний результат.

### Межі гарантій і незавершена робота

- LG5d не завершено: новий текст D17/D18 про слоти сокири/кайла та durability відсутній у цьому чаті. Збережено поточні правила, ручні визначення ще потрібні інтеграціям. D16 виправлено окремо.
- Unique-drop і атомарний облік `ownedUniques` ще не підключені до production-видачі. Немає погоджених джерел/шансів та правила повторного отримання після продажу; вони не вигадані в цьому патчі.
- Старі збережені shop token ID між різними героями не переписуються. Перед міжгеройним обміном потрібна міграція всіх місць збереження/посилань; inventory v3 ремонтує лише дублікати всередині одного інвентарю.
- Властивості нових предметів для змінених source ID можуть відрізнятися від старого алгоритму адресації. Збережені токени не перегенеровуються. Namespace магазину стабільний лише поки стабільний секрет: ротація секретів потребує окремої політики та збереження вже створених товарів.
- Швидкий SHA-256 digest не приховує слабкий seed від перебору. Авторитетний адаптер мусить використовувати високоентропійний серверний секрет; фабрика не може довести його походження. Перевірка підрядка seed — регресійний запобіжник, а не універсальний DLP-фільтр.
- Це не повний penetration test, не формальний криптографічний аудит і не гарантія відсутності майбутніх збоїв. Checklist нижче зберігається як критерії наступних інтеграцій; незакриті пункти не позначено виконаними лише через зелений suite.

### Правила з погляду гравця

1. Сервер фіксує джерело, його рівень/світ і ID нагороди до видачі. Рівень героя чи місце відкриття інвентарю не посилює предмет.
2. Повтор відкриття, reload або retry повертає той самий результат. Невдала видача через вагу/місце не повинна давати новий roll або знищувати нагороду.
3. Pickup, equip, stash, продаж і buyback переносять той самий токен, а не генерують новий.
4. Бос може мати іншу погоджену таблицю нагород, але не обходить ліміти рівня. Якщо унікальний предмет завеликий для джерела, конфігурацію треба виправити до релізу; приховано зменшувати бонус або повторювати roll до успіху не можна.
5. Нове джерело має пройти тести секретності, retry/конкуренції, повної сумки, persistence та збереження ID. Самого виклику фабрики недостатньо для надійної видачі.

## 3. Підтверджені дефекти

Пріоритети: P1 — закрити до використання токена як наскрізної ідентичності/міжгеройного обміну; P2 — закрити до розширення генератора новими джерелами та контентом. Пріоритет не означає, що вже доведено експлуатацію в production.

### F1. Повторні ID в одній квестовій нагороді — P1

Місце: `packages/engine/src/quests/quest-log.ts`, `rewardMint`, цикл `planClaim`; `inventory/apply-stock.ts`, `tokenSource`; `inventory/inventory-state.ts`, `everyIdIsUnique`.

Відтворення: готовий квест `audit`, герой `hero-1`, `done[audit] = 0`, нагороди `sword × 1` та `shield × 1`, seed `audit-secret-2026`.

```text
sword.token.id  = quest:audit.hero-1.0:0
shield.token.id = quest:audit.hero-1.0:0
inventoryStateSchema.safeParse(result.inventory).success = true
```

Кожен рядок отримує той самий mint і починає `piece` з нуля. Перевірка інвентарю контролює `item.id`, а не `item.token.id`.

Наслідок: два різні токени мають одну ідентичність; майбутній облік, дедуплікація та обмін за token ID будуть неоднозначними. Фактичну втрату предметів у поточному UI не продемонстровано.

Критерій виправлення: один наскрізний індекс на всю видачу або стабільний namespace кожного рядка; регресія на кілька типів і повторні рядки одного типу, повторний квест, retry та відмову через повну сумку. Перевірити унікальність token ID в агрегаті.

### F2. Магазин повторює ID між героями — P1

Місце: `packages/engine/src/trade/trader-view.ts`, `slotMint`.

Відтворення: `rollTraderGoods(TRADERS.ilva, seed, 'ilva', 0)` для `hero-one-secret` і `hero-two-secret`.

```text
seed A: shop:ilva.0.g2:0, price 388
seed B: shop:ilva.0.g2:0, price 511
```

Seed змінює властивості, але ID містить лише торговця, serial і слот. Для ізольованих інвентарів це не доведена поточна втрата даних; для майбутнього міжгеройного обміну це дефект глобальної ідентичності.

Критерій виправлення: публічний унікальний namespace власника/екземпляра магазину, незалежний від секретного seed. Не вставляти seed у ID. Два герої не мають отримувати однакові token ID; повторний запит одного героя повинен повертати старі ID.

### F3. Побудова source ID має колізії — P2

Місце: `packages/engine/src/tokens/game-tokens.ts`, `sourcePart`, `tokenSourceIdOf`.

```ts
tokenSourceIdOf('quest', 'a.b', 'c'); // quest:a.b.c
tokenSourceIdOf('quest', 'a', 'b.c'); // quest:a.b.c
```

Додатково нормалізація регістру й заміна символів зливають різні вхідні значення. Не кожна така пара досяжна з поточних UUID, але загальний helper не гарантує унікальності для майбутніх джерел.

Критерій виправлення: однозначне кодування сегментів або непрозорий публічний source UUID; property-based тест на роздільники, регістр, порожні та Unicode-значення. Зміна формату потребує сумісності зі збереженими ID.

### F4. `safeParse` шансів кидає винятки — P2

Місце: `packages/engine/src/tokens/unique-drop.ts`, `parseChance`, `fractionOf`, `totalChance`, `greatestDivisor`.

```ts
uniqueDropRulesSchema.safeParse([{ uniqueKey: 'a', chance: 'bad' }]);
// TypeError: Cannot read properties of null (reading 'den')

uniqueDropRulesSchema.safeParse([{ uniqueKey: 'a', chance: '1/' + '9'.repeat(310) }]);
// RangeError: Maximum call stack size exceeded
```

Перевірка суми повторно читає невалідний дріб через type assertion. Number може переповнитися, а рекурсивний НСД не завершується для NaN. Навіть скінченні великі дроби можуть втратити точність при множенні.

Критерій виправлення: не обчислювати суму невалідних дробів; гарантувати допустимий числовий діапазон або використовувати точну арифметику; повертати помилку схеми. Додати malformed/overflow/сума рівно 1/сума трохи понад 1. Не припускати, що контентний рядок зараз доступний зовнішньому користувачу: зовнішній DoS цим аудитом не доведено.

### F5. Фабрика не перевіряє узгодженість кастомного контенту — P2

Місце: `tokens/factory/create-token-factory.ts`, `token-validator.ts`, `content/validate-tokens.ts`.

Передано копію `lantern-eater` з фіксованим атрибутом `shield: 999`. `createUnique` повернув `ok: true` для меча, хоча `shield` має `implemented: false`, дозволений лише щиту, а 999 виходить за діапазон.

`uniqueContentFailures` містить потрібні перевірки, але конструювання фабрики їх не виконує. Валідація форми токена не замінює перевірку зв'язків між реєстрами.

Критерій виправлення: єдина перевірена точка завантаження контенту; кожен public шлях створення фабрики або відхиляє неузгоджений контент одразу, або приймає лише явно валідований набір. Не дублювати правила в кількох валідаторах.

### F6. Контракт відмов не охоплює всі помилки генерації — P2

Місце: `tokens/factory/token-factory.ts`, `description-builder.ts`, `name-generator.ts`.

`createBase(ctx, { attributes: [{ key: 'unknown-attribute', value: 1 }] })` кидає `Error: Unknown attribute`, не повертає `TokenResult`. Порожній/несумісний пул назв також має явний throwing path. Невідомий атрибут відтворено; порожній пул визначено читанням коду.

Відомий, але не реалізований `shield: 999` через overrides приймається. Overrides створені для DEV-фікстур: можливість задавати довільну силу там сама по собі не є production-експлойтом. Важливо явно відділити цей режим від звичайної генерації.

Критерій виправлення: визначити, які помилки є відмовою запиту, а які помилкою конфігурації; перевіряти їх до виконання кроків. Не маскувати всі програмні помилки загальним catch. DEV-overrides недоступні production-клієнту.

| Унікальні нагороди            | Фабрика й resolver є, виробничих викликів `createUnique`/`resolveUniqueDrop` не знайдено; `ownedUniques` зберігається, але не поповнюється видачею                   |
| Вага/слоти/бойові властивості | Частково залежать від старих визначень предметів; LG5d вже позначено незавершеним у плані                                                                            |
| Навички                       | Базові токени отримують порожній список; наявність skills у даних не означає реалізованого ефекту                                                                    |

Закритий перелік джерел — архітектурне обмеження, а не самостійний витік даних. `mapTier` може бути рівнем генерації, який передає магазин або квест без мапи; сама назва поля не створює runtime-залежності від дошки.

Для повної переносимості потрібні спільні правила генерації та вузькі адаптери видачі. Адаптер відповідає за авторизацію, секрет, source ID, транзакцію й збереження; фабрика — за токен. Бос-контейнер не повинен мати копію фабрики.

## 5. Якість випадкової генерації

У матриці 4800 токенів: 1584 без атрибутів, 3216 з одним. Це приблизно 33%/67%: запитана кількість 0–2 обрізається на одному реалізованому атрибуті `heart`. Два атрибути зараз не з'являються. Після додавання реалізованих атрибутів розподіл зміниться, тому потрібна окрема перевірка балансу.

Ціна рівномірно котиться в діапазоні світу, не оцінює силу, tier або атрибути. Це відповідає D4 і не є знайденим дефектом; «розумний» тут означає генерацію за правилами, а не оцінювання корисності предмета.

Наявні тести перевіряють імовірності unique-drop на 10 000 seed, детермінізм, схеми, імена, спрайти й потоки. Статистичний тест розподілу не є доказом криптографічної непередбачуваності.

### 5.1. Обов'язкові ліміти атрибутів за рівнем джерела

**Уточнення Олега, 2026-11-18:** значення атрибутів мають обмежуватися рівнем джерела, де предмет випав. Приклад для базового рівня: щит може бути без додаткового атрибута `shield` або мати `shield: 1`; `shield: 5` недопустимий. Це обмеження бонусного атрибута, а не рішення щодо базового `block.sides` щита або конфлікту LG5d.

Правило стосується всіх джерел: мапи, магазину, боса, контейнера й квестової нагороди. Рівень визначає серверний адаптер джерела, а фабрика отримує його як значення контексту — без залежності від конкретної дошки. Рівень героя, місце подальшого підбору/продажу чи клієнтський параметр не повинні підміняти рівень походження предмета.

Контракт для реалізації:

- Для кожного атрибута контент визначає допустимі значення або діапазон за рівнем джерела та дозволені типи предмета. Формат таблиці — деталь реалізації; інші числові ліміти цим уточненням не задані.
- Спочатку обираються допустимі атрибути, потім їхні значення лише в межах відповідного рівня. Відсутність бонусу зберігається як відсутність атрибута, а не `value: 0`.
- Фінальна семантична валідація перевіряє рівень і всі значення, незалежно від того, який компонент їх створив. Метаданих `mapTier` у токені недостатньо.
- Рідкість, босове походження або unique-статус не дають неявного дозволу перевищувати ліміт. Фіксовані атрибути unique також потребують перевірки: несумісне визначення не можна видати на цьому рівні. Автоматично знижувати authored-значення або вводити винятки без окремого правила не слід.
- Відсутній/невідомий рівень повинен мати явно визначену політику: відмова або документований базовий рівень для конкретного джерела. Некоректний рівень не можна мовчки перетворювати на сильніший.
- Після створення бонуси не перераховуються при перенесенні на іншу мапу, продажу, підборі іншим героєм чи reload. Рівень і результат походження зберігаються.

**Що вже є в коді:** `WeightedAttributeGenerator` бере значення з `definition.valueByTier[mapTier]`. Для `shield` контент задає `{ 1: 1, 2: 1, 3: 1, 4: 2 }`, але атрибут має `implemented: false`, тому зараз звичайна генерація його взагалі не обирає. Це часткова основа правила, а не завершена гарантія для всіх шляхів.

**Прогалини:** фінальний `ZodTokenValidator` не перевіряє відповідність значення рівню; overrides обходять `valueByTier`; фіксовані unique-атрибути не залежать від поточного tier. Навіть `uniqueContentFailures` перевіряє значення в загальному min/max усіх рівнів, а не допустимість для конкретного рівня видачі. Квестові нагороди й магазин зараз отримують `campTokenOrigin()`, тому для майбутніх джерел з іншими рівнями потрібна явна передача їхнього справжнього рівня. Це додаткова вимога до закриття F5–F6 та інтеграцій, а не твердження, що звичайний базовий щит уже випадає з +5.

Критерії перевірки:

- [ ] Базове джерело: для щита дозволено лише відсутність `shield` або `shield: 1`; +2, +5, +999 відхиляються. Поки атрибут не реалізовано, звичайний генератор не видає його зовсім.
- [ ] Матриця всіх рівнів × типів × атрибутів × джерел: кожен виданий бонус належить дозволеному набору; перевірити нижню/верхню межу й значення за межами.
- [ ] Однакові правила діють для random base, rolled unique і fixed unique; production не обходить їх через overrides або custom-компонент.
- [ ] Тест із підставним генератором, що повертає `shield: 5` на tier 1, отримує відмову фінального валідатора.
- [ ] API відхиляє/ігнорує підміну рівня клієнтом і обчислює його з авторитетного стану джерела.
- [ ] Джерела без дошки мають власний явний рівень; нагорода квесту не стає базовою лише через видачу в таборі, якщо її джерело має інший рівень.
- [ ] Підбір після переходу героя на інший рівень, передача, магазин і перезапуск зберігають початковий токен без reroll.

## 6. Секретність і передбачення луту

### Що підтверджено

- `aggregate-store.ts` створює серверний rngSeed через `node:crypto.randomBytes(16)`; `expedition/expedition-store.ts` так само створює seed експедиції. Це не `Math.random`, не час і не hero ID.
- RNG детермінований, похідні потоки використовують SHA-256 і окремі мітки. Детермінізм потрібен для retry/replay; безпека залежить від невідомого клієнту сильного секрету та правильного розділення контекстів.
- Для могил лут використовує серверний `tokenSecret`, а не публічний battlefield seed. Тест старого способу відновлення з клієнтських даних пройшов після LG5g.
- API-тести охоплюють відповіді й проєкції world chest, grave, quest chest, camp chest та quest reward; перевіряють приховані таблиці/вміст і секрети. Детектор шукає seed у сирому вигляді, з іншими роздільниками й як 16-hex підрядок.
- `sourceIdContainsSeed` відмовляє, якщо source ID містить повний seed у підтриманій нормалізації.

Це докази конкретних перевірених шляхів. Відмінний результат при іншому seed не доводить криптографічної стійкості. Відсутність сирого seed не виключає витік готового луту або стану RNG.

### Ризики та прогалини, які ще слід закрити

**S1. Передбачуваний fallback у загальній видачі.** `inventory/apply-stock.ts::fallbackMint` використовує `seed = grant:<heroId>` та `dev:<heroId>.<idSeq>`. Це публічно відтворюваний шлях. Він не перевіряє DEV-режим у самому helper. Основні перевірені джерела передають секрет або готовий token; досяжність fallback через звичайну production-команду не доведена. Потрібен тест: production-видача gear без token/secret має відмовити, а не тихо згенерувати передбачуваний предмет. DEV та міграції повинні мати явні окремі правила.

**S2. Перевірка seed у source ID — лише додатковий захист.** Вона не контролює description, ext, інші DTO, логи, помилки, metadata чи переданий custom-компонентом вміст. Частковий/закодований секрет також може пройти. Потрібні allowlist-проєкції й перевірки всіх публічних поверхонь, а не лише пошук рядка.

**S3. Короткий quest run ID.** `questRunId` бере 12 hex із SHA-256 seed, тобто 48 біт. Це не розкриття 128-бітного секрету, але простір ID має birthday-колізії; приблизно на 20 млн незалежних значень шанс хоча б однієї колізії сягає 50%. Це масштабний ризик, не відтворений поточний збій. Потрібен достатній публічний namespace/довший ID і визначений scope унікальності.

**S4. Seed-guard може відмовляти для дозволених коротких seed.** `seed: 's'` збігається з багатьма source ID; нормалізація деяких рядків дає порожній текст. Серверні randomBytes-seed не мають цієї проблеми, але public API фабрики приймає довільний string. Потрібен явний контракт seed для production і тестів; guard не повинен замінювати політику секретів.

**S5. Безпека seed на повному життєвому циклі ще не доведена.** Не виконано окремий аудит доступу до backup, журналів, admin/DEV endpoints, telemetry, source maps, error responses, чужих героїв, reconnect/resync та старих збережень. Наявні тести не слід описувати як покриття всіх цих каналів.

**S6. Вибір джерела/індексу клієнтом може створити oracle.** Потрібно перевірити, що користувач не може перебирати sourceId/n/serial/seed, робити безкоштовний preview або відмовлятися від невигідного результату з повторним roll. Це план перевірки, а не підтверджений експлойт.

## 7. Додатковий обов'язковий checklist

Позначка [ ] означає, що критерій ще не підтверджений цим аудитом у повному обсязі, навіть якщо часткові тести вже є.

### A. Ідентичність і атомарна видача

- [ ] F1–F3 мають постійні регресійні тести й виправлення.
- [ ] Одне джерело + одна логічна видача + той самий контент повертають ті самі токени після reload/retry.
- [ ] Два різні джерела/герої/нагороди не мають однакових token ID.
- [ ] Повторний commandId, подвійний клік, timeout і повтор WS-команди не дублюють нагороду або списання.
- [ ] Два паралельні запити на одну нагороду мають лише один успішний commit.
- [ ] Повна сумка, перевищення ваги, stale revision або помилка БД не втрачають контейнер, монети чи токен.
- [ ] sell → buyback → buy, list → unlist, bag ↔ stash ↔ equip, pickup і reconnect зберігають токен побітово, включно з ID.
- [ ] Для unique atomically перевіряються/змінюються ownedUniques і фактична видача. Визначена семантика: «колись отримував» чи «володіє зараз», особливо після продажу/передачі.

### B. Секретність та захист від передбачення

- [ ] Production без секрету/готового токена відмовляє; немає fallback на hero ID, час, map ID або публічний battle seed.
- [ ] HTTP, WS, reconnect, snapshots, errors і логи не розкривають seed, RNG state/counter, таблиці та прихований вміст до дозволеного моменту.
- [ ] Неавторизований користувач і власник іншого героя не можуть прочитати source state або змінити seed/serial/n.
- [ ] DEV_GRANT, token overrides і fixtures недоступні в production за всіх конфігурацій запуску.
- [ ] Публічні мапа, battle ID, імена/ціни вже виданих токенів і серія запитів не дають відтворити наступний лут; перевіряти відомі способи відновлення, не вимагати «нуль випадкових збігів».
- [ ] Loot streams відділені від публічної генерації геометрії/ініціативи та інших механік; зміна публічного RNG не змінює прихований лут.
- [ ] Перезапуск сервера, втрата відповіді й reconnect не дають безкоштовного reroll.
- [ ] Визначена політика створення, збереження та ротації секретів; ротація не перегенеровує вже створені предмети.
- [ ] Криптографічну конструкцію RNG та кодування її вхідних частин окремо переглянуто; SHA-256 і статистичні тести самі по собі не є повним security review.

### C. Незалежність і розширення

- [ ] Є headless-тест генерації для shop, quest, boss reward та довільного нового адаптера без MapRegistry/browser/DB.
- [ ] Новий тип додається через погоджений контентний контракт і проходить generate → inventory → equip/use → persist → project без прихованого key-switch.
- [ ] Новий атрибут має валідацію, опис, реалізацію ефекту та тест; `implemented: false` не потрапляє у звичайний лут.
- [ ] Заміна name/sprite-компонента не змінює price/attributes/skills для того самого токена.
- [ ] Один custom registry/factory використовується всіма адаптерами; singleton не підміняє конфігурацію типовим контентом.
- [ ] Фабрика не змінює вхідний контекст/контент; отримані з registry об'єкти не дають непомітно змінити поведінку вже створеної фабрики.

### D. Валідація й стійкість

- [ ] F4–F6 мають регресії; malformed контент не викликає stack overflow чи неконтрольований runtime exception.
- [ ] Property-based/fuzz: порожні пули, відсутній realm/type, дублі, невідомі ключі, великі числа, NaN/Infinity, крайні індекси, довгі рядки.
- [ ] Є ліміти кількості правил/нагород і розміру контенту; перевірена вартість масової генерації й токенізації amount N.
- [ ] Fraction math точна в дозволеному діапазоні, сума шансів ≤ 1; owned unique не перерозподіляє шанси всупереч правилу гри.
- [ ] Порожній пул допустимих атрибутів, фіксовані + rolled атрибути та виключення не створюють дублікати.
- [ ] Відсутній спрайт дає fallback; відсутня локалізація виявляється при перевірці контенту, до відкриття інвентарю користувачем.

### E. Збереження, версії та баланс

- [ ] Існуючий токен не перераховується при зміні слів, цін, ваг, спрайтів чи generatorVersion.
- [ ] Replay старої команди після релізу або бере збережений результат, або використовує явно підтримувану версію генератора/контенту.
- [ ] Міграція ідемпотентна; не дублює/не стирає токени, unique ownership і нагороди, зокрема у старих battle/snapshot-документах.
- [ ] Нові типи/атрибути не змінюють неочікувано розподіл інших характеристик; golden-зміни переглянуті разом із version policy.
- [ ] Статистика price/type/attributes/unique chance перевіряється на багатьох seed із наперед заданою толерантністю.
- [ ] Контентні ціни й знижки не створюють циклу buy/sell/deal з прибутком, якщо це заборонено правилами; правило D4 не змінюється мовчки.

## 8. Порядок закриття та критерій готовності

1. Закрити F1–F3: єдиний контракт ідентичності, глобальний scope, регресії та сумісність із наявними токенами.
2. Закрити S1 і перевірити S6: production-видача без передбачуваного fallback, сервер володіє параметрами roll.
3. Закрити F4–F6: валідований контент і передбачуваний контракт відмов; забезпечити ліміти атрибутів за авторитетним рівнем джерела з §5.1 для всіх шляхів генерації.
4. Завершити unique-видачу, ownership і конкурентну транзакційну перевірку.
5. Завершити контракт типу предмета та LG5d після рішень щодо слотів/блоку/зносу. Не приймати ці ігрові рішення в межах аудиту.
6. Запустити checklist для кожного адаптера, потім відповідні API та browser E2E через `sh scripts/pre-push-e2e.sh <spec>`.

Генератор можна називати готовим до повторного використання, коли: підтверджені дефекти закриті; кожне production-джерело використовує серверний секрет або вже створений токен; ідентичність зберігається між героями й операціями; повтори/конкуренція атомарні; новий адаптер проходить однаковий набір контрактних тестів; публічні проєкції не містять прихованих даних; replay і міграції мають зафіксовану політику. Невиконані пункти мають бути явно прийнятими обмеженнями, а не прихованими припущеннями.
