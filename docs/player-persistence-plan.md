# Збереження гравця на сервері → пентест → кооп → реліз (специфікація для Claude Code)

> Гра: **Path of Will** (репозиторій `hexoflat`).
> Гілку створює Олег. **Не комітити**, Олег комітить сам. Одна фаза = один чат.
> Скіли, які треба прочитати перед роботою: `hexoflat-phase`, `hexoflat-engine`, `hexoflat-web-state`, `hexoflat-e2e`.
> План складено без свіжого перегляду коду. Усі назви файлів і полів нижче — припущення, які **D0 має звірити** з репозиторієм. Якщо щось не збігається, спершу повідом Олега, а не підганяй код під план.

## 0. Мета

Будь-який гравець має чесний, захищений, серверний запис свого прогресу: інвентар, монети, Воля, навички, карти, експедиції. Цей запис:

- не можна накрутити з клієнта;
- легко розширюється новими видами прогресу без переробки БД;
- переживає зміни контенту;
- готовий до кооперативу й до ролі Creator.

Кінцева ціль дорожньої карти: **публічна онлайн-гра на веб-хостингу для будь-якого гравця**, після пентесту й закритого приймального тестування (Олег + друзі).

## 2. Архітектура одним екраном

```
client (Vue)                    apps/api (NestJS, WS gateway)                    Postgres
────────────                    ───────────────────────────────                    ────────
command envelope  ──►  auth (JWT) → active-session check → hero ownership
                       → Zod(envelope + payload, strict) → rate limit
                       → idempotency (command_id)
                       → load aggregate (+ upcast + content migration)
                       → engine.applyCommand(state, cmd, ctx{content, rng})  (pure)
                       → TX: UPDATE aggregate WHERE revision = expected
                             INSERT command_journal, item_ledger
                  ◄──  events + projected state + new revision
```

Принципи:

1. **Клієнт надсилає команди, ніколи стан.** Ендпоінта на кшталт «збережи мій інвентар» немає й не буде.
2. **Сервер виконує той самий `packages/engine`.** Правила живуть лише в engine. API — тільки оркестрація, сховище й безпека.
3. **Агрегат = одиниця атомарності** з власним `revision` (оптимістичне блокування).
4. **Стан агрегату — JSONB-документ** зі `schemaVersion` і `contentVersion`, валідований Zod. Новий вид прогресу = новий агрегат або нове поле + апкастер. Таблиці при цьому не змінюються.
5. **Журнал команд (append-only)** дає ідемпотентність, аудит, пошук читів, реплей і відкат.

## 3. Модель даних (Drizzle)

> Якщо таблиці `users` / `heroes` уже є, розширюємо їх, а не створюємо паралельні.

```ts
accounts            // існуюча таблиця користувачів
  id uuid pk, login text unique, password_hash text, created_at, deleted_at null
  // email: необов'язковий, лише для дорослого/батьківського акаунта (не в D1)

account_roles
  account_id fk, role enum('player','creator','admin'), granted_at, granted_by
  pk(account_id, role)

auth_sessions       // refresh-токени, відкликання, одна активна ігрова сесія
  id uuid pk, account_id fk, refresh_hash text, created_at, expires_at, revoked_at null,
  user_agent text null

heroes
  id uuid pk, account_id fk (index, НЕ unique), name text, created_at,
  deleted_at null, is_sandbox boolean default false   // пісочниця Creator, §8
  // data jsonb — після D2 лишаються лише поля профілю (ім'я, клас); решта мігрує в агрегати

hero_aggregates
  hero_id fk, kind text,                // 'inventory' | 'progress' | 'world-presence' | ...
  revision int not null,
  schema_version int not null,
  content_version text not null,
  state jsonb not null,
  server_state jsonb not null default '{}',  // серверні секрети (RNG seed), НІКОЛИ не йдуть клієнту
  updated_at timestamptz
  pk(hero_id, kind)

aggregate_snapshots // для відкату
  id bigserial, hero_id, kind, revision, state jsonb, reason text, created_at
  // робити кожні 50 ревізій + перед кожною міграцією контенту

command_journal
  id bigserial pk, command_id uuid UNIQUE, account_id, hero_id, expedition_id null,
  aggregate_kind text, command_type text, payload jsonb,
  expected_revision int, result enum('applied','rejected','conflict'),
  reason text null, events jsonb, new_revision int null, created_at
  index(hero_id, created_at)

item_ledger         // усі зміни кількості предметів, зокрема монет
  id bigserial pk, hero_id, command_id, item_key text, item_instance_id uuid null,
  delta int, balance_after int, reason text,   // 'shop_buy' | 'loot' | 'pay' | 'content_migration' ...
  created_at
  index(hero_id, item_key, created_at)
```

Ролі БД: застосунок працює під користувачем без DDL, міграції — під окремим. Необов'язково: Postgres RLS на `hero_*` за `account_id` як другий рубіж (у D1 записати як TODO; до S2 вирішити, вмикаємо чи ні).

## 4. Агрегати

### 4.1 Реєстр агрегатів (у `packages/engine`, чистий TS)

```ts
export interface IAggregateDefinition<TState> {
  kind: TAggregateKind;
  schemaVersion: number;
  schema: z.ZodType<TState>; // поточна версія, .strict()
  upcasters: Record<number, (old: unknown) => unknown>; // v → v+1
  createInitial(ctx: { content: IContentBundle }): TState;
  project(state: TState): unknown; // що бачить клієнт
  commandTypes: readonly string[]; // які команди обробляє
}
```

`AGGREGATES` — один реєстр. API нічого не знає про конкретні агрегати, крім цього реєстру. Додати новий вид прогресу = додати одне визначення + команди в engine.

### 4.2 `inventory` (D1)

- bag (клітинки), equip (слоти), stash (схованка кемпу) — **в одному агрегаті**, бо переміщення між ними атомарні (вимога Stash-специфікації).
- Кожен **неоднорідний** предмет (спорядження з рідкістю й міцністю) має `instanceId: uuid`. Однорідні стеки (`coins`, ресурси, зілля) — без `instanceId`, лише `key + amount`.
- `coins` — звичайний стековий предмет. Вагу монет визначає контент (рекомендація: дуже мала або 0, вирішить Олег у D0).

### 4.3 `progress` (D2)

Воля (`current`, `capacity`), навички й ранги, кроки розвідника, перемоги. Воля й навички вже мають `revision`, переносимо структуру як є.

### 4.4 `world-presence` (D4)

Де герой зараз: кемп, експедиція `expeditionId`, позиція. Сам світ живе в експедиції (§7).

### 4.5 Сід випадковості

`server_state.rngSeed` генерується при створенні героя. RNG для команди = `derive(rngSeed, aggregate, revision)`. Клієнт сіда не бачить, тому не може передбачити чи перекинути лут.

### 4.6 Механіка «монети в руці → гекс»

UI лишається як зараз: взяв `coins` у руку, переніс на гекс, обрав дію. Натомість клієнт надсилає команду:

```ts
{ type: 'OFFER_ITEM', payload: { itemKey: 'coins', amount: 5, targetHex, intent: 'buy' | 'pay' | 'give' } }
```

Engine перевіряє, що на цільовому гексі є об'єкт, який приймає цей `intent`: торговець, ворота з платою, NPC, інший герой (у коопі). Він сам рахує результат: списання, видачу, відмову. Перелік доступних дій для підказки в UI дає чиста функція `resolveOfferIntents(state, targetHex)`, і клієнт лише її показує. Магазин у D3 — це просто ще один тип цілі для `OFFER_ITEM` плюс вікно вибору товару.

## 5. D1 — основа збереження + інвентар (перша фаза з кодом)

### 5.1 Engine

- `AGGREGATES` + визначення `inventory` (schema v1, `createInitial` → **порожній** інвентар, `project`).
- Існуючі `GRANT_ITEM` / `CONSUME_ITEM` / переміщення в сумці й схованці працюють як `applyCommand` над агрегатом `inventory`. Якщо зараз це функції в store — перенести правила в engine (див. Stash spec §1).
- Контент: прапорець `coins` як стековий предмет. **Ніякого `starter-kit`**: якщо в коді вже є видача предметів при створенні героя — прибрати її.

### 5.2 API: конвеєр команд

- `PlayerCommandService.execute(ctx, envelope)`; envelope (Zod, `.strict()`):
  `{ commandId: uuid, heroId: uuid, aggregate: kind, expectedRevision: int, command: { type, payload } }`.
- Порядок: JWT → активна сесія героя → `hero.account_id === ctx.accountId` (accountId **лише з токена**) → Zod envelope → Zod payload конкретної команди → rate limit → ідемпотентність (якщо `command_id` уже в журналі, повернути збережений результат) → завантажити, апкастити, мігрувати контент → engine → транзакція.
- Транзакція: `UPDATE hero_aggregates SET ..., revision = revision + 1 WHERE hero_id = $1 AND kind = $2 AND revision = $expected`. 0 рядків → `REVISION_CONFLICT` + актуальний projected state. Далі в тій самій транзакції: `command_journal` і `item_ledger` (з подій `ITEM_GRANTED` / `ITEM_CONSUMED`).
- Відмови engine записуються в журнал як `rejected` (без зміни стану).
- Помилки клієнту — лише коди (`INSUFFICIENT_ITEMS`, `REVISION_CONFLICT`, `FORBIDDEN`, `RATE_LIMITED` ...), без stack trace.
- Ліміти: розмір payload (напр. 8 KB), команди на героя (напр. 20/с з burst), логін (напр. 5/хв на IP + на логін).

### 5.3 API: читання стану

`hero.snapshot` → `{ heroId, aggregates: { [kind]: { revision, state: project(state) } } }`. `server_state` у відповідь не потрапляє ніколи — додати тест.

### 5.4 Створення героя

У реєстрації / створенні героя, **в одній транзакції**: `heroes` + `hero_aggregates` для всіх зареєстрованих агрегатів через `createInitial` (порожній стан, без рядків ledger).

### 5.5 Одна активна сесія

Gateway тримає `heroId → connectionId`. Нове підключення того самого героя: старе отримує `SESSION_TAKEN_OVER` і закривається, команди зі старого з'єднання відхиляються.

### 5.6 Монети

- Прибрати `coins` з `heroes.data` і з усіх місць, що його читають (знайти в D0).
- Dev-кнопку «додати монети» перевести на команду `DEV_GRANT_ITEM`, яка дозволена лише при `NODE_ENV !== 'production'` **або** для героя з `is_sandbox = true`.

### 5.7 Web

- `hero-inventory-store` (і `hero-stash-store`, якщо є) стає **проєкцією** серверного стану: `apply(snapshot)`, `applyEvents(events, revision)`.
- Команди йдуть через один сервіс `services/player-commands.ts`, який генерує `commandId`, бере `expectedRevision` з проєкції й обробляє `REVISION_CONFLICT` (взяти стан з відповіді й показати м'яке повідомлення).
- Оптимістичні оновлення: **лише** для перетягування всередині сумки/схованки (з відкатом при відмові). Усе, що стосується монет і обміну, чекає на відповідь сервера.
- Прибрати ігровий стан інвентаря з `services/persistence/*-storage.ts` і localStorage. UI-налаштування лишаються.
- Пам'ятати клас багів з `user-store.ts`: `restoreSession()` не повинен скидати те, що скидають `login` / `register` (тепер це передусім кеш проєкцій).

### 5.8 Тести

- Vitest (engine): кожна команда, `createInitial`, апкастер v1 (тотожний), `project` не містить серверних полів.
- Vitest/інтеграція (api з тестовою БД): ідемпотентність (той самий `commandId` двічі → одна зміна), конфлікт ревізії, **паралельні команди** (10 одночасних `CONSUME_ITEM` на той самий стек не дають мінусового балансу), чужий герой → `FORBIDDEN`, невідоме поле в payload → відмова, транзакція відкочується, якщо журнал не записався, ledger сходиться з балансом.
- Playwright: новий акаунт → порожній інвентар і 0 монет; герой (через `seed-hero` або ігровий лут) отримує предмет → перемістити предмет → перезавантажити сторінку → предмет на місці; друга вкладка витісняє першу.

### 5.9 Інструменти

- `pnpm --filter api seed-hero <login> [preset]` — тестовий герой з набором (лише dev).
- `pnpm --filter api hero-history <heroId>` — показує журнал і ledger героя.
- `pnpm --filter api hero-rollback <heroId> <kind> <revision>` — відкат зі знімка (з підтвердженням; лише admin / dev).

### 5.10 Definition of done

Інвентар і монети живуть лише на сервері. Правка localStorage нічого не дає. Повторений запит не дублює зміну. Typecheck, lint, Vitest, Playwright зелені. Нічого не закомічено. Звіт Олегу українською: що змінено, як запустити міграції й тести, відкриті питання.

## 6. Зміна контенту й компенсації

- `packages/engine/src/content/migrations/` — таблиця:
  `{ fromContentVersion, retire: { [itemKey]: { replaceWith?: itemKey, compensate?: { itemKey, amount } } } }`.
- Під час завантаження агрегату з меншим `contentVersion`: зробити знімок, застосувати міграцію, записати системну команду `CONTENT_MIGRATED` у журнал і ledger, додати повідомлення «Скринька спадку» в стан гравця, щоб UI показав, що змінилося.
- Предмет з контенту можна видалити **лише** разом із записом у цій таблиці. Додати перевірку в тест контенту.

## 7. Кооператив: експедиції (D4 — соло, D5 — кооп)

- **Експедиція** (`expeditions`: `id`, `host_account_id`, `kind` (world/dungeon), `seed`, `revision`, `state jsonb`, `status`, `created_at`, `ended_at`) — спільний світ: карта, туман, вороги, лут на землі, черговість.
- `expedition_members`: `expedition_id`, `hero_id`, `joined_at`, `left_at`, `controlled_by_account_id` (для передачі керування героєм).
- Соло = експедиція з одним учасником. **D4 уже будує таблиці експедицій**, просто з одним учасником. Тоді D5 додає лише приєднання, передачу керування й синхронізацію, а модель даних не змінюється.
- Команди, що зачіпають і світ, і героя (підібрати лут, заплатити іншому героєві), змінюють обидва агрегати **в одній транзакції**. Порядок блокування фіксований (спершу експедиція, потім герої за `hero_id`), щоб не було взаємних блокувань.
- Під час гри стан експедиції тримається в пам'яті процесу API (одне джерело правди). У БД — знімок кожні N команд + журнал, тож перепідключення й відновлення після рестарту = знімок + реплей.
- Гравець виходить → його герой лишає експедицію з інвентарем і прогресом. Світ лишається хосту.
- Приєднання до чужої експедиції — **лише за кодом-запрошенням** від хоста (без публічного пошуку незнайомців на старті: гра дитяча). Чат між гравцями на старті не робимо або лише готові фрази.

## 8. Creator і AI-агент (D6–D7, у D1 лише закладаємо основу)

У D1 вже мають бути: `account_roles`, `heroes.is_sandbox`, `DEV_GRANT_ITEM` для пісочниці.

**D6 — Creator:**

- `content_drafts`: `id`, `kind` (map / quest / item / enemy / scenario), `author_account_id`, `version`, `status` (`draft → playtest → published → retired`), `body jsonb`, `validation_report`, `created_at`.
- Чернетка перевіряється тими самими Zod-схемами контенту, що й вбудований контент.
- **Пісочниця:** Creator грає чернетку героєм з `is_sandbox = true`. Предмети й монети пісочниці не можуть потрапити до звичайних героїв (окремий герой, окремі агрегати, `OFFER_ITEM` між sandbox і не-sandbox заборонений).
- Публікація = нова `contentVersion` бандла. Публікувати може лише `admin` (тобто Олег).
- Якщо D6 з'являється **після** публічного релізу, перед вмиканням ролі Creator на проді — окремий міні-пентест ролей (S4): ескалація `creator → admin`, доступ creator до даних гравців, XSS у тексті чернеток.

**D7 — AI-агент:**

- Сервісний акаунт з роллю `creator`, окремий API-токен з обмеженими правами: створювати й редагувати **лише власні чернетки**. Без доступу до даних гравців, без публікації.
- Кожна дія агента — в журналі авторства.
- Перед публікацією Олег проходить чернетку в пісочниці й публікує вручну. Для дитячої гри будь-який згенерований контент проходить людську перевірку.

### S2 — пентест (вхідна умова: S1 готовий, D0–D4 зелені)

Обсяг (на основі OWASP ASVS рівня 2 + ігрові атаки):

- **Auth:** брутфорс і rate limit, перевикористання refresh, фіксація сесії, вихід і відкликання, витіснення сесії.
- **Доступ (IDOR):** чужий `heroId` / `expeditionId` у кожній команді й запиті, ролі `player → creator/admin`.
- **Ігрова економіка:** повтор команди (replay), гонки паралельних команд (подвійна витрата монет), від'ємні та величезні `amount`, предмети, яких немає в контенті, обхід ціни, перепродаж з прибутком, переповнення стеку.
- **Ввід:** ін'єкції (SQL через JSONB-запити), XSS в імені героя та будь-якому тексті гравця, надвеликі payload, кривий JSON у WS.
- **Витоки:** `server_state` / сід, stack trace, чужі дані у відповідях, дані в логах.
- **Доступність:** флуд WS-з'єднань і команд.
- Формат: спершу власний прохід (скриптові атаки в окремому наборі тестів `apps/api/test/security/` + OWASP ZAP), потім за бажанням — зовнішній фахівець.
- Результат: звіт `docs/security/pentest-S2.md` (знахідка → ризик → виправлення → регресійний тест). Кожна знахідка закривається тестом, щоб не повернулася.
- **Вихідна умова:** немає відкритих критичних і високих знахідок.

### S3 — доповнювальний пентест коопу (після D5)

Кооп відкриває нові поверхні атаки, тому окремий короткий прохід: приєднання без запрошення, керування чужим героєм, передача предметів між героями (дюп через гонку), підміна черговості, витік чужого інвентаря через стан експедиції, флуд від одного учасника.

## 12. Реліз: R1 закрита бета → R2 публічний реліз

### R1 — приймальне тестування (Олег + друзі)

- Той самий staging або окремий `beta`, доступ **лише за інвайт-кодами** (`invites`: код, хто створив, скільки використань, строк).

- **Вихідна умова:** немає блокерів, Олег підтверджує готовність. Рішення: скидати прогрес бета-тестерів перед R2 чи ні.

### R2 — публічний реліз

Тут відновлюються Фази 11–12 повністю:

- Вибір хостингу (рішення Олега), домен, TLS, автоматичні бекапи БД з **перевіреним відновленням**, план відкату релізу.
- Моніторинг (помилки, навантаження, аномалії економіки), алерти.
- Обов'язково перед відкриттям: політика конфіденційності й умови, експорт і видалення акаунта, строки зберігання даних, юридична перевірка вимог для дітей у цільових країнах.
- Реєстрація відкрита для всіх; кооп — за кодами-запрошеннями між гравцями.

### D0.2 Серверна основа (що вже є)

- **Таблиці Drizzle** (`apps/api/src/db/schema.ts`): `users` (username, password, name, tokenVersion), `heroes` (`userId` → users, `data jsonb`), `campaigns`, `scenarios`, `saves`, `snapshots`. - **Auth:** `bcryptjs` (не argon2id), один access-JWT (`jwt.env.ts`, `expiresIn` з env), **refresh-токенів і `auth_sessions` немає**; відкликання через `users.tokenVersion` (logout збільшує). `@fastify/cookie` і `helmet` підключені, httpOnly-refresh немає. Rate limit на auth — `@nestjs/throttler`.
- **Герой:** `GET /heroes/me` ліниво створює героя (`findOrCreateByUserId`); `findByUserId` бере `limit(1)` — один герой на користувача **захардкоджено**.
- **WS gateway** (`game.gateway.ts`, socket.io): JWT у `handshake.auth.token`, події `join-scenario` / `command`; перевірка власника сценарію, ліміт 10 команд/с на сокет, Zod `HEX_ENGINE_COMMAND_SCHEMAS`, `commandRefusal` (HERO_SCOPED команди мусять мати `heroId` = керований герой; `GRANT_ITEM`/`CONSUME_ITEM` — SERVER_ONLY). Стан кімнати тримається в `ScenarioStateService.rooms` (пам'ять) + автозбереження кожні 30 с у `snapshots`.

### D0.3 Де виконуються інвентарні команди

Правила вже в engine: `packages/engine/src/inventory/` (`MOVE_ITEM`, `AUTO_PLACE_ITEM`, `STORE_RESOURCES`, `SORT_STASH`, `UNLOCK_STASH_CHEST`, `GRANT_ITEM`, `CONSUME_ITEM`, подія `INVENTORY_CHANGED`, `InventoryState` зі своїм `revision`, схема `inventoryStateSchema`). ### D0.5 «Монети в руці → гекс»

Монети — предмет, який лягає в руку (`hand-tools.ts: toolKeyOfItem(COINS)`), і сьогодні мають одну механіку: **розблокування скрині схованки** (`UNLOCK_STASH_CHEST`: 100, потім 1000; платяться з монет у руці, решта лишається). Торговців, воріт з платою, `OFFER_ITEM` ще немає — це D3.

### D0.6 Що отримує новий герой сьогодні

- **API:** `starterHeroData()`: 3/3 здоров'я, attack 1, defense 1, coins 0, kills 0, energy 100/100.
- **Інвентар (web/engine):** `createInitial` в `inventory-state.ts` кладе у першу (заблоковану) скриню `STARTER_STASH_ITEMS` = меч, сокира, щит, кирка (`starterGiven`) **і ще 50 Return Scroll** (`STARTER_SCROLL_COUNT`, `grantStarterGear`). Це суперечить §1.3а («порожньо»): рішення Олега потрібне — прибрати і сувої теж? (див. питання нижче).
- **Воля:** старт 20, ємність 50 — у `KNOWLEDGE_RULES` (`knowledge/math.ts`), тобто вже в engine-контенті, захардкоджених значень в API немає.
- **«Рука»:** `HEXOBJECT_KEYS.HAND` — це **інструмент** (`tools.content.ts`, `HERO_TOOL_TYPE.HAND`), який герой тримає за замовчуванням, а не предмет у сумці/екіпіровці: `toolKeyOfItem` повертає `HAND` для порожньої руки. Зробити «руку» неінвентарною не потрібно, лише перевірити в D1 тестом, що `createInitial` не кладе `hand` у `bag/equip/stash`.

### D0.7 Джерела предметів і монет

Прогрес з нуля без dev-кнопок **зараз неможливий для монет**: єдине джерело монет — dev-кнопка в налаштуваннях (плюс `COINS` як hexobject на карті, але в camp-малюнку його прибрано, див. CLAUDE.md). Тому без першого легального джерела монет скриню не розблокувати, а в ній старе спорядження (меч, сокира, щит, кирка), без якого вести бої/добування неможливо. Предмети є з: збирання ресурсів (дерево/камінь через сокиру/кирку), лут/скрині на підземних картах, Книга Волі (лише Воля). **Блокер для §1.3а:** при порожньому старті гравець без монет не отримає жодного знаряддя. Рішення в «Питаннях» нижче.

### D0.8 Розбіжності з планом і питання до Олега

### Пропозиції до плану

**P1. Розвести «зберігання» і «захист від читів».** Зараз D1–D4 змішують два завдання. Для закритої бети з друзями довіри достатньо: потрібне надійне зберігання й відновлення, а не повна серверна авторитетність кожного ходу. Тому: **D1 = універсальне сховище агрегатів + журнал + конвеєр команд**, а перенесення кожного виду прогресу (D2, D4) може йти спершу як «сервер перевіряє схему й інваріанти та зберігає», і лише потім — як «сервер виконує правила». Пентест S2 тоді потрібен **перед R2 (публічним)**, а не перед R1.

**P2. Віха «Усі дані героя в БД» = завершення D4 (соло-експедиції).** Після D1 в БД інвентар і монети, після D2 — Воля, навички, здоров'я, після D4 — карти, туман, позиція, бої. Тільки D4 закриває потребу «закрити вкладку, відкрити на іншому пристрої — все на місці». D0–D2 — це чверть шляху; монети й предмети там, але світ ще ні.

**P3. Мінімальна віха для друзів (R1-lite) може стояти одразу після D4 + урізаного S1** (staging з TLS, секрети, бекап БД, Origin-перевірка, інвайт-коди), **до** повного пентесту. Умова: тестери відомі, прогрес не виставляється як змагальний. Повний S1+S2+S3 — перед публічним R2. Це скорочує шлях до живих тестерів на дві великі фази.

**P4. D4 розбити.** Це найважча фаза (карти генеруються на клієнті, стан карти + знімок бою зараз пишуться в localStorage). Пропозиція: **D4a** — серверний «блоб-стан» експедиції (карта + стан, checksum, ревізія, зберігання в БД, генерація на сервері тим самим engine), **D4b** — авторитетне виконання команд руху/дій на сервері, **D4c** — `world-presence` + повернення порталом. D4a сам по собі дає віху P2.

**P5. Генерація на сервері вимагає детермінованого seed.** План уже має `rngSeed`; додати: карти й бої генеруються з `seed`, збереженого в `expeditions.seed`, щоб реплей і відновлення після рестарту були байт-в-байт однакові (інакше знімок + реплей з §7 не зійдеться).

**P6. Вимкнути localStorage-стан за прапором, а не видаляти одразу.** У D1–D2 зберегти старі `*-storage.ts` за `VITE_LEGACY_LOCAL_STATE` для відкату до завершення D4, потім видалити в D4c.

**P7. Тести економіки готувати з D1.** Перенести `10 одночасних CONSUME_ITEM` у спільну інтеграційну фікстуру і потім розширювати для S2, а не писати з нуля перед пентестом.

### Відповіді O1–O3 (2026-11-09)

- **O1.** `createInitial` = порожній інвентар, 0 монет, Воля 20. Перша скриня кемпу — об'єкт у кемпі, який герой відкриває сам: безкоштовно, один раз; вміст — меч, сокира, щит, кирка. До D4b сервер перевіряє: достатньо Волі, крок на сусідній гекс від збереженої позиції, предмет існує в контенті, лут має `lootId` від серверного seed і підбирається лише раз. **Відома прогалина, прийнятна до R1, обов'язкова до R2:** повна перевірка світу (досяжність, стан гексів, вороги) — лише в D4b.

**Наслідки для D1/D2, які треба врахувати:**

1. `claimedRewards` живе в `progress`, а `progress` за планом з'являється в D2. Тому D1 створює **мінімальний `progress` v1** (лише `claimedRewards`), D2 його розширює апкастером.
2. `CLAIM_CAMP_CHEST` змінює два агрегати (`inventory` + `progress`) в одній транзакції; конвеєр §5.2 розрахований на один агрегат, тож D1 має підтримати команду з кількома агрегатами (порядок блокування за `kind`).
3. Перевірка «`lootId` від серверного seed» у D2 вимагає, щоб сервер знав, який лут існує. До D4a карта лишається на клієнті, тому в D2 сервер може лише (а) видавати `lootId` детерміновано з `rngSeed` + координат + ревізії карти і (б) фіксувати вже підібрані `lootId` (один раз). Повна відповідність «лут справді лежить на цьому гексі» — D4b.
4. Dev-кнопка монет (`DEV_GRANT_ITEM`) і `seed-hero` лишаються єдиним способом отримати монети до D3.

## Результати D2 (2026-11-09)

**Зроблено.** Воля, навички, кроки й присутність героя живуть на сервері в агрегаті `progress` v2 (`claimedRewards`, `knowledge`, `presence`, `steps`). Старий `progress` v1 піднімається апкастером (`upcastAggregate` тепер отримує `{ heroId }`).

- **Engine** (`aggregates/execute-progress-command.ts`): серверні команди `KNOWLEDGE` (крок, Книга Волі: start/answer/next/open), `SACRIFICE_TO_SKILL`, `RESET_SKILLS`, `ARRIVE`, `SPEND_WILL` і dev-фікстури `DEV_GRANT_WILL`, `DEV_SET_KNOWLEDGE`. Контекст знання (`serverKnowledgeContext`) будує сервер із того, де герой стояв: зона Волі береться з локації, «біля Книги» з відомого гекса Книги в кемпі (`CAMP_BOOK_HEX`), бій і рух сервер вважає вимкненими, тож крок може лише коштувати більше, не менше. Крок має бути на сусідній гекс від збереженої позиції. `SPEND_WILL` бере ціну дії з `willCost` контенту (лише там, де локація бере Волю), ціну порталу з навички Teleport; клієнтський `cost` ігнорується.
- **API:** без змін у конвеєрі, окрім правила ревізій `PLAYER_COMMAND_REVISION` (`aggregate` / `knowledge` / `none`) і `asAggregates`, що не вимагає інвентаря для команд прогресу.
- **Web:** `sendProgress` / `ensurePresence` / `pushKnowledgeFixture` в `services/inventory/inventory-sync.ts`; `knowledge-controller.ts` шле команди на сервер і чекає відповідь (Воля не передбачається локально). Дії та портал спершу виконуються локально на копії, потім сервер списує Волю (`SPEND_WILL`) і його відповідь стає правдою. Крок тепер завжди йде через сервер (і в кемпі, де він безкоштовний). `localStorage` для Волі прибрано; лишилась тільки чиста `recoverStepPosition` (`services/knowledge/step-recovery.ts`). Для юніт-тестів є фейковий сервер на справжніх правилах engine (`src/test-support/fake-player-server.ts`, `fake-session.ts`).
