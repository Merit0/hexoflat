# Збереження гравця на сервері → пентест → кооп → реліз (специфікація для Claude Code)

> Гра: **Path of Will** (репозиторій `hexoflat`).
> Гілку створює Олег. **Не комітити**, Олег комітить сам. Одна фаза = один чат.
> Скіли, які треба прочитати перед роботою: `hexoflat-phase`, `hexoflat-engine`, `hexoflat-web-state`, `hexoflat-e2e`.
> План складено без свіжого перегляду коду. Усі назви файлів і полів нижче — припущення, які **D0 має звірити** з репозиторієм. Якщо щось не збігається, спершу повідом Олега, а не підганяй код під план.

## 0. Мета

Будь-який гравець має чесний, захищений, серверний запис свого прогресу: інвентар, монети, Воля, навички, карти, експедиції. Цей запис:

- не можна накрутити з клієнта;
- легко розширюється новими видами прогресу без переробки БД;
- переживає зміни контенту;
- готовий до кооперативу й до ролі Creator.

Кінцева ціль дорожньої карти: **публічна онлайн-гра на веб-хостингу для будь-якого гравця**, після пентесту й закритого приймального тестування (Олег + друзі).

## 2. Архітектура одним екраном

```
client (Vue)                    apps/api (NestJS, WS gateway)                    Postgres
────────────                    ───────────────────────────────                    ────────
command envelope  ──►  auth (JWT) → active-session check → hero ownership
                       → Zod(envelope + payload, strict) → rate limit
                       → idempotency (command_id)
                       → load aggregate (+ upcast + content migration)
                       → engine.applyCommand(state, cmd, ctx{content, rng})  (pure)
                       → TX: UPDATE aggregate WHERE revision = expected
                             INSERT command_journal, item_ledger
                  ◄──  events + projected state + new revision
```

Принципи:

1. **Клієнт надсилає команди, ніколи стан.** Ендпоінта на кшталт «збережи мій інвентар» немає й не буде.
2. **Сервер виконує той самий `packages/engine`.** Правила живуть лише в engine. API — тільки оркестрація, сховище й безпека.
3. **Агрегат = одиниця атомарності** з власним `revision` (оптимістичне блокування).
4. **Стан агрегату — JSONB-документ** зі `schemaVersion` і `contentVersion`, валідований Zod. Новий вид прогресу = новий агрегат або нове поле + апкастер. Таблиці при цьому не змінюються.
5. **Журнал команд (append-only)** дає ідемпотентність, аудит, пошук читів, реплей і відкат.

## 3. Модель даних (Drizzle)

> Якщо таблиці `users` / `heroes` уже є, розширюємо їх, а не створюємо паралельні.

```ts
accounts            // існуюча таблиця користувачів
  id uuid pk, login text unique, password_hash text, created_at, deleted_at null
  // email: необов'язковий, лише для дорослого/батьківського акаунта (не в D1)

account_roles
  account_id fk, role enum('player','creator','admin'), granted_at, granted_by
  pk(account_id, role)

auth_sessions       // refresh-токени, відкликання, одна активна ігрова сесія
  id uuid pk, account_id fk, refresh_hash text, created_at, expires_at, revoked_at null,
  user_agent text null

heroes
  id uuid pk, account_id fk (index, НЕ unique), name text, created_at,
  deleted_at null, is_sandbox boolean default false   // пісочниця Creator, §8
  // data jsonb — після D2 лишаються лише поля профілю (ім'я, клас); решта мігрує в агрегати

hero_aggregates
  hero_id fk, kind text,                // 'inventory' | 'progress' | 'world-presence' | ...
  revision int not null,
  schema_version int not null,
  content_version text not null,
  state jsonb not null,
  server_state jsonb not null default '{}',  // серверні секрети (RNG seed), НІКОЛИ не йдуть клієнту
  updated_at timestamptz
  pk(hero_id, kind)

aggregate_snapshots // для відкату
  id bigserial, hero_id, kind, revision, state jsonb, reason text, created_at
  // робити кожні 50 ревізій + перед кожною міграцією контенту

command_journal
  id bigserial pk, command_id uuid UNIQUE, account_id, hero_id, expedition_id null,
  aggregate_kind text, command_type text, payload jsonb,
  expected_revision int, result enum('applied','rejected','conflict'),
  reason text null, events jsonb, new_revision int null, created_at
  index(hero_id, created_at)

item_ledger         // усі зміни кількості предметів, зокрема монет
  id bigserial pk, hero_id, command_id, item_key text, item_instance_id uuid null,
  delta int, balance_after int, reason text,   // 'shop_buy' | 'loot' | 'pay' | 'content_migration' ...
  created_at
  index(hero_id, item_key, created_at)
```

Ролі БД: застосунок працює під користувачем без DDL, міграції — під окремим. Необов'язково: Postgres RLS на `hero_*` за `account_id` як другий рубіж (у D1 записати як TODO; до S2 вирішити, вмикаємо чи ні).

## 4. Агрегати

### 4.1 Реєстр агрегатів (у `packages/engine`, чистий TS)

```ts
export interface IAggregateDefinition<TState> {
  kind: TAggregateKind;
  schemaVersion: number;
  schema: z.ZodType<TState>; // поточна версія, .strict()
  upcasters: Record<number, (old: unknown) => unknown>; // v → v+1
  createInitial(ctx: { content: IContentBundle }): TState;
  project(state: TState): unknown; // що бачить клієнт
  commandTypes: readonly string[]; // які команди обробляє
}
```

`AGGREGATES` — один реєстр. API нічого не знає про конкретні агрегати, крім цього реєстру. Додати новий вид прогресу = додати одне визначення + команди в engine.

### 4.2 `inventory` (D1)

- bag (клітинки), equip (слоти), stash (схованка кемпу) — **в одному агрегаті**, бо переміщення між ними атомарні (вимога Stash-специфікації).
- Кожен **неоднорідний** предмет (спорядження з рідкістю й міцністю) має `instanceId: uuid`. Однорідні стеки (`coins`, ресурси, зілля) — без `instanceId`, лише `key + amount`.
- `coins` — звичайний стековий предмет. Вагу монет визначає контент (рекомендація: дуже мала або 0, вирішить Олег у D0).

### 4.3 `progress` (D2)

Воля (`current`, `capacity`), навички й ранги, кроки розвідника, перемоги. Воля й навички вже мають `revision`, переносимо структуру як є.

### 4.4 `world-presence` (D4)

Де герой зараз: кемп, експедиція `expeditionId`, позиція. Сам світ живе в експедиції (§7).

### 4.5 Сід випадковості

`server_state.rngSeed` генерується при створенні героя. RNG для команди = `derive(rngSeed, aggregate, revision)`. Клієнт сіда не бачить, тому не може передбачити чи перекинути лут.

### 4.6 Механіка «монети в руці → гекс»

UI лишається як зараз: взяв `coins` у руку, переніс на гекс, обрав дію. Натомість клієнт надсилає команду:

```ts
{ type: 'OFFER_ITEM', payload: { itemKey: 'coins', amount: 5, targetHex, intent: 'buy' | 'pay' | 'give' } }
```

Engine перевіряє, що на цільовому гексі є об'єкт, який приймає цей `intent`: торговець, ворота з платою, NPC, інший герой (у коопі). Він сам рахує результат: списання, видачу, відмову. Перелік доступних дій для підказки в UI дає чиста функція `resolveOfferIntents(state, targetHex)`, і клієнт лише її показує. Магазин у D3 — це просто ще один тип цілі для `OFFER_ITEM` плюс вікно вибору товару.

## 5. D1 — основа збереження + інвентар (перша фаза з кодом)

### 5.1 Engine

- `AGGREGATES` + визначення `inventory` (schema v1, `createInitial` → **порожній** інвентар, `project`).
- Існуючі `GRANT_ITEM` / `CONSUME_ITEM` / переміщення в сумці й схованці працюють як `applyCommand` над агрегатом `inventory`. Якщо зараз це функції в store — перенести правила в engine (див. Stash spec §1).
- Контент: прапорець `coins` як стековий предмет. **Ніякого `starter-kit`**: якщо в коді вже є видача предметів при створенні героя — прибрати її.

### 5.2 API: конвеєр команд

- `PlayerCommandService.execute(ctx, envelope)`; envelope (Zod, `.strict()`):
  `{ commandId: uuid, heroId: uuid, aggregate: kind, expectedRevision: int, command: { type, payload } }`.
- Порядок: JWT → активна сесія героя → `hero.account_id === ctx.accountId` (accountId **лише з токена**) → Zod envelope → Zod payload конкретної команди → rate limit → ідемпотентність (якщо `command_id` уже в журналі, повернути збережений результат) → завантажити, апкастити, мігрувати контент → engine → транзакція.
- Транзакція: `UPDATE hero_aggregates SET ..., revision = revision + 1 WHERE hero_id = $1 AND kind = $2 AND revision = $expected`. 0 рядків → `REVISION_CONFLICT` + актуальний projected state. Далі в тій самій транзакції: `command_journal` і `item_ledger` (з подій `ITEM_GRANTED` / `ITEM_CONSUMED`).
- Відмови engine записуються в журнал як `rejected` (без зміни стану).
- Помилки клієнту — лише коди (`INSUFFICIENT_ITEMS`, `REVISION_CONFLICT`, `FORBIDDEN`, `RATE_LIMITED` ...), без stack trace.
- Ліміти: розмір payload (напр. 8 KB), команди на героя (напр. 20/с з burst), логін (напр. 5/хв на IP + на логін).

### 5.3 API: читання стану

`hero.snapshot` → `{ heroId, aggregates: { [kind]: { revision, state: project(state) } } }`. `server_state` у відповідь не потрапляє ніколи — додати тест.

### 5.4 Створення героя

У реєстрації / створенні героя, **в одній транзакції**: `heroes` + `hero_aggregates` для всіх зареєстрованих агрегатів через `createInitial` (порожній стан, без рядків ledger).

### 5.5 Одна активна сесія

Gateway тримає `heroId → connectionId`. Нове підключення того самого героя: старе отримує `SESSION_TAKEN_OVER` і закривається, команди зі старого з'єднання відхиляються.

### 5.6 Монети

- Прибрати `coins` з `heroes.data` і з усіх місць, що його читають (знайти в D0).
- Dev-кнопку «додати монети» перевести на команду `DEV_GRANT_ITEM`, яка дозволена лише при `NODE_ENV !== 'production'` **або** для героя з `is_sandbox = true`.

### 5.7 Web

- `hero-inventory-store` (і `hero-stash-store`, якщо є) стає **проєкцією** серверного стану: `apply(snapshot)`, `applyEvents(events, revision)`.
- Команди йдуть через один сервіс `services/player-commands.ts`, який генерує `commandId`, бере `expectedRevision` з проєкції й обробляє `REVISION_CONFLICT` (взяти стан з відповіді й показати м'яке повідомлення).
- Оптимістичні оновлення: **лише** для перетягування всередині сумки/схованки (з відкатом при відмові). Усе, що стосується монет і обміну, чекає на відповідь сервера.
- Прибрати ігровий стан інвентаря з `services/persistence/*-storage.ts` і localStorage. UI-налаштування лишаються.
- Пам'ятати клас багів з `user-store.ts`: `restoreSession()` не повинен скидати те, що скидають `login` / `register` (тепер це передусім кеш проєкцій).

### 5.8 Тести

- Vitest (engine): кожна команда, `createInitial`, апкастер v1 (тотожний), `project` не містить серверних полів.
- Vitest/інтеграція (api з тестовою БД): ідемпотентність (той самий `commandId` двічі → одна зміна), конфлікт ревізії, **паралельні команди** (10 одночасних `CONSUME_ITEM` на той самий стек не дають мінусового балансу), чужий герой → `FORBIDDEN`, невідоме поле в payload → відмова, транзакція відкочується, якщо журнал не записався, ledger сходиться з балансом.
- Playwright: новий акаунт → порожній інвентар і 0 монет; герой (через `seed-hero` або ігровий лут) отримує предмет → перемістити предмет → перезавантажити сторінку → предмет на місці; друга вкладка витісняє першу.

### 5.9 Інструменти

- `pnpm --filter api seed-hero <login> [preset]` — тестовий герой з набором (лише dev).
- `pnpm --filter api hero-history <heroId>` — показує журнал і ledger героя.
- `pnpm --filter api hero-rollback <heroId> <kind> <revision>` — відкат зі знімка (з підтвердженням; лише admin / dev).

### 5.10 Definition of done

Інвентар і монети живуть лише на сервері. Правка localStorage нічого не дає. Повторений запит не дублює зміну. Typecheck, lint, Vitest, Playwright зелені. Нічого не закомічено. Звіт Олегу українською: що змінено, як запустити міграції й тести, відкриті питання.

## 6. Зміна контенту й компенсації

- `packages/engine/src/content/migrations/` — таблиця:
  `{ fromContentVersion, retire: { [itemKey]: { replaceWith?: itemKey, compensate?: { itemKey, amount } } } }`.
- Під час завантаження агрегату з меншим `contentVersion`: зробити знімок, застосувати міграцію, записати системну команду `CONTENT_MIGRATED` у журнал і ledger, додати повідомлення «Скринька спадку» в стан гравця, щоб UI показав, що змінилося.
- Предмет з контенту можна видалити **лише** разом із записом у цій таблиці. Додати перевірку в тест контенту.

## 7. Кооператив: експедиції (D4 — соло, D5 — кооп)

- **Експедиція** (`expeditions`: `id`, `host_account_id`, `kind` (world/dungeon), `seed`, `revision`, `state jsonb`, `status`, `created_at`, `ended_at`) — спільний світ: карта, туман, вороги, лут на землі, черговість.
- `expedition_members`: `expedition_id`, `hero_id`, `joined_at`, `left_at`, `controlled_by_account_id` (для передачі керування героєм).
- Соло = експедиція з одним учасником. **D4 уже будує таблиці експедицій**, просто з одним учасником. Тоді D5 додає лише приєднання, передачу керування й синхронізацію, а модель даних не змінюється.
- Команди, що зачіпають і світ, і героя (підібрати лут, заплатити іншому героєві), змінюють обидва агрегати **в одній транзакції**. Порядок блокування фіксований (спершу експедиція, потім герої за `hero_id`), щоб не було взаємних блокувань.
- Під час гри стан експедиції тримається в пам'яті процесу API (одне джерело правди). У БД — знімок кожні N команд + журнал, тож перепідключення й відновлення після рестарту = знімок + реплей.
- Гравець виходить → його герой лишає експедицію з інвентарем і прогресом. Світ лишається хосту.
- Приєднання до чужої експедиції — **лише за кодом-запрошенням** від хоста (без публічного пошуку незнайомців на старті: гра дитяча). Чат між гравцями на старті не робимо або лише готові фрази.

## 8. Creator і AI-агент (D6–D7, у D1 лише закладаємо основу)

У D1 вже мають бути: `account_roles`, `heroes.is_sandbox`, `DEV_GRANT_ITEM` для пісочниці.

**D6 — Creator:**

- `content_drafts`: `id`, `kind` (map / quest / item / enemy / scenario), `author_account_id`, `version`, `status` (`draft → playtest → published → retired`), `body jsonb`, `validation_report`, `created_at`.
- Чернетка перевіряється тими самими Zod-схемами контенту, що й вбудований контент.
- **Пісочниця:** Creator грає чернетку героєм з `is_sandbox = true`. Предмети й монети пісочниці не можуть потрапити до звичайних героїв (окремий герой, окремі агрегати, `OFFER_ITEM` між sandbox і не-sandbox заборонений).
- Публікація = нова `contentVersion` бандла. Публікувати може лише `admin` (тобто Олег).
- Якщо D6 з'являється **після** публічного релізу, перед вмиканням ролі Creator на проді — окремий міні-пентест ролей (S4): ескалація `creator → admin`, доступ creator до даних гравців, XSS у тексті чернеток.

**D7 — AI-агент:**

- Сервісний акаунт з роллю `creator`, окремий API-токен з обмеженими правами: створювати й редагувати **лише власні чернетки**. Без доступу до даних гравців, без публікації.
- Кожна дія агента — в журналі авторства.
- Перед публікацією Олег проходить чернетку в пісочниці й публікує вручну. Для дитячої гри будь-який згенерований контент проходить людську перевірку.

### S2 — пентест (вхідна умова: S1 готовий, D0–D4 зелені)

Обсяг (на основі OWASP ASVS рівня 2 + ігрові атаки):

- **Auth:** брутфорс і rate limit, перевикористання refresh, фіксація сесії, вихід і відкликання, витіснення сесії.
- **Доступ (IDOR):** чужий `heroId` / `expeditionId` у кожній команді й запиті, ролі `player → creator/admin`.
- **Ігрова економіка:** повтор команди (replay), гонки паралельних команд (подвійна витрата монет), від'ємні та величезні `amount`, предмети, яких немає в контенті, обхід ціни, перепродаж з прибутком, переповнення стеку.
- **Ввід:** ін'єкції (SQL через JSONB-запити), XSS в імені героя та будь-якому тексті гравця, надвеликі payload, кривий JSON у WS.
- **Витоки:** `server_state` / сід, stack trace, чужі дані у відповідях, дані в логах.
- **Доступність:** флуд WS-з'єднань і команд.
- Формат: спершу власний прохід (скриптові атаки в окремому наборі тестів `apps/api/test/security/` + OWASP ZAP), потім за бажанням — зовнішній фахівець.
- Результат: звіт `docs/security/pentest-S2.md` (знахідка → ризик → виправлення → регресійний тест). Кожна знахідка закривається тестом, щоб не повернулася.
- **Вихідна умова:** немає відкритих критичних і високих знахідок.

### S3 — доповнювальний пентест коопу (після D5)

Кооп відкриває нові поверхні атаки, тому окремий короткий прохід: приєднання без запрошення, керування чужим героєм, передача предметів між героями (дюп через гонку), підміна черговості, витік чужого інвентаря через стан експедиції, флуд від одного учасника.

## 12. Реліз: R1 закрита бета → R2 публічний реліз

### R1 — приймальне тестування (Олег + друзі)

- Той самий staging або окремий `beta`, доступ **лише за інвайт-кодами** (`invites`: код, хто створив, скільки використань, строк).

- **Вихідна умова:** немає блокерів, Олег підтверджує готовність. Рішення: скидати прогрес бета-тестерів перед R2 чи ні.

### R2 — публічний реліз

Тут відновлюються Фази 11–12 повністю:

- Вибір хостингу (рішення Олега), домен, TLS, автоматичні бекапи БД з **перевіреним відновленням**, план відкату релізу.
- Моніторинг (помилки, навантаження, аномалії економіки), алерти.
- Обов'язково перед відкриттям: політика конфіденційності й умови, експорт і видалення акаунта, строки зберігання даних, юридична перевірка вимог для дітей у цільових країнах.
- Реєстрація відкрита для всіх; кооп — за кодами-запрошеннями між гравцями.

### D0.2 Серверна основа (що вже є)

- **Таблиці Drizzle** (`apps/api/src/db/schema.ts`): `users` (username, password, name, tokenVersion), `heroes` (`userId` → users, `data jsonb`), `campaigns`, `scenarios`, `saves`, `snapshots`. - **Auth:** `bcryptjs` (не argon2id), один access-JWT (`jwt.env.ts`, `expiresIn` з env), **refresh-токенів і `auth_sessions` немає**; відкликання через `users.tokenVersion` (logout збільшує). `@fastify/cookie` і `helmet` підключені, httpOnly-refresh немає. Rate limit на auth — `@nestjs/throttler`.
- **Герой:** `GET /heroes/me` ліниво створює героя (`findOrCreateByUserId`); `findByUserId` бере `limit(1)` — один герой на користувача **захардкоджено**.
- **WS gateway** (`game.gateway.ts`, socket.io): JWT у `handshake.auth.token`, події `join-scenario` / `command`; перевірка власника сценарію, ліміт 10 команд/с на сокет, Zod `HEX_ENGINE_COMMAND_SCHEMAS`, `commandRefusal` (HERO_SCOPED команди мусять мати `heroId` = керований герой; `GRANT_ITEM`/`CONSUME_ITEM` — SERVER_ONLY). Стан кімнати тримається в `ScenarioStateService.rooms` (пам'ять) + автозбереження кожні 30 с у `snapshots`.

### D0.3 Де виконуються інвентарні команди

Правила вже в engine: `packages/engine/src/inventory/` (`MOVE_ITEM`, `AUTO_PLACE_ITEM`, `STORE_RESOURCES`, `SORT_STASH`, `UNLOCK_STASH_CHEST`, `GRANT_ITEM`, `CONSUME_ITEM`, подія `INVENTORY_CHANGED`, `InventoryState` зі своїм `revision`, схема `inventoryStateSchema`). ### D0.5 «Монети в руці → гекс»

Монети — предмет, який лягає в руку (`hand-tools.ts: toolKeyOfItem(COINS)`), і сьогодні мають одну механіку: **розблокування скрині схованки** (`UNLOCK_STASH_CHEST`: 100, потім 1000; платяться з монет у руці, решта лишається). Торговців, воріт з платою, `OFFER_ITEM` ще немає — це D3.

### D0.6 Що отримує новий герой сьогодні

- **API:** `starterHeroData()`: 3/3 здоров'я, attack 1, defense 1, coins 0, kills 0, energy 100/100.
- **Інвентар (web/engine):** `createInitial` в `inventory-state.ts` кладе у першу (заблоковану) скриню `STARTER_STASH_ITEMS` = меч, сокира, щит, кирка (`starterGiven`) **і ще 50 Return Scroll** (`STARTER_SCROLL_COUNT`, `grantStarterGear`). Це суперечить §1.3а («порожньо»): рішення Олега потрібне — прибрати і сувої теж? (див. питання нижче).
- **Воля:** старт 20, ємність 50 — у `KNOWLEDGE_RULES` (`knowledge/math.ts`), тобто вже в engine-контенті, захардкоджених значень в API немає.
- **«Рука»:** `HEXOBJECT_KEYS.HAND` — це **інструмент** (`tools.content.ts`, `HERO_TOOL_TYPE.HAND`), який герой тримає за замовчуванням, а не предмет у сумці/екіпіровці: `toolKeyOfItem` повертає `HAND` для порожньої руки. Зробити «руку» неінвентарною не потрібно, лише перевірити в D1 тестом, що `createInitial` не кладе `hand` у `bag/equip/stash`.

### D0.7 Джерела предметів і монет

Прогрес з нуля без dev-кнопок **зараз неможливий для монет**: єдине джерело монет — dev-кнопка в налаштуваннях (плюс `COINS` як hexobject на карті, але в camp-малюнку його прибрано, див. CLAUDE.md). Тому без першого легального джерела монет скриню не розблокувати, а в ній старе спорядження (меч, сокира, щит, кирка), без якого вести бої/добування неможливо. Предмети є з: збирання ресурсів (дерево/камінь через сокиру/кирку), лут/скрині на підземних картах, Книга Волі (лише Воля). **Блокер для §1.3а:** при порожньому старті гравець без монет не отримає жодного знаряддя. Рішення в «Питаннях» нижче.

### D0.8 Розбіжності з планом і питання до Олега

### Пропозиції до плану

**P1. Розвести «зберігання» і «захист від читів».** Зараз D1–D4 змішують два завдання. Для закритої бети з друзями довіри достатньо: потрібне надійне зберігання й відновлення, а не повна серверна авторитетність кожного ходу. Тому: **D1 = універсальне сховище агрегатів + журнал + конвеєр команд**, а перенесення кожного виду прогресу (D2, D4) може йти спершу як «сервер перевіряє схему й інваріанти та зберігає», і лише потім — як «сервер виконує правила». Пентест S2 тоді потрібен **перед R2 (публічним)**, а не перед R1.

**P2. Віха «Усі дані героя в БД» = завершення D4 (соло-експедиції).** Після D1 в БД інвентар і монети, після D2 — Воля, навички, здоров'я, після D4 — карти, туман, позиція, бої. Тільки D4 закриває потребу «закрити вкладку, відкрити на іншому пристрої — все на місці». D0–D2 — це чверть шляху; монети й предмети там, але світ ще ні.

**P3. Мінімальна віха для друзів (R1-lite) може стояти одразу після D4 + урізаного S1** (staging з TLS, секрети, бекап БД, Origin-перевірка, інвайт-коди), **до** повного пентесту. Умова: тестери відомі, прогрес не виставляється як змагальний. Повний S1+S2+S3 — перед публічним R2. Це скорочує шлях до живих тестерів на дві великі фази.

**P4. D4 розбити.** Це найважча фаза (карти генеруються на клієнті, стан карти + знімок бою зараз пишуться в localStorage). Пропозиція: **D4a** — серверний «блоб-стан» експедиції (карта + стан, checksum, ревізія, зберігання в БД, генерація на сервері тим самим engine), **D4b** — авторитетне виконання команд руху/дій на сервері, **D4c** — `world-presence` + повернення порталом. D4a сам по собі дає віху P2.

**P5. Генерація на сервері вимагає детермінованого seed.** План уже має `rngSeed`; додати: карти й бої генеруються з `seed`, збереженого в `expeditions.seed`, щоб реплей і відновлення після рестарту були байт-в-байт однакові (інакше знімок + реплей з §7 не зійдеться).

**P6. Вимкнути localStorage-стан за прапором, а не видаляти одразу.** У D1–D2 зберегти старі `*-storage.ts` за `VITE_LEGACY_LOCAL_STATE` для відкату до завершення D4, потім видалити в D4c.

**P7. Тести економіки готувати з D1.** Перенести `10 одночасних CONSUME_ITEM` у спільну інтеграційну фікстуру і потім розширювати для S2, а не писати з нуля перед пентестом.

### Відповіді O1–O3 (2026-11-09)

- **O1.** `createInitial` = порожній інвентар, 0 монет, Воля 20. Перша скриня кемпу — об'єкт у кемпі, який герой відкриває сам: безкоштовно, один раз; вміст — меч, сокира, щит, кирка. До D4b сервер перевіряє: достатньо Волі, крок на сусідній гекс від збереженої позиції, предмет існує в контенті, лут має `lootId` від серверного seed і підбирається лише раз. **Відома прогалина, прийнятна до R1, обов'язкова до R2:** повна перевірка світу (досяжність, стан гексів, вороги) — лише в D4b.

**Наслідки для D1/D2, які треба врахувати:**

1. `claimedRewards` живе в `progress`, а `progress` за планом з'являється в D2. Тому D1 створює **мінімальний `progress` v1** (лише `claimedRewards`), D2 його розширює апкастером.
2. `CLAIM_CAMP_CHEST` змінює два агрегати (`inventory` + `progress`) в одній транзакції; конвеєр §5.2 розрахований на один агрегат, тож D1 має підтримати команду з кількома агрегатами (порядок блокування за `kind`).
3. Перевірка «`lootId` від серверного seed» у D2 вимагає, щоб сервер знав, який лут існує. До D4a карта лишається на клієнті, тому в D2 сервер може лише (а) видавати `lootId` детерміновано з `rngSeed` + координат + ревізії карти і (б) фіксувати вже підібрані `lootId` (один раз). Повна відповідність «лут справді лежить на цьому гексі» — D4b.
4. Dev-кнопка монет (`DEV_GRANT_ITEM`) і `seed-hero` лишаються єдиним способом отримати монети до D3.

## Результати D2 (2026-11-09)

**Зроблено.** Воля, навички, кроки й присутність героя живуть на сервері в агрегаті `progress` v2 (`claimedRewards`, `knowledge`, `presence`, `steps`). Старий `progress` v1 піднімається апкастером (`upcastAggregate` тепер отримує `{ heroId }`).

- **Engine** (`aggregates/execute-progress-command.ts`): серверні команди `KNOWLEDGE` (крок, Книга Волі: start/answer/next/open), `SACRIFICE_TO_SKILL`, `RESET_SKILLS`, `ARRIVE`, `SPEND_WILL` і dev-фікстури `DEV_GRANT_WILL`, `DEV_SET_KNOWLEDGE`. Контекст знання (`serverKnowledgeContext`) будує сервер із того, де герой стояв: зона Волі береться з локації, «біля Книги» з відомого гекса Книги в кемпі (`CAMP_BOOK_HEX`), бій і рух сервер вважає вимкненими, тож крок може лише коштувати більше, не менше. Крок має бути на сусідній гекс від збереженої позиції. `SPEND_WILL` бере ціну дії з `willCost` контенту (лише там, де локація бере Волю), ціну порталу з навички Teleport; клієнтський `cost` ігнорується.
- **API:** без змін у конвеєрі, окрім правила ревізій `PLAYER_COMMAND_REVISION` (`aggregate` / `knowledge` / `none`) і `asAggregates`, що не вимагає інвентаря для команд прогресу.
- **Web:** `sendProgress` / `ensurePresence` / `pushKnowledgeFixture` в `services/inventory/inventory-sync.ts`; `knowledge-controller.ts` шле команди на сервер і чекає відповідь (Воля не передбачається локально). Дії та портал спершу виконуються локально на копії, потім сервер списує Волю (`SPEND_WILL`) і його відповідь стає правдою. Крок тепер завжди йде через сервер (і в кемпі, де він безкоштовний). `localStorage` для Волі прибрано; лишилась тільки чиста `recoverStepPosition` (`services/knowledge/step-recovery.ts`). Для юніт-тестів є фейковий сервер на справжніх правилах engine (`src/test-support/fake-player-server.ts`, `fake-session.ts`).
- **Тести:** engine 903, API 114, web 2281, e2e: повний прогін 139 зелених + виправлені 8 (сувої й гонка «фікстура → перезавантаження»), потім 23 зелені.
- **Виправлено заднім числом D1:** e2e, що потребували стартових Return Scroll, тепер видають їх хуком (`VerifyInventoryFeature.givenItem`), а перед `page.goto` фікстури чекають збереження (`settleInventorySync`).

**НЕ зроблено (переїздить у D4a/D4b, бо сервер ще не має карти):** серверні `MOVE_HERO` / `START_HEX_ACTION` як повні команди, лут із `lootId` від серверного seed і разовий підбір, здоров'я/kills/portal у `progress`, прибирання застарілих полів `heroes.data` (`attack`, `defense`, `currentEnergy`, `maxEnergy`, `imgPath`).

**Відомі прогалини (прийнятні до R1, обов'язкові до R2):** `ARRIVE` сервер приймає зі слів клієнта (телепорт заявою); `hexobjectKey` у `SPEND_WILL` клієнт може підмінити на безкоштовний; відповідь питання Книги видно клієнту й швидкий бонус рахується з `elapsedMs`, який надсилає клієнт; світ, туман, бій і здоров'я ще в `localStorage`.

## Результати D4a (2026-11-09)

**Зроблено (тимчасово, до D4b).** Усе, що описує світ героя, живе в БД, а не в `localStorage`: карти з туманом, знімки бою, індекс карт, таймери респавну, де герой стоїть, його здоров'я, зв'язок порталу. Збереження лише від вкладки, що володіє героєм: токен вкладки видається разом зі знімком і йде заголовком `X-Player-Session`, інакше 409 `SESSION_TAKEN_OVER`. Дозволені ключі: `map:<uuid>`, `state:<uuid>`, `index`, `respawn`, `nav`, `progress`, `hero-store`; документ ≤ 3 МБ і валідний JSON, експедиція ≤ 24 МБ і ≤ 64 ключів. Скидання героя для dev стирає й світ. CORS тепер дозволяє `PATCH` і `X-Player-Session` (`src/cors.ts`).

Закриття вкладки: великі документи не вкладаються в `keepalive` (~64 КБ), тож останні ~400 мс змін можуть загубитися; e2e перед перезавантаженням явно чекає збереження (`settleInventorySync`). Старий локальний світ не переноситься. Колонки `heroes.data` з `heroLocation`/`currentHealth` лишились як були (серверна позиція тепер у `progress.presence` і документі `hero-store`).

## Розвідка D4b (2026-11-09): що означає «авторитетний світ» і як його різати

**Що вже є.** Engine вміє виконувати світові команди без Vue: `applyCommand` з портами `IActionContext` (`heroToolStore`, `hero`, `gathering`, `events`, `worldMap`), туман (`map/fog-service.ts`), рух (`hero-movement/`), дії та лут (`features/`), портали, бій, сквади; карти будуються детерміновано з seed (`MapRegistry.create({ seed })`, `runBoardPipeline`). На сервері є заготовка портів (`apps/api/src/game/server-action-context.ts`).

**Чого немає.** Сервер не тримає карту: її створює, мігрує й змінює клієнт (`world-map-store`: генерація, `installCampBook`, розміщення героя на вході, `revealAroundHero`, респавн, збереження). Тому три прогалини з D2/D4a (положення зі слів клієнта, `hexobjectKey` у `SPEND_WILL`, ефекти й лут дій як `DEV_*` команди, заборонені в production) **не закриваються частковою перевіркою**: щоб перевірити крок чи дію, сервер мусить мати карту і сам її змінювати.

**Наслідок для розрізання.** Немає когерентного шматка «лише лут» або «лише рух»: крок змінює туман і може почати засідку, дія змінює гекс і дає лут, вихід і портал міняють карту, бій читає карту. Тому D4b це зміна ролі клієнта на проєкцію, і різати її треба за **шарами**, кожен з яких залишає гру працюючою:

| Етап  | Що                                                                                                                                                                                                                                                                                                                                                                                    | Критерій готовності                                                       |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| D4b-1 | Сервер володіє картами: генерує їх з `expeditions.seed` (статичні й підземелля), зберігає й віддає клієнту знімок. Клієнт більше не завантажує карти й не шле їх (`map:*`/`state:*` лише на запис сервера). Крок (`KNOWLEDGE step`) виконується на карті сервера: прохідність, туман, засідка; відповідь має зміни гексів (`tileDiffs`). `ARRIVE` зникає, положення береться з карти. | e2e руху/туману/перезавантаження зелені, клієнт не може сам змінити карту |
| D4b-2 | `START_HEX_ACTION` / `FINISH_PENDING_ACTIONS` на сервері над картою, прогресом і інвентарем в одній транзакції; лут від серверного seed і разовий; зникають `SPEND_WILL` з клієнтським ключем, `DEV_GRANT_ITEM`/`DEV_CONSUME_ITEM`/`DEV_SET_INVENTORY` для світових змін.                                                                                                             | добування, скрині, підбір, свиток працюють у production-режимі            |
| D4b-3 | Виходи між картами, портали, респавн, `heroes.data` позиція/здоров'я в `progress`.                                                                                                                                                                                                                                                                                                    | подорож між локаціями, e2e порталу                                        |
| D4b-4 | Бій: `BATTLE` start/close і ходи на сервері (перепідключення посеред бою вже працює через знімок).                                                                                                                                                                                                                                                                                    | e2e бою без клієнтських фікстур у production                              |
| D4b-5 | Прибрати тимчасове: `ARRIVE`, `DEV_*` світові команди, `PATCH` документів світу від клієнта, `localStorage`-залишки.                                                                                                                                                                                                                                                                  | S2 має що пентестити                                                      |

**Ризики.** Усі ~150 e2e йдуть через світ; кожен етап ламає багато з них, поки клієнт не переведений на проєкцію. Реплікація стану на клієнт: потрібні `tileDiffs` (порівняння серіалізованих гексів до/після команди) або події → патч карти (`applyRemote`); повні знімки карти (200-500 КБ) на кожен крок неприйнятні. Час: сервер повинен мати годинник для тривалості дій (`endsAt`).

### Уточнення після читання `world-map-store` (2026-11-09): D4b-1 і D4b-2 не існують окремо

Клієнт сам створює карту (`loadLocationMap` → `MapRegistry.create`, `initFog`, `hydrateResourcesFromConfig`, `installCampBook`, `placeHeroAtEntry`, `revealEntryTile`), сам її змінює діями й зберігає (`saveToStorage` → документи D4a). Якщо сервер лише **генерує** карту (D4b-1), але дії ще виконує клієнт, то зміни карти (зрубане дерево, відкрита скриня, підібраний лут) або вантажаться як дозволений клієнтський запис (і сервер не має чого перевіряти), або губляться після перезавантаження. Тому реальний мінімальний когерентний шматок це **D4b-A = D4b-1 + D4b-2**: сервер генерує карту, виконує крок (прохідність, туман, засідка) і дію (`START_HEX_ACTION`/`FINISH_PENDING_ACTIONS`, лут) над своєю картою, прогресом та інвентарем в одній транзакції, а клієнт отримує зміни гексів (`tileDiffs`). Етапи D4b-3 (виходи, портали, респавн, здоров'я) і D4b-4 (бій) залишаються окремими.

**Фундамент D4b-A, який потрібен будь-яким розрізанням** (і який можна зробити й перевірити без зміни клієнта): чиста функція створення світу `createWorldMap(locationKey, seed)` з тими самими кроками ініціалізації, що має клієнт; серверні порти `IActionContext` з годинником сервера; виконання кроку й дії над серверним станом з обчисленням `tileDiffs`; зберігання карт як серверних документів. Клієнт переводиться на проєкцію окремим кроком.

## Результати D4b-A, фундамент (2026-11-09; клієнт ще не переведено)

**Зроблено (сервер і engine, без змін клієнта; гра працює як після D4a).**

- **Engine** (`packages/engine/src/world/`): `createServerWorld(locationKey, mapId, expeditionSeed, heroId)` створює карту з тими самими кроками, що має клієнт (генерація з seed, туман, ресурсні спавнери, Книга в кемпі, герой на вході, відкрита зона навколо); `serializeWorld`/`deserializeWorld` (з `contentVersion`); `stepWorld` (сусідній гекс, прохідність за картою сервера, маршрут і засідка через `MOVE_HERO`, Воля за правилом локації, туман), `actWorld` (дія над гексом з Волею й лутом в одній операції), `tickWorld` (завершення дій за годинником сервера); `diffTiles` дає лише змінені гекси (`tileDiffs`). `createServerActionContext` (порти без UI) переїхав з API в engine; `hero-placement` теж. Схеми `WORLD_ENTER`, `WORLD_STEP`, `WORLD_ACTION`, `WORLD_TICK` (strict).
- **API:** `WorldService` (`apps/api/src/world/`) виконує ці команди в одній транзакції над прогресом, інвентарем і картою, з ідемпотентністю за `commandId`, журналом, ledger і ревізією прогресу; WS-подія `world:command` → `world:result` і `GET /player/world` (повна карта поточної локації). Карти лежать серверними документами `srv-index` та `srv-world:<uuid>` в `expedition_blobs`: браузер їх не читає (`GET /expeditions/current` фільтрує) і не пише (`PATCH` відхиляє ключі `srv-*`).
- **Тести:** engine 917 (світ: однаковий seed дає однаковий світ, туман, крок, дія з лутом по годиннику сервера, `tileDiffs`), API 140 на реальному Postgres (вхід у світ, крок з Волею й туманом після перезавантаження, відмови, ідемпотентність, паралельні команди, лут за `WORLD_ACTION` + `WORLD_TICK` з ledger, ізоляція серверних документів, сокет і REST).

**Не зроблено (наступні чати, у порядку).**

1. **Клієнт на проєкцію:** `world-map-store` бере карту з `GET /player/world` і не генерує її; рух і дії йдуть командами `WORLD_*`, відповідь дає `tileDiffs`, які клієнт вставляє в локальну карту; прибирається `ARRIVE`, `SPEND_WILL` з клієнтським ключем, світові `DEV_*` команди, `PATCH` документів карт. Зачепить значну частину e2e.
2. D4b-3: виходи між локаціями й портали (`WORLD_ENTER` зараз дозволяє будь-яку локацію, тож не можна вважати його перевіреним переходом), респавн, здоров'я в `progress`.
3. D4b-4: бій на сервері (`engagement` вже зберігається в документі світу).
4. D4b-5: прибрати тимчасове.

**Відомі межі фундаменту.** Дія вимагає, щоб гекс був поруч із героєм (відстань ≤ 1); якщо e2e покаже законний випадок далі, правило треба уточнити. Здоров'я лікування (вогнище) на сервері поки нічого не робить. Генератор карт кладе випадкові фонові картинки гексів (`Math.random()` у білдері), на механіку це не впливає.

## D4b-A, друга половина: зупинено на розвідці (2026-11-09)

**Що додано на сервері** (бо клієнту знадобиться): `POST /player/world/ensure` (карта локації будується при першому зверненні й зберігається, герой не рухається) і `PUT /player/world` (dev/sandbox: клієнт передає змінену карту, у production відмова; замінює стару карту локації й оновлює `presence`), обидва лише від вкладки-власника (`X-Player-Session`), у відповіді `WORLD_*` є `engagement`. Тести: API 142.

**Що з'ясувалося при переведенні клієнта.** Клієнт можна зробити проєкцією карти (джерело карти, `tileDiffs`, крок через `WORLD_STEP`), і ця частина проста. Але **дії** (`START_HEX_ACTION`/тік) у engine працюють через порти `IActionContext`, які в клієнті реалізує сам Pinia-стор інструмента та героя: `consumeDurability`, `lockTool(tile, endsAt)`, `addTreeCut`, `collectStones`, `gathering.add`, `events.push`, `healHero` і читання стану перетягування (`isDragging`, `hover`, `activeTool`) у циклі лікування біля вогнища. Сервер без UI не може їх виконати, тож мовчазні порти `createServerActionContext` дають втрату поведінки: довговічність не зменшується, інструмент не блокується, лічильники й рядки журналу зникають, лікування біля вогнища завершується одним тиком. Тому друга половина **не робиться як «просто переключити клієнт»**.

**План, як різати далі (у порядку).**

1. **Порти як запис і відтворення:** у engine замінити порти сервера записувачем побічних ефектів (`lockTool`, `consumeDurability`, `treeCut`, `stones`, `gather`, `log`, `heal`, зміна `activeTool`), які `actWorld`/`tickWorld` повертають як `effects`; клієнт відтворює їх на справжніх сторах. Окремо спроєктувати `USE` біля вогнища без залежності від стану перетягування (стан інструмента передає клієнт у команді, або лікування стає серверною дією зі здоров'ям, D4b-3).
2. **Клієнт: джерело карти й крок.** `loadLocationMap` бере карту з серверного кешу (`ensure` для всіх локацій при старті сесії), прибрати локальні `revealAroundHero`/`installCampBook`/`hydrateResourcesFromConfig` для завантаженої карти, `moveHeroTo` шле `WORLD_STEP`, застосовує `tileDiffs`, прибрати `ARRIVE`.
3. **Клієнт: дії й тік.** `dispatchHexAction` шле `WORLD_ACTION`, світовий цикл шле `WORLD_TICK`, коли дозріла дія чи спавнер; відтворення `effects`; прибрати `SPEND_WILL` з клієнтським ключем і світові `DEV_*`.
4. **Фікстури й тимчасові шляхи:** хуки, що ставлять гекси, портал, перетин, респавн і dev-інструменти передають карту через `PUT /player/world` (dev-гейт), до D4b-3/D4b-4.
5. Юніт-тести з заповненим кешем світу (`createServerWorld`), e2e по групах `board`, `hero`, `camp`, `combat`.

**Стан дерева:** клієнт без змін відносно D4a (гра працює як раніше); серверні `ensure`/`adopt`/`WORLD_*` ще не мають клієнтського споживача.

## D4b-3, частина 3 (2026-11-10): здоров'я в `progress`

**Зроблено: здоров'я героя належить серверу.**

- **Стан:** `progress` v4 має `health: { current, bonus, debt }` (база 3 серця, `HERO_BASE_HEALTH`; правило `HeroModel` те саме, що було на клієнті: повний герой лишається повним при зростанні максимуму, поранений зберігає здоров'я, зняття щита запам'ятовує борг). `HeroModel` отримав `restoreHealth`/`healthState`.
- **Лікування біля вогнища** рахує сервер: порти світових команд тримають `HeroModel` з `progress.health` (`createRecordingPorts(hint, model)`), тож підказка клієнта більше не несе `health` (схема `client` лишила тільки `tool`). Клієнт не відтворює ефект `heal`, а бере здоров'я з відповіді.
- **Максимум від щита:** `executePlayerCommand` після будь-якої зміни інвентаря перераховує `bonus` з екіпірованих предметів (`sumHeartPoints`) і змінює `progress.health`. Для цього всі інвентарні команди тепер блокують і `progress` (`PLAYER_COMMAND_AGGREGATES: ['inventory', 'progress']`); без цього максимум не зберігався (знайшли e2e `shield-max-health`).
- **Тимчасове до D4b-4:** `DEV_SET_HEALTH` (заборонена в production) для бою, респавну після поразки, dev-кнопки й e2e-фікстури; на клієнті це `heroStore.reportHealth` (`services/inventory/health-report.ts`): локальне значення ставиться одразу, запізнілі відповіді сервера на старі звіти ігноруються, поки є непідтверджені. Локальний `useEquipmentHealthSync` лишився для миттєвого відгуку UI (правило збігається з серверним, сервер авторитетний через `bindHealthListener`).
- Тести: engine 941 (`aggregates/health.test.ts`, лікування з `progress.health` в `world/effects.test.ts`), API 153 (екіпірування щита піднімає збережений максимум, лікування від серверного здоров'я), web 2307, e2e: 78 з 78 (`battle-flow`, `shield-max-health`, `hero-persistence`, `return-portal`, двічі поспіль), попередні 33 з `camp`/`board`.

## Старт чату: D4b-4, розвідка (бій на сервері)

Прочитай: цей документ (розділи «D4b-A кроки 2–5», «D4b-3 частини 1–3», «Результати D4b-A, крок 5»), `docs/battle-system/BATTLE-HANDOFF.md`, скіли `hexoflat-phase`, `hexoflat-engine`, `hexoflat-web-state`, `hexoflat-e2e`, `CLAUDE.md`. Гілка `player-persistent-data-implement`. Не комітити, наприкінці дати повідомлення для коміту й звіт українською. Не використовувати `git stash`/`checkout`/`reset`. Коментарі в код не додавати.

**Перший чат тільки розвідка й розрізання** (як було для D4b-A): нічого не міняти в коді, лише прочитати й записати в цей документ план кроків D4b-4 з критерієм готовності кожного, показати Олегу.

**Що вже серверне:** карта, крок, дії, тік, подорож (перетин меж, брама), портал, Воля, навички, здоров'я (`progress.health`), інвентар. `engagement` вже лежить у серверному документі світу (`ServerWorld.engagement`), ATTACK на загоні вже створює його на сервері (`actWorld`).

**Що ще на клієнті й має переїхати:**

1. Стан бою (`BattleState`): старт з `engagement` (`squad-flow.ts`, `battle-store.ts`), генерація поля бою, ініціатива, ходи героя й ворожий AI, вікно блоку (5 с, годинник), щити, `set-hands`. Рушій бою вже чистий (`packages/engine/src/battle/`), тож це питання команд, годинника сервера й відтворення подій на клієнті.
2. Закриття бою (`closeBattle`): перемога (загін зникає з карти, герой на стартовому гексі), поразка (респавн у таборі: `respawnHeroAtCamping`, закриття порталу, свіжа карта покараної локації, `reviveAtOneHp`), витрата предметів і лут з бою (`withStoreInventory` у `squad-flow`).
3. Здоров'я з бою (`followBattleHealth`, `closeOut`) йде зараз через `DEV_SET_HEALTH`.
4. Анімації (`apps/web/src/render/battle/`, `battle-timing.ts`) лишаються на клієнті й мають відтворювати серверні події; рушій не чекає візуалу.

**Питання, які розвідка мусить вирішити:** модель команд бою (одна команда на дію героя чи сесія з довгим життям; ходи ворогів сервер виконує сам у відповіді); хто тримає годинник вікна блоку (сервер, `reaction-timeout` тікає по `WORLD_TICK`-подібній команді); як клієнт показує ворожі ходи покроково (події з часовими мітками чи відповідь з кроками для `battle-animation-queue`); перепідключення посеред бою; що робити, коли два вкладки (одна активна сесія героя вже є); баланс (два тести `it.skip`, не чіпати до переробки щитів).

**Що прибере D4b-4/D4b-5:** `DEV_SET_HEALTH`, останній `DEV_SET_INVENTORY` (бій), міст `PUT /player/world` з полем `current`, клієнтську локальну генерацію карт і клієнтський тік, `localStorage`-залишки, довіру до `client.tool` (знос інструмента на сервері).

**Тести й запуск:** API на реальному Postgres, engine перебудувати (`pnpm --filter @hexoflat/engine build`) після змін; e2e тільки `sh scripts/pre-push-e2e.sh <шляхи спеків>` у фоні і тільки впалі спеки; будь-який новий метод чи заголовок браузера додати в `apps/api/src/cors.ts`; фікстури асинхронні до сервера, перед перезавантаженням `settleInventorySync()`.

## Розвідка D4b-4 (2026-11-10): план кроків бою на сервері (чернетка до відповідей Олега)

### Що є сьогодні (факти)

- Рушій бою чистий і вже має все потрібне: `startBattle`, `applyBattleCommand` (hero / run-enemy-turn), `beginBattle` / `closeBattle` (`squads/squad-battle.ts`, працюють над `SquadWorld`: карта, `engagement`, `battle`, `inventory`, `knowledge`), `projectBattleForViewer` / `projectBattleEvent`. `closeBattle` уже сам знімає загін при перемозі, збільшує `attempts` при поразці й списує витрачені предмети з чернетки інвентаря (`spendConsumables`).

- Збереження: `battle-store.snapshot()` `{ engagement, battle }` лягає в документ світу, автозбереження через `$subscribe`. Тестові хуки (`e2e/battle-hooks.ts`) пишуть прямо в `store.battle` (завершити бій, віддати хід, поставити Волю).

Клієнт лише переходить на отриману карту табору.                                                                                                             | Той самий механізм, що `travelWorld`; зникає `respawnHeroAtCampingAction` і її виклики стору.                                                                                                                                                                                     |

### Кроки

Кожен крок окремий чат, гілка `player-persistent-data-implement`, e2e тільки за вашою командою.

**B1. Engine: серверний бій над `ServerWorld`** (без API й клієнта)

- `ServerWorld.battle` у схемі й `serializeWorld` (з міграцією: відсутній = `null`). Модуль `world/battle-world.ts`: `battleWorld(run, command)` над `WorldRun` викликає `beginBattle` / `applyBattleCommand` / `closeBattle`, годинник з `run.now`, створіння героя з прогресу й інвентаря, лінива розв'язка простроченого вікна, `progress.health` після кожного кроку, відповідь `steps` з проєкцією.
- Схема `WORLD_BATTLE` (strict, без `atMs` і `heroes`).
- Критерій: юніт-тести рушія й світу зелені; повний бій із seed через `WORLD_BATTLE` дає ті самі події, що пряма симуляція; клієнтські `atMs`/`heroes` відхиляються; вікно після дедлайну дає `WINDOW_CLOSED`, ранній `reaction-timeout` дає `TOO_EARLY`; відповідь не містить прихованих щитів ворога (тест на проєкцію); перемога знімає загін, поразка збільшує `attempts`; витрачені предмети зникають з інвентаря в тій самій операції.

**B2. Respawn на сервері (engine)**

- `respawnWorld(run)` на основі `travelWorld` і `closePortalIfOpen`: свіжа карта покараної локації, `presence` у табір, 1 серце, `touched`. Викликається з `close` при поразці.
- Критерій: тест «поразка в підземеллі з відкритим порталом» (портал закритий з обох кінців, карта свіжа, герой у таборі з 1 серцем, `sealedUntil` не змінився або змінився так, як вимагає правило); тест поразки в таборі-сусідній локації.

**B3. API: `WORLD_BATTLE` у `WorldService`**

- Маршрут команди, транзакція світ + прогрес + інвентар, ідемпотентність за `commandId`, журнал, ledger для списаних предметів, `GET /player/world` з проєкцією бою й `engagement`, відповідь `steps`/`touched`.
- Критерій: інтеграційні тести на реальному Postgres: бій від ATTACK до перемоги й до поразки; перезавантаження посеред бою (стан бою той самий); дві вкладки (одна активна сесія, друга отримує `SESSION_TAKEN_OVER` і не може діяти); паралельні команди; повтор `commandId` не дає другого ходу; відповідь і `GET` не містять прихованої інформації; прострочене вікно розв'язується при наступній команді й при `GET`.

**B4. Клієнт: міст бою на команди**

- `bindBattleBridge` (`send`, `start`, `leave`) шле `WORLD_BATTLE` і вставляє `steps` у `absorb`; прибрати `engineState`, `runLifecycle`, `followBattleHealth`, `closeOut`-запис здоров'я, локальний `applyCommand`; `battle-store` тримає проєкцію; автозбереження бою у світовий документ вимкнути (бій відновлюється з `GET /player/world`); `respawnHeroAtCamping` лише переходить на серверну карту; `kills` (див. питання 5).
- Фейковий сервер у `test-support/fake-player-server.ts` виконує `WORLD_BATTLE` справжніми правилами.
- Критерій: web юніт-тести зелені; тест-шпигун показує, що жоден шлях бою й респавну не викликає `DEV_SET_HEALTH`, `DEV_SET_INVENTORY`, `PUT /player/world`; анімації не змінено (знімки `battle-animation-*` тести без змін).

**B5. Тестові хуки бою → серверні фікстури**

- `battle-hooks.ts` (завершити бій, віддати хід, поставити Волю, очистити рани) переїжджають на серверні фікстури, дозволені лише там, де їх дозволяє рішення з питання 4.
- Критерій: `apps/playwright/e2e/world/battle-flow.spec.ts`, `squad-actions.spec.ts` зелені (запуск за вашою командою через `scripts/pre-push-e2e.sh`, спершу `combat`, потім `board`, `hero`); у production-режимі API жодної бойової фікстури не прийме (тест).

**B6 (= D4b-5). Прибрати тимчасове**

- Видалити `DEV_SET_HEALTH`, `DEV_SET_INVENTORY` (у схемах, виконавцях, `health-report.ts`, `inventory-sync.ts`, тестах), `PUT /player/world` з полем `current` і чергою `queueFreshServedWorld`, клієнтську локальну генерацію карт і клієнтський тік, `localStorage`-залишки, довіру до `client.tool` (знос інструмента на сервері).
- Критерій: `grep` не знаходить жодного з цих імен поза історією документа; схеми команд у production-режимі не містять `DEV_*`; усі групи e2e зелені (`board hero camp combat auth shell`); чекліст для S2 (що пентестити: команди, проєкція бою, годинник вікон, ізоляція документів світу) записано в цей документ.

### Ризики

1. **`set-hands`, `use-item` і зовнішні інвентарні команди під час бою.** Рушій бою тримає руки у створінні, інвентар на сервері у своїй структурі. Потрібно вибрати одну правду (пропозиція: у бою інвентарні команди відмовляють, зміна рук лише через `set-hands`, який оновлює і створіння, і серверний інвентар у тій самій операції). Це перше, що перевірити в B1.
2. **Зайві запити.** Кожен хід ворога стає запитом; на анімаціях це непомітно, але `animating`-замок і `enemyTurnPlaying` мають чекати відповіді (`absorb` приходить асинхронно). Перевірити в B4, що `needsEnemyTurn` не шле другий `run-enemy-turn`, поки перший не відповів.
3. **Тестові хуки.** Їх багато, і вони мутують стан напряму, тож B5 найтрудомісткіший з e2e.
4. **Баланс.** Два тести `it.skip` у `balance.test.ts` не чіпаємо; рушій у B1 лише обгортається, правила не змінюються.

### Питання до Олега (відповіді потрібні до B1)

1. Темп ворожих ходів: **A** (рекомендовано) клієнт шле `run-enemy-turn` по одному ходу темпом анімації, поведінка та сама; **B** сервер відіграє всі ворожі ходи до ходу героя одним запитом (менше запитів, але вікно блоку другого ворога почнеться до показу першого).
2. Годинник вікон: сервер, без фонових таймерів, прострочене вікно розв'язується лінивo при наступній команді або `GET`. Підходить? Чи гравець, що закрив вкладку під час вікна блоку, має отримати `take-hit` одразу після повернення (так і буде за цією моделлю)?
3. Приховані щити й сторони ударів більше не потрапляють у браузер (проєкція). Підтверджуєте, що нічого в UI не потребує повного стану?
4. Серверні фікстури для e2e бою: чи дозволити їх на тестовому API за прапором оточення (`HEXOFLAT_E2E_FIXTURES`, не залежить від `NODE_ENV`), чи залишити поточне правило «`DEV_*` дозволені поза production»?
5. Лічильник вбивств `hero.addKilled()` (зараз лише в клієнтському `hero-store`): переносити в `progress` у B1 чи залишити клієнтським до окремого рішення?
6. Старі локальні збереження з відкритим боєм (у документах світу `battle`) просто відкидаємо без міграції (production-гравців ще немає)?

### Відповіді Олега до B1 (2026-11-10) і що з них випливає

1. **Темп: варіант A.** Кожен ворожий хід окремий запит `WORLD_BATTLE { kind: 'run-enemy-turn' }`, вікно блоку своє, дедлайн від годинника сервера на момент обробки.
2. **Годинник.** Вікна рахує сервер без фонових таймерів. Відповідь героя (щит, aim, `take-hit`, `answer-task`) приймається до `deadline + 500 мс` (константа `BATTLE_NETWORK_GRACE_MS` у контенті правил, не в клієнті). `reaction-timeout` / `task-timeout` приймаються від `deadline` (раніше `TOO_EARLY`). Повернення після закритої вкладки під час блоку = лінива розв'язка `take-hit`. **Відоме обмеження:** немає активного серверного таймера, тож у коопі (D5) знадобиться серверний годинник (планувальник по відкритих вікнах), інакше вкладка, що мовчить, блокує бій для решти.
   - Нова деталь: клієнт зараз порівнює `deadlineMs` з `Date.now()` (`use-battle-reaction`, `battle-timed-task`). Дедлайни тепер у часі сервера, тому відповідь має `serverNowMs`, а клієнт зберігає зсув годинника (`serverOffsetMs`) і показує таймер за ним. Без цього UI покаже хибний залишок часу.
3. **Проєкція замість повного стану.** Перелік того, що UI читає з повного `battle` (перевірено `grep`):
   - **Уже читає проєкцію** (`store.projection`): `use-battle-view`, `use-battle-reaction`, `use-battle-warnings`, `battle-board-tap`, `battle-overlay-model`, `battle-tool-hex`, `battle-hint`. Для них міняти нічого, тільки перевірити в B4, що вони не потребують прихованих полів.
   - **Читає повний `battleStore.battle` (треба замінити):** `use-battle-enemy-driver` і `needsEnemyTurn` (`phase`, `task`, `activeId`, є в проєкції), `actorFor` (`task.creatureId`, `activeId`: є), `hero-store.ts:263,469` і `squad-flow.engineState` (передають `battle` у локальний `applyCommand`; зникають із міграцією на команди), `world-map-store` / `world-map-store-helpers` (знімок бою для збереження: зникає), `battle-hooks` (e2e, переходить на серверні фікстури, B5).
   - **Що проєкція ще віддає зайвого** і треба прибрати в B1 (тест на кожне): `draws` (результати жеребкування ініціативи), `undo`, `wounds`, `struckHands` і `bag` ворожих створінь, `taskHistory`, відповідь завдання (`task.answer` уже обнулена). Поле `seed` і `pending[].fromHex` ворога вже приховані.
   - **Поля проєкції для UI (узгоджено з Олегом):** свій стан повністю (руки, сумка, Воля, `placedShields` героя); серця ворогів (`hp`, `maxHp`); видима кількість ворожих щитів (`shieldsRaised: boolean` зараз; якщо UI має показувати число, додати `shieldCount`, перевірити в B4); блоки ворога лише після розкриття (`STRIKES_RESOLVED.burnedShields`, 2.5 с). Руки ворога лишаються видимими (рядок ворогів у вкладці BATTLE показує їх).
4. **Фікстури.** Лише при `HEXOFLAT_E2E_FIXTURES=1` і `NODE_ENV !== 'production'`. Якщо прапор увімкнено в production, API відмовляється стартувати (перевірка при старті, як JWT fail-fast). Перші `DEV_*` команди теж переходять під цей прапор у B6 (зараз гейт лише `NODE_ENV`).
5. **`addKilled` у `progress`.** У B1: `progress` v5 з `kills: number` (міграція з 0), `closeBattle` додає `kills` у тій самій транзакції; `hero-store` читає лічильник з відповіді, локальний `addKilled` і `saveProgressToStorage` для вбивств зникають.
6. **Старі локальні бої відкидаємо.** При завантаженні документа світу із `battle`/`engagement` старого формату клієнт скидає їх (і серверний `engagement` без `battle` теж закривається як програний/скасований без покарання, див. нижче) і показує м'яке повідомлення в журналі подій (`events`) «A battle from an older version was dismissed». Ключ i18n додати в `ui.json` і в `hexInfo`-тест не потрапляє.

**Руки.** Вміст рук є частиною серверного інвентаря (`inventory.hands`), `set-hands` це команда над тим самим агрегатом, а не окремий стан бою. Наслідки для B1:

- Створіння героя в `beginBattle` бере руки з інвентаря (так і є, `withInventoryLoadout`).
- `set-hands` у `battle-world` виконується над інвентарним агрегатом (існуюча операція руки/слоти з `inventory/`) і оновлює `hands` створіння в тій самій транзакції; ціна 4 Волі за руку лишається правилом бою (`turnWill`).
- Зовнішні `MOVE_ITEM` / `AUTO_PLACE_ITEM` / `SORT_STASH` та ін., поки `world.battle` відкритий, відмовляють (`BATTLE_OPEN`), щоб руки й створіння не розійшлися (тест у B1/B3).
- `closeBattle` порівнює `startItems` з тим, що лишилося в руках і сумці створіння, і списує витрачене (як зараз), але вже з тієї самої серверної правди.

**Висновок для порядку.** Кроки B1–B6 не змінюються; B1 тепер додатково містить: `BATTLE_NETWORK_GRACE_MS`, розширену проєкцію, `kills` у `progress` v5, `serverNowMs` у відповіді, відмову інвентарних команд під час бою. B3 додає перевірку прапора `HEXOFLAT_E2E_FIXTURES` при старті API. B4 додає зсув годинника в клієнті й скидання старих боїв з повідомленням.

### Доповнення Олега до B1–B6 (2026-11-10)

**Захист від подвійного `run-enemy-turn`** лежить на сервері: ідемпотентність за `commandId` (повтор віддає ту саму відповідь) і відмова поза ходом ворога (`NOT_YOUR_TURN`, уже є в `perform-action.ts`). Клієнтський замок `animating` / `enemyTurnPlaying` лишається лише для анімацій. **Руки:** `set-hands` це команда над серверним `inventory`.

**Вимоги до B1 (з доповнення) і тести.**

1. **Відповіді задач бою не в проєкції.** Задачі бою це `TASK_KINDS = ['saw', 'push']` (ухилення з бою вже прибране; ініціатива рахується з `draws`, а не із задачі, але `draws` теж не в проєкції). Клієнт отримує умову й дедлайн, перевірка лише на сервері. Тест: проєкція й `steps[].events` будь-якого кроку не містять `task.answer`, `draws`, `seed`, `taskHistory`; відповідь `answer-task` з клієнта звіряється лише на сервері.
2. **Хід ворога.** Поки триває хід ворога, дії героя відхиляються (`NOT_YOUR_TURN`). Якщо `run-enemy-turn` не прийшов до дедлайну ходу, сервер відіграє його ліниво перед наступною командою й при `GET`. Дедлайн ходу ворога це новий параметр правил `enemyTurnDueMs` (пропозиція: `enemyTurnDelayMs` клієнта + запас на анімацію, близько 15 с, **значення вибирає Олег**: від нього залежить, як довго ворог «чекає» на закриту вкладку). Тест: дія героя в хід ворога відмовляє; прострочений хід ворога відігрується при наступній команді й при `GET`; повтор `run-enemy-turn` з тим самим `commandId` не дає другого ходу.
3. **Здоров'я.** Єдине джерело `progress.health`. У стані бою серця героя не копіюються як окреме поле: створінню героя `hp` ставиться з `progress.health` на початку кожної команди, а після команди пишеться назад у `progress.health` у тій самій транзакції. Проєкція показує лише це значення. Тест: після будь-якої команди `progress.health.current * 2 === hp` героя в серверному стані; зовнішнього способу змінити `hp` в бою немає (`DEV_SET_HEALTH` у бою відмовляє, поки відкритий бій).
4. **Кидки.** Ініціатива, AI, завдання та будь-який лут (його в бою немає) лише з серверного seed; стан RNG у проєкції відсутній (поле `seed` уже вилучене). Тест на невидимість `seed`.
5. **Склад і здобич нерозвіданого загону не в проєкції до SCOUT.** Знайдено витік **поза боєм**: `members` і `loot` загону лежать у `creature.squad` гекса на карті, а карта (повна й `tileDiffs`) іде в браузер. Тому B1 має окрему підзадачу **проєкція карти для клієнта**: перед відправкою (`GET /player/world`, `ensure`, відповіді `WORLD_*`, `touched`) у гексах із загоном, який не розвіданий (`!compositionKnown`), лишається лише лідер (`members[0]`) і довжина, `loot` вилучається; вміст нерозвіданих гексів під туманом перевірити тим самим тестом (відкладене питання, чи шле сервер зміст прихованих гексів: перевірити). Тест: відповідь API про карту з нерозвіданим загоном не містить інших членів і `loot`; після `SCOUT` склад з'являється; після початку бою склад відомий (бій показує ворогів).

### Рішення Олега щодо ворожого ходу й карти (2026-11-10)

- **`enemyTurnDueMs = 15000`** у конфігу бою. Зараз `enemyTurnDelayMs` (700 мс) живе на клієнті в `apps/web/src/render/battle/battle-timing.ts`, а правила, потрібні серверу, в `packages/engine/src/battle/battle-content.ts` (`BATTLE_RULES`, схема `battleRulesSchema`). Серверу потрібне значення в рушії, тому `enemyTurnDueMs` додається в `battleRulesSchema` / `BATTLE_RULES` (поруч з `blockWindowMs`, `taskMs`) і читається звідти й сервером, і клієнтом; `enemyTurnDelayMs` лишається в `BATTLE_TIMING` (це темп анімації, серверу він не потрібен). Не хардкод. Тест схеми: поле обов'язкове, додатне ціле.
- **Вікна при поверненні.** Вікно блоку, відкрите до закриття вкладки, спливає: лінива розв'язка `take-hit`. Якщо ворожий хід відіграно ліниво при поверненні (`GET` або команда), **нове** вікно блоку, що відкривається тим ходом, стартує з `now` цієї відповіді, а не з моменту дедлайну ходу (`atMs` ліниво відіграного ходу = `now` сервера). Порядок: (1) прострочене вікно (якщо є) розв'язується `take-hit` при `now`, (2) якщо ворожий хід прострочений, він відігрується один раз із `atMs = now`, (3) відповідь віддає стан зі свіжим дедлайном.
- **Проєкція карти застосовується і до `tileDiffs`.** Тобто в усіх виходах карти до клієнта (`GET /player/world`, `ensure`, `world:result`, `touched`, `tileDiffs`) діє одна функція проєкції (лише лідер і довжина загону, без `loot`, поки загін не розвіданий); окремого шляху, що обходить її, немає. Тест: `diffTiles` / `tileDiffs` після кроку, що відкриває гекс із нерозвіданим загоном, не містить інших членів і `loot`.
- **Тест «повернення після 60 с тиші».** Герой у бою, відкрите вікно блоку (або хід ворога прострочений), 60 с без команд, далі `GET` або команда: ворожий хід відіграно **рівно один раз** (один `TURN_STARTED` ворога у журналі), прострочене вікно розв'язано `take-hit` один раз, нове вікно блоку (якщо той хід відкриває) має `deadlineMs = now відповіді + blockWindowMs`, а не `дедлайн ходу + blockWindowMs`.
